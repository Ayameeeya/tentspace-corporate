MCPサーバーがクライアントへ提供できるものは、ツール（tools）だけではありません。仕様にはリソース（resources）とプロンプト（prompts）という、あと2つのプリミティブがあります。結論から言うと、3つの違いは「できること」ではなく**「誰が起動を決めるか」**です。toolsはモデルが、resourcesはアプリケーション（ホスト）が、promptsはユーザーが決める。そして実務の使い分けは、この分類を覚えた後に、**対象クライアントがどのプリミティブへ対応しているかを数えてから**決めます。私は自作MCPサーバーで、読み取り専用の機能も含めてすべてをtoolsとして実装していますが、これは理解不足の「全部tools」ではなく、数えた結果の判断です。

想定読者は、MCPの概要は知っていて、これからサーバーを設計する方。「toolsしか使っていないけど、resourcesやpromptsも使うべきなのか」が気になっている方です。3つの違い、教科書どおりに分けると詰まる場面、使い分けを決める質問の順に整理します。MCP自体の仕組みから知りたい場合は、先に入門記事をどうぞ。

## 3つのプリミティブは「誰が起動を決めるか」で分かれる

まず仕様上の整理です。MCPサーバーが提供できる主なプリミティブは3つで、公式ドキュメントはそれぞれに想定する制御主体を割り当てています。

| プリミティブ | 起動を決める主体 | 典型的な用途 | 代表的なメソッド |
| --- | --- | --- | --- |
| tools | モデル | 検索、計算、書き込みなどの実行 | `tools/list` / `tools/call` |
| resources | アプリケーション（ホスト） | ファイルやドキュメントを文脈として渡す | `resources/list` / `resources/read` |
| prompts | ユーザー | 定型ワークフローの呼び出し | `prompts/list` / `prompts/get` |

<LinkCard url="https://modelcontextprotocol.io/docs/concepts/tools" title="MCP公式ドキュメント: Tools（Resources・Promptsも同階層にあります）" />

### tools: モデルが「呼ぶかどうか」を判断する

toolsは、モデルが会話の流れから必要性を判断して呼び出す機能です。入力はJSON Schemaで定義し、副作用のある操作（書き込み、送信、削除）も持てます。「モデルが起動を決める」ので、エージェントに自律的な作業を任せる場面の主役はこれになります。多くのMCP解説がtools中心なのは、単に説明が楽だからではなく、現状のエージェント運用で実際に回っているのがここだからです。

### resources: アプリケーションが「文脈に載せるか」を決める

resourcesは、URIで識別されるデータです。ファイル、ログ、設定、ドキュメントのような「読ませたいもの」をサーバー側が一覧として公開し、**どれをモデルの文脈へ載せるかはホストアプリケーション側（またはそのUIを操作するユーザー）が決めます**。仕様が想定しているのはapplication-controlled、つまりモデルが勝手に取りに行く形ではありません。

たとえばClaude Codeでは、MCPサーバーのresourcesは`@サーバー名:URI`の形の@メンションで参照する使い方になっています。人がチャット欄で「この資料を見て」と選んで渡す形です。

### prompts: ユーザーが「明示的に」呼び出す

promptsは、引数を取れるメッセージテンプレートです。サーバーが「このサーバーを使うならこういう定型指示が便利です」という形で配布し、**ユーザーが明示的に選んで起動します**。Claude Codeではスラッシュコマンド（`/mcp__サーバー名__プロンプト名`）として現れます。コードレビューの定型手順や、決まった形式での問い合わせ起票のような、「人がきっかけを作る定型ワークフロー」の置き場です。resourcesの@参照とあわせて、ホスト側の対応の形は[Claude CodeのMCPドキュメント](https://code.claude.com/docs/en/mcp)に記載があります。

### 同じ「記事一覧」でも、toolとresourceでは形が違う

分類だけだと抽象的なので、同じ読み取り機能を両方の形で書いたときの違いを最小の形で示します。公式TypeScript SDKだと、toolは「モデルに見せる説明と入力スキーマ」を持つ関数として登録します。

```typescript
// tool版: モデルが「呼ぶかどうか」を判断するための説明を持つ
server.registerTool(
  "articles_list",
  {
    description: "公開済み記事の一覧を返す。重複チェックに使う",
    inputSchema: { query: z.string().optional() },
  },
  async ({ query }) => ({
    content: [{ type: "text", text: await listArticles(query) }],
  })
);
```

resourceは、URIで識別されるデータとして登録します。説明の宛先はモデルではなく、一覧を表示して選ばせるホストUIです。

```typescript
// resource版: URIで識別され、ホスト側が一覧から選んで読む
server.registerResource(
  "articles",
  "articles://list",
  { title: "公開済み記事一覧", mimeType: "application/json" },
  async (uri) => ({
    contents: [{ uri: uri.href, text: await listArticles() }],
  })
);
```

中身の処理は同じでも、tool版には「いつ呼ぶべきか」をモデルへ伝える説明文が要り、resource版には要りません。**定義の形そのものが、起動を判断する相手の違いを映しています**。どちらで実装するかは、この「説明を読んで起動を決めるのは誰か」を先に決めないと選べない、ということでもあります。

## 「読み取りはresources」と分けたら、無人運用で止まった設計になる

ここからが本題です。この3分類を覚えると、きれいに分けたくなります。「副作用のある操作はtools、読み取り専用のデータはresources、定型手順はprompts」。REST APIでGETとPOSTを分けるのと同じ感覚で、行儀のよい設計に見えます。

私も自作サーバーの設計時にこの分け方を検討しました。公開済み記事の一覧や本文を返す機能は読み取り専用なので、教科書どおりならresourcesの候補です。でも実装する前に気づきました。**私の運用では、それを読むのは人間ではなくエージェントです**。

resourcesはapplication-controlled、つまり「ホストのUIで人が選んで文脈に載せる」ことを想定したプリミティブです。ところが無人のRoutine実行には、@メンションで資料を選んでくれる人がいません。エージェントが「既存記事と重複していないか確認したいから一覧を読む」と**自分で判断して取りに行く**必要がある。その起動判断の主体はモデルです。つまり分類の正解は、データの性質（読み取り専用かどうか）ではなく、起動主体で引いたとおり**tools**でした。この判断で組んだサーバーの実装は[自作MCPサーバーの記事](/blog/mcp-server-cloudflare-workers)に書いています。

もう1つ、設計より先に数えるべき現実があります。クライアント側の対応状況です。MCP公式サイトのクライアント一覧には、各クライアントがどのプリミティブへ対応しているかの表があります。見ると分かりますが、**tools対応がもっとも広く、resourcesとpromptsへの対応はクライアントによって分かれます**。

<LinkCard url="https://modelcontextprotocol.io/clients" title="MCP公式: クライアント一覧とプリミティブ対応表" />

ここから出る実務の順序はこうです。サーバーを設計する前に、自分のサーバーを**どのホストから使うのか**を先に確定し、そのホストの対応列を見る。resourcesに対応していないホストから使うなら、resourcesとして実装した機能は存在しないのと同じです。逆に、社内ツールとして特定のホスト1つで使うと決まっているなら、そのホストが対応している範囲で3プリミティブを使い分ける価値が出ます。

「全部toolsにする」は、この2つ（起動主体が常にモデルである運用か、対象ホストの対応状況）を数えた帰結なら、手抜きではなく設計判断です。逆に、数えずに「toolsしか知らないから」で寄せているなら、次の節の使いどころを一度見ておく価値があります。

## resourcesとpromptsが効く場面

では、どういうときに残り2つを使うのか。起動主体の分類に戻すと整理が早いです。

**resourcesが効くのは、「人がホストのUIで素材を選んで渡す」体験を作りたいときです。** たとえばIDEやチャットUIで、サーバーが公開するドキュメント群から必要なものだけを@メンションで文脈に載せる形。toolsで同じことをすると、モデルが「どれを読むか」を毎回判断することになり、人が選びたい場面ではむしろ邪魔になります。渡す素材の選択権を人に残したいかどうかが分かれ目です。

**promptsが効くのは、サーバーの正しい使い方そのものを配布したいときです。** 複数ツールを決まった順で使う手順や、引数の揃え方をテンプレートにして、ユーザーがスラッシュコマンド一発で起動できるようにする。「使い方のドキュメントを読んでもらう」のではなく「正しい使い方を実行可能な形で同梱する」イメージです。

なお「手順を配る」が目的なら、MCPのpromptsだけでなくスキル（SKILL.md）という選択肢もあります。ツール定義がコンテキストに載る固定費の話も含めて、こちらの記事に整理しています。

<LinkCard slug="mcp-tool-overload-context" />

コンテキストの固定費は、この使い分けでも効いてきます。toolsの定義は使われなくても毎セッション文脈に載りますが、resourcesの中身は読まれたときだけ載ります。「モデルに判断させるために常時見せておく」toolsと、「必要になったときだけ運ばれる」resources。同じデータでも、どちらに置くかで文脈の消費パターンが変わります。

## プリミティブは3つで終わりではない

本題は3つの使い分けですが、仕様のプリミティブはこれで全部ではないことも触れておきます。サーバー側からクライアントのモデルへ生成を依頼するsampling、ツール実行の途中で人へ確認や入力を求めるelicitationなど、「サーバー→クライアント」方向の機能も定義されています。elicitationは便利そうに見えて、無人実行では「答える人がいない」ために空振りする罠があり、これは[別の記事](/blog/mcp-elicitation)に整理しました。

方向性としては今回の話と同じです。**どのプリミティブも「誰がそこにいる前提の機能か」を持っていて、自分の運用にその誰かがいるかを先に数える**。人が対話する前提の機能を無人運用へ持ち込むと、仕様上は正しくても動かない設計になります。

## 使い分けを決める3つの質問

まとめとして、私がサーバー設計時に使っている質問を3つ置いておきます。

1. **その機能の起動を決めるのは誰か。** モデルが自分の判断で使うならtools。人がUIで選んで渡すならresources。人がきっかけを作る定型手順ならprompts。データの性質（読み取り専用かどうか）では分けない
2. **対象ホストはそのプリミティブに対応しているか。** 公式クライアント一覧の対応表で、自分が使うホストの列を先に見る。対応していないプリミティブに実装しても存在しないのと同じ
3. **その定義は文脈にいつ載るべきか。** 常時見せてモデルに選ばせたいならtoolsの固定費を払う。必要なときだけ載ればよい素材なら、resourcesか、ツール経由で読む設計にして本文だけを運ぶ

私の自作サーバーが「全部tools」なのは、質問1の答えが常に「モデル」で、質問2の運用ホストが無人実行前提だからです。前提が変われば答えも変わります。たとえば人が対話しながら使う社内アシスタントを作るなら、resourcesとpromptsを使う設計を最初から検討します。

3つのプリミティブの違いは、覚えること自体は5分で終わります。設計で効くのは、機能一覧を眺めることではなく、自分の運用の起動主体と対応状況を数えることでした。
