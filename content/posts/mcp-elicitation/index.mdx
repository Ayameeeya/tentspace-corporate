結論から言うと、MCPのelicitationは「ツール実行の途中で、サーバーが人に聞き返す」ための仕組みです。曖昧なまま進むより、聞いてから進むほうが安全。対話で使う分には、素直に良い仕様だと思います。

ただ、先に言い切っておきます。**無人実行では、elicitationは必ず空振りします。** 答える人がその場にいないからです。そして空振りがただの「失敗」としてモデルへ返ると、モデルは再試行で解決しようとします。書き込み系のツールでこれが起きるのが、一番怖いパターンです。Claude Code 2.1.310がこの場面のエラー文言を変えたのは、まさにこの事故を小さくするための手当でした。

この記事では、elicitationの仕組みを仕様の一次情報から整理し、Claude Code側の最近の変更を読み、無人運用に対話前提のツールを持ち込まないための線引きをまとめます。想定読者は、MCPサーバーを自作している方と、エージェントの定時実行・ヘッドレス実行を運用している方です。

## elicitationとは。サーバーが「逆向きに」聞いてくる

MCPのやり取りの基本方向は、クライアントからサーバーです。エージェントが`tools/call`でツールを呼び、サーバーが結果を返す。elicitationはこの向きが逆転します。ツールを実行している途中のサーバーが、クライアント経由でユーザーに問い合わせを送り、回答を受け取ってから処理を続けるのです。

elicitationは2025-06-18の仕様改訂で導入されました。要点は4つです。

<LinkCard url="https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation" title="MCP仕様 2025-06-18: Elicitation" />

1. **使えるのは、クライアントが対応を宣言した場合だけ。** elicitationはクライアント側のcapabilityで、宣言していないクライアントにサーバーが問い合わせを送ることはできません
2. **聞けるのは単純なフォームだけ。** サーバーが要求できるのはフラットなオブジェクトで、プロパティは文字列・数値・真偽値などのプリミティブに限られます。ネストした複雑な構造は要求できません
3. **ユーザーの応答は3分類。** 回答して進める「accept」、明示的に断る「decline」、何もせず閉じる「cancel」。サーバーはこの3つを区別して受け取ります
4. **機微情報を求めてはならない。** 仕様は、サーバーがelicitationでパスワードなどの機微情報を要求することを禁じています。UIの見せ方はクライアントの持ち物で、どのサーバーからの問い合わせかを利用者に明示する形が求められます

用途としてイメージしやすいのは、曖昧さの解消と確認です。「同名のファイルが既にあります。上書きしますか」「候補のリポジトリが3つ見つかりました。どれですか」。呼び出し時の引数だけでは決めきれないことを、実行の途中で人に返す。これがelicitationの役割です。

## なぜ「途中で聞ける」が必要とされたのか

elicitationがない世界でも、同じことはできていました。決めきれない状況になったらツールがエラーを返し、エージェントが引数を増やして呼び直す。つまり「聞く」を呼び出しの外側でやる形です。

この形の弱点は、確認の相手がエージェント（モデル）になることです。「上書きしますか」への答えをモデルが勝手に推測して呼び直してしまえば、人に聞いた意味がありません。elicitationは問い合わせの宛先を人に固定し、往復を1回のツール呼び出しの中に畳み込みます。サーバーは質問の中身だけを決め、見せ方と答えるかどうかの主導権はクライアントとユーザー側に残る。サーバーが一方的に押し込むのではなく、クライアント側が受けると宣言した分だけ成立する契約型の設計で、この構図は[イベント購読の記事](/blog/mcp-event-subscriptions)で整理した`subscriptions/listen`とも共通しています。

ここまでが、elicitationの「表の顔」です。人がその場にいる対話セッションでは、この仕組みは素直に機能します。

## 2.1.310の修正が示した、無人実行との衝突

今回この記事を書くきっかけになったのは、Claude Code 2.1.310（2026-10-23リリース）のchangelogにあった一文です。非対話セッションで、elicitationが未応答のままMCPツール呼び出しがタイムアウトしたときのエラーが変更されました。新しいエラーは「応答が来なかった」ことと、**「同じ呼び出しを繰り返すな」** をモデルへ明示します（確認日2026-10-24）。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code changelog" />

地味な変更に見えますが、私はここに無人運用の急所が全部詰まっていると読みました。

非対話セッション、つまり`claude -p`でのヘッドレス実行や定時実行には、フォームに答える人がいません。サーバーがelicitationを送った瞬間に、その呼び出しの行き先は決まっています。誰も答えず、タイムアウトまで待って、落ちる。空振り自体は避けられない構造です。

問題はその後です。タイムアウトが「ツール呼び出しの失敗」という一般的な顔で返ってくると、モデルは失敗を挽回しようとします。一番ありそうな挽回策は、同じツールをもう一度呼ぶこと。ところがelicitationはツール実行の途中で発生するので、一度目の呼び出しがどこまで進んでいたかは外から分かりません。書き込み系のツールなら、半分進んだ処理の上にもう一度同じ処理が走る可能性があります。

Claude Codeはこの少し前、2.1.307で「接続が途中で切れたHTTP MCPツール呼び出しの二重送信」を修正し、自動の再試行を読み取り専用か冪等なツールだけに限定しています（確認日2026-10-22）。2.1.310は同じ関心の続きだと読めます。「この呼び出しは繰り返してよいか」という線引きを、再試行ロジックだけでなくエラー文言のレベルまで下ろし、モデル自身に「繰り返すな」と伝える。二重実行の危うさについては別の記事で整理したので、そちらもどうぞ。

<LinkCard slug="mcp-idempotency-retry" />

つまりこの修正は、elicitationを便利にする話ではありません。**対話前提のツール呼び出しが無人経路に紛れ込んだとき、事故を小さくする話です。** 紛れ込むこと自体は、クライアント側の文言改善では止まりません。止めるのは運用側の設計です。

## 対話前提のツールを、無人経路から外す3つの線引き

以上を踏まえて、無人運用側で引く線を3つに絞ります。

1. **ツール表面を「対話前提」と「無人可」で分ける。** elicitationに依存するツールは、ヘッドレス実行や定時実行の経路に含めない。厄介なのは、あるツールがelicitationを送りうるかどうかがツール定義の一覧からは見えないことです。サーバーのドキュメントか実装を確認して棚卸しし、無人経路に渡すツールの許可リストを対話セッションとは別に持つのが確実です
2. **聞く代わりに、既定値と入力で決める。** 無人運用での確認は、実行時に人へ聞くのではなく、呼び出し時の入力に寄せます。上書き可否なら`overwrite`のような明示パラメータ、危険な操作の承認なら確認フラグを引数で渡し、渡されなければ安全側の既定値で動く。「実行の瞬間に人が承認する」前提を外して既定値で作る考え方は、別の記事でも整理しています
3. **サーバー側は、再試行を誘発しないエラーを返す。** 自作MCPサーバーで人の応答を待つ処理を入れるなら、未応答のタイムアウトを一般的な失敗と同じ顔で返さないことです。「応答が得られなかった。再送しても結果は変わらない」まで言い切るエラーにする。Claude Codeが2.1.310で入れた文言変更は、クライアント側から見た同じ答えです

<LinkCard slug="ai-agent-human-in-the-loop" />

3つに共通するのは、「聞けるかどうか」ではなく「聞けない経路がある」を設計の前提に置くことです。

## 人に聞ける仕様は、無人運用では境界線になる

elicitationは、人がその場にいる対話では正しい仕組みです。曖昧なまま進むより、聞いてから進むほうがいい。[MCPの入門記事](/blog/what-is-mcp)では「そういう拡張もある」程度に流しましたが、対話セッションでの価値は疑っていません。

一方で無人運用の側から見ると、elicitationは機能ではなく境界線です。このツールは人がいないと完走しない、という印が付いているのと同じ。無人経路に要るのは聞ける仕組みではなく、聞かずに済む入力設計です。

対話前提と無人可の線は、クライアントの文言改善が引いてくれるものではなく、ツールを渡す側と運用する側が引くものです。定時実行のエージェントにMCPサーバーを渡している方は、そのサーバーのツールに「人に聞き返すもの」が混ざっていないか、一度だけ棚卸ししておくことをおすすめします。空振りのタイムアウトを待つより、ずっと安い確認です。
