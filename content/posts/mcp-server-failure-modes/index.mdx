MCPサーバーを運用に組み込んで困るのは、実は「接続できない朝」だけではありません。運用してみて効いてくるのは、**セッションの途中で構成が変わること**です。繋がらないのは起動時に1回だけ起きる問題ですが、途中の変化はセッションが長いほど、無人であるほど、気づかない形で起きます。

この記事では、MCPサーバーの運用で起きる失敗を3つのモードに整理します。「読み込まれない」「途中で変わる」「黙って外れる」の3つです。2026年11月のClaude Code 2.1.326と2.1.328の変更履歴には、この「途中で変わる」系統の挙動変更がまとまって入りました。公式が途中変更を前提として扱い始めた、と読める内容です。自作MCPサーバーを無人のスケジュール実行から呼んでいる立場から、変更の中身と運用側の設計を整理します。

想定読者は、MCPサーバーを定時実行やCIなどの無人経路で使っている方と、これから組み込もうとしている方です。「そもそも接続できない」段階の切り分けは別記事にまとめてあるので、初期設定のトラブルはそちらをどうぞ。

## 「接続できない」の切り分けは、起動時のスナップショットの話

上の記事で整理した設定→接続方式→権限の3段チェックは、セッションが始まる瞬間の話です。どこに登録されているか、どの方式で繋ぐか、権限はあるか。これらはセッション開始時に1回確定すれば、あとは変わらない前提で切り分けられます。

ところが実際のセッションは、その前提ほど静的ではありません。管理者が設定を配り直す。プラグインが入れ替わる。サーバーの接続が遅れて、ツール一覧が後から揃う。セッションが長く走る無人運用では、この「開始時と今で構成が違う」状態が普通に発生します。そして構成の変化は、エラーとして飛んでくるとは限りません。ツールが1本消えている、という静かな形で現れます。

## 2.1.326と2.1.328で「途中で変わる」が公式の前提になった

変更履歴を時系列で読むと、この領域に手が入り続けているのが分かります。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code Changelog（公式変更履歴）" />

2026年11月16日付の2.1.326には、管理者向け設定ファイル`managed-mcp.json`まわりの変更が2つ入りました（確認日2026-11-17）。1つは、セッションの実行中に管理者が`managed-mcp.json`を追加したとき、**なぜMCPサーバーの読み込みが止まるのかを説明するメッセージ**が追加されたこと。もう1つは、途中追加された`managed-mcp.json`が**次のチェック時点から部分的に適用されうる**ようになり、完全に適用するには開いているセッションの再起動が必要と明記されたことです。「次のチェック」の間隔がどれくらいか、どのサーバーが落ちるのかまでは変更履歴に書かれていません。

同じ2.1.326では、プラグインをアンインストールするとそのプラグインのMCPバンドル（.mcpb、.dxt）から展開されたファイルも削除されるようになりました（他のプラグインが同じバンドルを使っている場合を除く）。プラグインの出し入れが、MCPサーバーの実体ファイルの増減に直結するということです。

そして11月19日付の2.1.328では、MCPサーバーを持つCode Modeの新規セッションでプロンプトキャッシュが改善されると同時に、**サーバーがまだ接続中であること、サーバー一覧が変わったことがClaudeに伝えられる**ようになりました（確認日2026-11-20）。モデル側に「一覧は揺れるもの」という情報を渡す設計です。裏を返せば、それまでのモデルは一覧が揺れたことを知らされないまま、あるはずのツールを呼ぼうとしていたことになります。

## 障害と設定変更は、同じ顔で現れる

ここで運用側に効いてくるのは、**「障害」と「設定変更」が現象としては同じに見える**ことです。

セッションの途中でツールが消えたとします。原因がサーバーの障害なら、対処は待つか再試行です。原因が管理者の設定配布なら、対処はセッションの再起動で、再試行しても戻りません。現象は同じ「ツールがない」なのに、正しい対処が逆方向を向いています。2.1.326で追加された「なぜ読み込みが止まるのか」の説明メッセージは、まさにこの切り分けのための口だと読めます。

私自身、この「静かな欠落」は起動時の形で踏んでいます。定時実行の処理が、使う予定のMCPツール群が接続されないまま始まり、公開パイプラインが使えない状態で終わったことがありました。エラーは出ていません。ツールが最初から存在しない、という形でした。詳細は先ほどの接続トラブルシューティングの記事に書いたとおりです。起動時にこの形で起きることは、途中でも同じ形で起きます。むしろ途中のほうが、「さっきまで使えていた」という思い込みが挟まる分だけ気づきにくいはずです。

## 失敗モード1: 読み込まれない——欠落はエラーの顔をしていない

1つ目のモードは、セッション開始時にサーバーが読み込まれない・接続が間に合わないケースです。

これは既知の領域で、公式も続けて手を入れてきました。2.1.274ではSDKホストのMCPサーバーが接続中のうちに最初のターンが始まってしまう問題が修正され、2.1.273ではWeb版の定時実行が、組織のコネクタを外して入れ直した後も古いコネクタを呼び続ける問題が修正されています。2.1.328の「接続中であることをClaudeに伝える」は、この系統の最新の手当てです。

運用側でできることは2つあります。1つは、**本処理の前に読み取り専用のツールを1本呼んで、接続の有無をその場で確認する**工程を置くこと。欠落は「ツールが存在しない」という形で現れるので、存在確認がそのまま検出になります。もう1つは、実行結果をセッションの外側の記録で数えることです。接続の通知はセッション内に出ても、無人実行では誰も見ていません。

## 失敗モード2: 途中で変わる——再試行では直らない

2つ目のモードは、セッションの途中で構成が変わるケースです。`managed-mcp.json`の途中配布、プラグインの出し入れ、コネクタの入れ替え。2.1.326の変更で、途中配布は「次のチェックから部分適用・完全適用は再起動」という挙動になりました。

このモードの厄介さは、**部分適用という中間状態が公式に存在する**ことです。一部のサーバーは新しい設定で、一部は古いまま。この状態は障害ではなく仕様ですが、セッションの中から見れば「さっきまであったツールがない」「あるはずのないツールがある」という不整合として現れます。

運用の設計はシンプルに倒すのがよいと考えています。**長く走る無人セッションは、構成変更があったら再起動する**。中間状態のまま走り続けて原因不明の失敗を増やすより、構成変更をセッションの区切りとして扱うほうが、失敗の原因を数えられる状態を保てます。構成変更のタイミングを運用側が握れない場合（管理者配布など）は、前述の存在確認の工程が途中変化の検出口を兼ねます。

## 失敗モード3: 黙って外れる——書いた設定と実効値がズレる

3つ目のモードは、設定ファイルは変わっていないのに、実際に効いている値がズレるケースです。

2.1.326には、この系統の変更も入っています。`claude mcp serve`が`sandbox.excludedCommands`を無視するようになった変更。そして、`plugin.json`の表示フィールドの不備を理由に読み込みを拒否されていたプラグインが、**hooksとMCPサーバーごと読み込まれるようになった**変更です。後者には「管理者は配布しているプラグインを確認すべき」と注記が付いています。不備を理由に止まっていたものが動き出す方向の変化なので、「入っていないはず」のサーバーが入る側のズレも起きうるということです。

このモードは、設定ファイルの差分を見ても検出できません。ファイルは変わっていないからです。対処は**実効値の監査**になります。セッションが実際に持っているツール一覧を取得して、使う予定のツールが名指しで存在するか、想定外のサーバーが混ざっていないかを突合する。全ツールの網羅監査を毎回やるのはコストが重いので、公開処理のような外部に副作用のある工程の前だけに絞って突合を置くのが現実的だと考えています。

## 揺れはコストにも効く

ツール一覧の揺れは、機能の欠落だけでなくコストにも波及します。プロンプトキャッシュはプレフィックス一致で効くため、会話の途中でツール一覧が書き換わると、積み上げたキャッシュが破棄されるからです。この構図は別記事で整理しました。

<LinkCard slug="claude-code-cache-miss-tool-changes" />

2.1.328の「MCPサーバーを持つCode Modeセッションのキャッシュ改善」と「一覧の変化を伝える」が同じ行に並んでいるのは、この2つが同じ問題の両面だからだと読んでいます（この読みは私の解釈で、改善幅の数値は変更履歴にありません）。構成の揺れを前提にした設計は、安定性のためだけでなく、トークン請求を読める状態に保つためでもあります。

## まとめ: 版を上げる前に数える3点

MCPサーバーの運用失敗を3つのモードで整理しました。

1. **読み込まれない**: 欠落はエラーではなく「ツールが存在しない」という形で現れる。本処理前の存在確認と、外側で数える記録を置く
2. **途中で変わる**: 部分適用という中間状態が公式に存在する。構成変更をセッションの区切りとして扱い、再起動を運用の既定にする
3. **黙って外れる**: 設定ファイルの差分では検出できない。副作用の大きい工程の前に実効値を突合する

そのうえで、Claude Code本体の版を上げる前に変更履歴のMCP関連の行を読む習慣をおすすめします。2.1.326や2.1.328のように、設定ファイルを1文字も変えていなくても実効値が動く変更は、変更履歴にしか書かれていません。障害対応の手順書より先に、「障害と設定変更を見分ける口」を用意しておく。それがMCPサーバーを無人で回すときの、いちばん地味で、いちばん効く備えだと思います。
