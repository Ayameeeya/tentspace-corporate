結論から言うと、git worktreeで並列に進めた作業を合流させる専用コマンドは**存在しません**。マージは普通の`git merge`か`git rebase`で行います。worktree特有なのはコマンドではなく、**「どのworktreeで実行するか」と「どの順番で畳むか」**の2点です。この2点さえ決めておけば、合流は拍子抜けするほど普通のgit操作になります。

この記事は、[Claude Codeをgit worktreeで並列実行する方法](/blog/claude-code-git-worktree-parallel)の続きにあたります。前回は並列の「始め方」を整理しました。今回は「畳み方」です。想定読者は、worktreeで2〜3本のタスクを走らせたあと、「で、これどうやってmainに戻すんだっけ」と手が止まった方です。

## 合流の前に、worktreeの前提を30秒で復習する

[git worktree](https://git-scm.com/docs/git-worktree)は、1つのリポジトリに複数の作業ツリーを接続する標準機能です。合流を考えるうえで効いてくる性質は2つあります。

- **コミット履歴は全worktreeで共有される。** あるworktreeでコミットした瞬間、他のworktreeからもそのコミットは見えます。ローカル内の合流にpushもpullも要りません。
- **同じブランチを2つのworktreeで同時にチェックアウトできない。** gitがエラーで拒否します。この制約が、マージを「どこで実行するか」を事実上決めてくれます。

つまり、`feature-a`のworktreeと`feature-b`のworktreeで作業していても、成果はすべて同じリポジトリの中にあります。合流とは「リモートから取り込む」作業ではなく、「隣のブランチを混ぜる」だけの作業です。

## 手順の基本形——mainを持つworktreeに「取り寄せて」マージする

リポジトリ本体が`~/project`（mainをチェックアウト中）、タスク用worktreeが`~/project-feature-a`にあるとします。合流の基本形は3ステップです。

```bash
# 1. mainを持つworktreeへ移動する
cd ~/project

# 2. featureブランチをマージする（ローカル同士なのでfetch不要）
git merge feature-a

# 3. その場で検証する
npm test
```

ポイントは、**マージはブランチを受け取る側のworktreeで実行する**ことです。mainに合流させたいならmainをチェックアウトしているworktreeで、という当たり前の話ですが、worktreeが増えると「いまどこで何を実行しているか」を見失いがちです。迷ったら`git worktree list`で現在地を確認します。

```bash
git worktree list
# /home/you/project            abc1234 [main]
# /home/you/project-feature-a  def5678 [feature-a]
# /home/you/project-feature-b  789abcd [feature-b]
```

逆方向の操作、つまり**featureブランチ側をmainに追従させたい**ときは、featureのworktree側で`git rebase main`（または`git merge main`）を実行します。mainは別のworktreeがチェックアウト中でも、rebaseの対象として参照するだけなら問題ありません。チェックアウトの排他制約は「作業ツリーとして開くこと」への制約であって、「参照すること」への制約ではないからです。

## 詰まるのはマージコマンドではなく、順番と生成物

「worktree用のマージ手順」を探してこのページにたどり着いた方は多いはずです。でも答えは「存在しない」で、worktreeだから難しいことは何もありません。**詰まりやすいのは、並列作業そのものが作る次の2つの構造**です。

### 原因1: 合流の順番を決めていない

並列タスクが3本あるとき、[git merge](https://git-scm.com/docs/git-merge)には複数ブランチを一括で畳むoctopusマージという方式もありますが、手動解消が必要なコンフリクトがあると失敗する仕様です。コンフリクトを解消しながら進める実務では、1本ずつ畳むのが前提になります。このとき順番を決めずに進めると、2本目以降のマージで「1本目の変更と自分の変更」のコンフリクトをまとめて踏むことになります。

定石は次の形です。

1. **差分が小さい・リスクが低いタスクから先に**mainへマージする
2. 1本マージするたびに、**残りの全worktreeでmainを取り込む**（`git rebase main`）
3. 取り込みで出たコンフリクトは、その場で（そのタスクの文脈があるworktreeで）解消する
4. 次のタスクをマージする

一見遠回りですが、コンフリクトを「mainへのマージ時」ではなく「各worktreeへの取り込み時」に分散させるのが狙いです。マージの瞬間のmainは常にクリーンに保たれ、コンフリクト解消はそのコードを一番よく知っているセッションの手元で起きます。

### 原因2: コンフリクトの主戦場は生成物

並列作業の合流では、コンフリクトはアプリケーションコードよりも、**lockfileやビルド生成物などの自動生成ファイル**で起きがちです。複数のタスクがそれぞれ依存を追加していれば、`package-lock.json`はほぼ確実に衝突します。

生成物のコンフリクトは、手で混ぜてはいけません。**「どちらかを捨てて、ツールで再生成する」**が原則です。

```bash
# lockfileの衝突は手で解消せず、再生成する
git checkout --theirs package-lock.json  # いったんどちらかを採用
npm install                               # 両方の依存を含む状態で再生成
git add package-lock.json
```

手作業でlockfileの行を選ぶと、整合性の壊れたlockfileができあがります。再生成なら、マージ後の`package.json`（こちらは普通にコンフリクト解消する）を正として、機械が整合性を保証してくれます。

## コンフリクト解消をClaude Codeに任せるときの指示

コンフリクトが出たら、受け取り側のworktreeでClaude Codeを起動し、解消を任せられます。Anthropicの[公式ドキュメント（Common workflows）](https://code.claude.com/docs/en/common-workflows)でも、マージコンフリクトの解消はClaude Codeの典型的な用途として案内されています。

ただし、丸投げは危険です。コンフリクトとは「両方の変更が同じ場所を触った」という機械的な事実にすぎず、**どちらの意図を優先すべきかはコードの中に書かれていません**。それを知っているのは、両方のタスクを発注した人間だけです。

指示の型の例を挙げます。

```text
feature-aをmainにマージ中で、3ファイルがコンフリクトしています。
- mainに先に入ったfeature-bは「設定の読み込みをasync化」する変更
- feature-aは「設定にバリデーションを追加」する変更
両方の意図を残す形で解消してください。
解消後にnpm testを実行し、結果を報告してください。
```

要するに、**両側のタスクの意図を1行ずつ言語化して渡す**ことと、**解消直後の検証までをセットで指示する**こと。この2つを渡せば、Claude Codeは`git status`からコンフリクトファイルを特定し、両方の変更を読み、意図を保った解消を提案してくれます。逆にこれを渡さないと、「構文としては正しいが、片方の意図が静かに消えた」マージ結果になりえます。コンフリクト解消の失敗はビルドエラーのような分かりやすい形では現れないので、マージ直後のテスト実行までを1つの作業として扱うのが安全です。

## mainを汚さずに合流を試す——統合用worktreeという選択肢

「このままマージしてmainが壊れたら嫌だ」というときは、**統合テスト専用のworktreeを1つ作る**手があります。worktreeの追加は一瞬なので、使い捨ての合流実験場として使えます。

```bash
# mainから統合用ブランチを切ったworktreeを作る
git worktree add ../project-integration -b integration main

# そこで複数のタスクをまとめてマージしてみる
cd ../project-integration
git merge feature-a
git merge feature-b
npm test
```

ここでテストが通れば、mainへのマージは安心して実行できます。コンフリクトの解消結果も`integration`ブランチにコミットとして残っているので、本番のマージで同じ解消を再利用できます。逆に壊れていたら、`integration`ごと捨てるだけです。mainには一切痕跡が残りません。

```bash
cd ../project
git worktree remove --force ../project-integration
git branch -D integration
```

毎回やる必要はありません。合流の不確実性が高いとき——コンフリクトが数ファイル以上出そうなとき、複数タスクが同じモジュールを触っていたと分かったとき——だけこの形にして、普段の小さな合流は基本形の直接マージで十分です。

## 後片付け——worktreeとブランチを消すまでが合流

マージが済んだworktreeは放置せず、その場で片付けます。残したworktreeは「もう存在しない作業の机」であり、次の並列作業のときに自分を混乱させるだけだからです。

```bash
# 1. worktreeを削除する（未コミットの変更が残っているとgitが拒否してくれる）
git worktree remove ../project-feature-a

# 2. マージ済みブランチを削除する（未マージならgitが拒否してくれる）
git branch -d feature-a

# 3. 状態を確認する
git worktree list
```

どちらのコマンドも、消してはいけない状態（未コミットの変更、未マージのコミット）が残っていれば標準でエラーになります。`--force`を付けたくなったら、それは「何かを確認し忘れている」合図です。ディレクトリを`rm -rf`で直接消してしまった場合は、`git worktree prune`で管理情報だけを掃除できます。

## そもそもコンフリクトしない分け方が最大のマージ対策

最後に、順番の工夫よりも効く対策をひとつ。それは**タスクの切り方の時点で、触るファイルが重ならないように分ける**ことです。

前回の記事でも触れたとおり、worktreeはファイル編集の衝突を防いでくれますが、それは「作業中の衝突」を防ぐだけで、「合流時の衝突」は先送りされているだけです。同じモジュールを触る2つのタスクは、worktreeを分けても合流時に高い確率で対価を払います。

- **並列に向く分け方**: フロントエンドの改修とCIの修正、別モジュール同士、コードとドキュメント
- **並列に向かない分け方**: 同じサービス層のリファクタと機能追加、同じ設定ファイルを書き換える2タスク

向かない組み合わせだと気づいたら、worktreeで並列にせず、1本のブランチで直列にやる方が合計時間は短くなります。マージ運用の最適化には上限がありますが、コンフリクトを発生させない分割には上限がありません。

## まとめ

worktreeの合流に特別なコマンドはありません。やることは次の5つです。

1. マージは**受け取る側のworktree**で実行する（`git worktree list`で現在地確認）
2. 複数タスクは**小さいものから1本ずつ**畳み、1本ごとに残りのworktreeへmainを取り込む
3. lockfileなどの生成物は手で混ぜず**再生成**する
4. Claude Codeに解消を任せるときは**両タスクの意図と検証コマンド**をセットで渡す
5. マージ済みworktreeとブランチは**その場で削除**する

並列の始め方は軽快ですが、運用の実力が出るのは畳むときです。worktreeの作り方からやり直したい方は、前回の記事からどうぞ。
