結論から言うと、MCPのツール呼び出しは**同じ呼び出しが二度届くことがある**前提で設計すべきです。Claude Code 2.1.307のbug fixに、「HTTP MCPのツール呼び出しが、呼び出し中に接続が閉じたときに二度送られていた」不具合の修正が入りました。修正後に再試行されるのは、読み取り専用か冪等なツールだけです。裏を返すと、この修正より前は、投稿や削除のような書き込み系ツールも、接続断のたびに二度届き得たということです。

そしてもう1つ、先に言い切っておきます。この修正を見て「クライアントが賢くなったから、もう大丈夫」と考えるのは逆です。**二重実行を止める線は、ツールを受け取るサーバー側に引く。** クライアント側の線引きは歓迎ですが、安全装置としては数えません。

この記事では、接続断と再送がなぜ二重実行を生むのかという構造、MCP仕様のToolAnnotationsが保証するもの・しないもの、そして受ける側（自作MCPサーバー）に置く防波堤の設計を整理します。想定読者は、MCPサーバーを自作して書き込み系のツールをエージェントに渡している方、またはこれから渡そうとしている方です。

## 接続が切れた瞬間、呼び出しは「届いたか分からない」になる

まず2.1.307で何が直ったのかを押さえます。公式changelogのbug fixにはこうあります。HTTP MCPのツール呼び出しが、呼び出しの最中に接続が閉じられたとき、二度送られていた。修正後は、読み取り専用または冪等なツールだけが再試行される。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code Changelog（公式）" />

なぜ「二度送る」実装が生まれるのか。これはMCP固有のバグというより、ネットワークを挟んだ呼び出し全般が持つ古典的な性質です。応答が返ってこなかった呼び出しは、送る側から見ると2つの可能性を区別できません。

1. リクエストが届かずに消えた（実行されていない）
2. リクエストは届いて実行されたが、応答だけが失われた

再送しなければ1のケースで処理を取りこぼし、再送すれば2のケースで二重実行になります。送る側だけでこのジレンマは解けません。選べるのは「少なくとも1回は届ける（at-least-once）」と「多くても1回しか届けない（at-most-once）」のどちらに倒すかだけで、「ちょうど1回」は受ける側の冪等性と組み合わせてはじめて近似できます。

冪等（べきとう）とは、同じ操作を何度適用しても、1回だけ適用したときと結果が変わらない性質です。記事一覧の取得やステータス照会は何度呼んでも同じなので冪等。一方「投稿を1件作る」は、素朴に実装すれば呼んだ回数だけ投稿が増えるので冪等ではありません。

この整理で2.1.307の修正を読み直すと、Claude Codeは再送のジレンマに対して「冪等なツールはat-least-once、そうでないツールはat-most-once」という線を引いた、と読めます。線の引き方としては真っ当です。問題は、その線をどう判定しているかが見えないことです。

## クライアントは「冪等なツール」をどう見分けるのか

MCPの仕様には、ツールの性質をクライアントへ伝えるToolAnnotationsが定義されています。ツール定義に添えるメタデータで、主なものは次の4つです。

- `readOnlyHint`: 環境を変更しないツールかどうか（既定はfalse）
- `destructiveHint`: 破壊的な更新を行い得るかどうか（既定はtrue）
- `idempotentHint`: 同じ引数での再実行が追加の効果を持たないかどうか（既定はfalse）
- `openWorldHint`: 外部の世界と相互作用し得るかどうか（既定はtrue）

<LinkCard url="https://modelcontextprotocol.io/specification/2025-06-18/server/tools" title="MCP仕様: Tools — Tool annotations" />

一見、これで解決に見えます。サーバーが`idempotentHint: true`を宣言し、クライアントはそれを見て再試行の可否を決めればいい。しかし仕様自身が、その読み方に釘を刺しています。annotationsはあくまでヒントであり、ツールの振る舞いを忠実に説明する保証はない。クライアントは、信頼できるサーバーから来たものでない限り、annotationsを信頼してはならない、と明記されています。

当然の注意書きです。annotationsを書くのはサーバー作者自身、つまり自己申告です。悪意がなくても、実装を変えて宣言を直し忘れれば、その瞬間から宣言は実態とずれます。「冪等だと宣言されたツール」と「冪等なツール」は別物です。

さらに、2.1.307のchangelogは「読み取り専用または冪等なツール」をどう判定するのかを書いていません。annotationsの宣言を読むのか、ツールの性質を別の方法で推定するのかが不明です。サーバー作者の立場では、自分のツールが「再試行される側」と「されない側」のどちらに分類されたかを確かめる手段がない。クライアントの線引きを安全装置として数えられない理由が、ここでもう1つ増えます。

## サーバーを1行も変えていないのに、二重実行の条件が変わった

ここで視点をサーバー作者側に移します。私はSNS公開用のMCPサーバーをCloudflare Workersで自作して運用していますが、2.1.307の前後で、サーバーのコードは1行も変わっていません。それでも、二重送信が起きる条件はこう変わりました。

- 修正前: 接続が途中で閉じれば、どのツールも二度届き得た
- 修正後: 二度届き得るのは、読み取り専用か冪等と判定されたツールだけ（判定基準は非公開）

リスクが減る方向の変化なので、文句はありません。ただ、設計の観点で重要なのは、**この変化を自分では観測も制御もできなかった**という事実のほうです。クライアントの更新は、こちらのデプロイやリリースサイクルとは無関係のタイミングで降ってきます。

同じ構図は、MCPのプロトコルバージョンでも起きました。クライアント側の既定ネゴシエートバージョンが上がった結果、サーバーを触っていないのにツールが1本も表示されなくなったり、全ツール呼び出しが失敗したりする。その経緯は別記事に整理しています。

<LinkCard slug="mcp-protocol-version-compatibility" />

「今のクライアントは書き込みツールを二度送らない」も「今のクライアントはこの版でネゴシエートする」も、どちらも自分の管理外にある前提です。管理外の前提に安全を預けると、クライアントの次の更新で前提ごと動きます。だから、二重実行を止める実装は、自分が管理できる側——ツールを受けるサーバー——に置くしかありません。

## 受ける側に置く3つの防波堤

では、受ける側に何を置くか。実運用しているWorkerの構成から、3つに絞って書きます。

### 1. 書き込み系ツールは、実行前に「枠」か「対象」をロックする

公開系ツール（SNSへの投稿など）は、実行前にWorkers KVで公開枠を確保してから動く形にしています。単純な回数カウントではなく、reserve（予約）→commit（確定）/release（返却）の二段階です。同じ呼び出しが二度届いても、枠の予約が直列化の役割を果たすので、上限を超える公開には進めません。この実装の詳細は別記事に書いています。

<LinkCard slug="mcp-server-publish-rate-limit" />

もう1枚、対象側の排他もあります。投稿キューの行をclaim（取得宣言）して自分のものにしてから実行する設計で、2度目の実行は対象の状態遷移に失敗して止まります。こちらは[Notionキューでの排他claim設計](/blog/ai-agent-notion-queue-claim)として記事にしました。回数の「枠」と対象の「排他」は守る範囲が違うので、2枚重ねると、どちらかの想定漏れをもう片方が拾ってくれます。

### 2. 自前の再試行は「実行されなかったと確かめられる失敗」に絞る

二重実行の火種は、クライアントの自動再送だけではありません。自分で書くリトライも同じ性質を持ちます。

実運用のWorkerに再試行を足したのは2箇所だけです。ThreadsのHTTP 400（subcode 4279009、Media not found）と、Instagramのcode 9007（Media is not ready）。どちらも「素材側の準備がまだ」という系統の間欠エラーで、**同じエラーコードに限って1回だけ**再試行する形にしました。

逆に、タイムアウトや接続断のような「実行されたかどうか分からない失敗」は、自動再試行の対象にしていません。そこで再送すれば、クライアントの二重送信とまったく同じ問題を自分の手で作ることになるからです。再試行してよいのは、相手のエラー応答によって「実行されなかった」と確かめられる失敗だけ。この線を狭く保つほうが、リトライ回数を増やすより事故が減ります。

### 3. annotationsは正しく書く。ただし安全装置には数えない

自己申告に意味がないわけではありません。annotationsは、クライアントが確認ダイアログを出すかどうか、再試行するかどうかの判断材料になり得ますし、ツール一覧を読む人間にとってのドキュメントにもなります。書くべきです。

ただし、順序を間違えないことです。実装を冪等にすれば、宣言がなくてもサーバーは安全です。宣言だけ冪等にしても、サーバーは1ミリも安全になりません。だから、先に実装の性質を決めて、annotationsはそれを写す。そして宣言と実装がずれないよう、ツール定義のスナップショットをテストで固定しておく。守る順番は実装→宣言で、その逆はありません。

## 冪等にできないツールを、冪等に寄せる型

「投稿を1件作る」のような操作は、操作そのものを冪等にはできません。それでも、受け側の設計で「2度目」を無害化する型はいくつかあります。

- **冪等キー**: 呼び出し側がリクエストに一意のキーを添え、受け側は同じキーの2度目に対して、再実行せず初回の結果をそのまま返す
- **状態遷移で弾く**: キューの行を「処理中」へ遷移させてから実行する。2度目は遷移に失敗して止まる（claim設計はこの型です）
- **枠の予約で弾く**: 公開枠をreserveしてから実行する。2度目は枠の制約に当たる（reserve→commitはこの型です）

共通するのは、「2度目が来るかどうか」を予測しないことです。クライアントの実装、ネットワークの状態、自分のリトライ——どこから来るかは制御できないので、来ても壊れない構造だけを信じます。

## まとめ

最後に、設計の確認項目として整理します。

- MCPのツール呼び出しは二度届き得る。クライアント側の再送条件は2.1.307で狭まったが、判定基準は公開されていない
- 仕様のToolAnnotationsはヒントであり、仕様自身が「信頼できるサーバー由来でない限り信頼するな」と明記している
- 書き込み系ツールは、枠の予約・対象の排他・冪等キーのいずれかで「2度目」を無害化する
- 自前の再試行は、「実行されなかった」と確かめられるエラー応答に限定し、回数も絞る
- クライアントの更新は管理外。管理外の前提に安全を預けない

クライアントが賢くなるのは良いことです。ただ、その賢さは自分のサーバーの外にあり、バージョンひとつで変わります。二重実行の防波堤を自分の側に持っているかどうかは、クライアントが何であっても変わらない、数少ない自分で決められる部分です。
