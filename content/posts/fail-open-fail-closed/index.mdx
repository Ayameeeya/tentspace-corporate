ガードは、書いた時点では安全装置になっていません。そのガード自体が評価できなかった瞬間に「通す」か「止める」か——フェールオープンとフェールクローズのどちらへ倒れるかを決めて、初めて安全装置になります。そして不可逆な操作を守るガードの既定は、フェールクローズ（止める）に置くべきです。

この記事では、セキュリティ設計の古典であるフェールオープン／フェールクローズの違いを整理し、AIエージェントのガードレールに当てはめます。後半では、Claude Codeが2026年10月の連続リリースでフックの既定を「止める側」へ寄せた変更群を一次情報から読み、自分の運用中のガードを棚卸しした結果を書きます。対象読者は、エージェントに自動実行を任せ始めた開発者と、その統制設計を確認したい発注側の方です。

## フェールオープンとフェールクローズとは

フェールオープン（fail-open）とフェールクローズ（fail-closed）は、検査や制御の仕組みが**故障したときにどちらへ倒すか**という設計方針の呼び名です。

- **フェールオープン**: 検査が動かないとき、対象を**通す**。守るのは可用性。
- **フェールクローズ**: 検査が動かないとき、対象を**止める**。守るのは統制と機密性。

ネットワーク機器が定番の例です。ファイアウォールが故障したとき、通信を全部通せば業務は止まりませんが、無検査のトラフィックが流れます。全部遮断すれば安全ですが、業務が止まります。どちらが正解かは機器の性能では決まりません。**落ちたときに失うものがどちらか**で決まります。

ここで大事なのは、フェールオープンもフェールクローズも「故障しにくさ」の話ではないことです。検査は必ずいつか評価に失敗します。プロセスが起動しない、タイムアウトする、想定外の入力が来る。そのときの既定値をどちらに置くかは、検査のロジックとは独立した、もう1つの設計判断です。

## AIエージェントのガードに当てはめる

AIエージェントの運用では「プロンプトの禁止は確率的だから、破られたくない一線はフックや権限ルールの決定的な層に置く」という整理が広まりつつあります。私もSNS運用の自動化で同じ構成を取っていて、mainへの直接pushや自己マージを止めるBashガードの実装は[以前の記事](/blog/claude-code-hooks-bash-guard)に書きました。

ただ、この整理には盲点があります。**その決定的な層自体が評価できなかったとき、どうなるか**です。

- ガードのスクリプトが起動に失敗したら？
- ガードがタイムアウトしたら？
- ガードに渡る入力が、途中で切り詰められていたら？

人間が横で見ている対話的な使い方なら、ここは大きな問題になりません。ガードがエラーを吐けば画面に出て、人が気づきます。しかし無人運用では話が変わります。フェールオープンの検問は、落ちたときに**「検問を通過した」と「検問が存在しなかった」が同じ結果になる**。ログ上はどちらも「ツールが実行された」でしかなく、検問が消えていたことに気づく契機がありません。

だから無人でエージェントを回すなら、不可逆な操作を守るガードの既定はフェールクローズに置く。これが冒頭の結論です。

## Claude Codeは2026年10月に「止める側」へ寄った

この設計判断を裏付ける動きが、Claude Code本体で立て続けに起きました。公式changelogの2026年10月の連続リリースに、フックの「落ちたときの倒れ方」に関する変更がまとまって入っています（いずれも確認日2026-10-15）。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code changelog（公式）" />

時系列で並べます。

| バージョン（公開日） | 変更 | 倒れ方の変化 |
| --- | --- | --- |
| 2.1.290（10-05） | PreToolUseフックがツール入力を書き換えた後、一部の権限ルールと安全チェックが適用されていなかった問題を修正 | 書き換え後の再判定が通る側に抜けていた穴を閉鎖 |
| 2.1.294（10-08） | 指示文として書いたprompt / agentフック（例「〜なコマンドをブロックせよ」）が、ブロックすべき対象を通していた問題を修正 | 自然文の検問が判定できず通していた穴を閉鎖 |
| 2.1.295（10-08） | command・HTTPフックに `onFailure: "block"` を追加。起動できない・タイムアウトした・想定外の終了コードで終わったフックが、対象の動作をブロックできるように | フック失敗時の倒れ方を**設定で選べる**ように |
| 2.1.295（10-08） | 深くネストしたツール入力が、エラーなしに切り詰められた状態でフックへ渡っていた問題を修正 | ガードが見ていない内容が通り得る穴を閉鎖 |
| 2.1.299（10-14） | ブロック権限を持つpluginフックは、フックへ渡せなかった・フックが答えを返せなかった場合に「通す」ではなく「拒否」に変更。実行済みのツールは結果を差し止め | 評価不能時の**既定そのものをフェールクローズへ** |
| 2.1.299（10-14） | Windowsでshell未指定のPreToolUse / PermissionRequestフックが、Git for Windows不在で失敗したとき素通りしていた問題を、失敗したガードは呼び出しをブロックする側へ修正 | fail-openだった失敗経路をfail-closedへ |

個別に見ればただのバグ修正と機能追加です。しかし並べると向きが揃っています。**「フックが評価できないときは通す」だった既定が、10日ほどの間に「止める」側へ段階的に寄せられた**。2.1.295までは `onFailure: "block"` という任意指定の形で、2.1.299ではpluginフックの既定値そのものが変わっています。

私がこの変更群で一番重いと思うのは、2.1.299の「通す」から「拒否」への文言です。つまりそれまでは、ブロックを期待して書いたフックでも、フック自体に入力が渡らなければ対象は通っていた。**フックを書いたかどうかと、フックが落ちたときに守られるかどうかは、別の軸だった**ということです。私はこの軸を、恥ずかしながら10月のchangelogを読むまで設計項目として持っていませんでした。

## 自分のBashガードを棚卸しする——中は閉じていて、外が開いていた

そこで、運用中のガードを「落ちたときの倒れ方」で棚卸ししました。対象は、SNS運用自動化のリポジトリに置いているPreToolUseのBashガードです。bashのラッパースクリプトがNode.jsの検査スクリプトを起動し、禁止パターンに一致したら終了コード2（ブロック）で止める構成です。

結果は半分合格でした。

**閉じていたところ**: 検査スクリプトの中では、標準入力のJSONをパースできなかったとき、素通しせずに終了コード2で止める実装になっていました。「読めない入力は通さない」という意味で、スクリプトの内側はフェールクローズです。

**開いていたところ**: スクリプトの外側です。この構成は bash → Node.js の2段になっていて、Node.js自体が起動できない環境ではラッパーが異常終了します。その終了コードは2ではありません。フックのブロックは終了コード2が条件なので、**ガードの起動失敗は「ブロック」として扱われない**。タイムアウトも同様で、検査スクリプトの中からはどうやっても倒す方向を選べません。ここはまさに、2.1.295の `onFailure: "block"` が初めて埋めた領域です。

つまり、検問の中身をどれだけ丁寧にフェールクローズで書いても、**検問を呼び出す層の既定がフェールオープンなら、全体はフェールオープン**です。鍵のかかった門を作っても、門が建たなかった日は素通りになっていました。

採否ははっきりしています。`onFailure: "block"` は入れる側です。ただし、うちの運用ではフック設定を含む設定ファイルを「エージェントが自分で書き換えない層」としていて、変更は人間のレビューを通す決まりにしています。なのでこの記事の時点では変更案を出した段階で、適用後の挙動はまだ未検証です。適用して分かったことがあれば追記します。

## すべてを閉じると運用が止まる——fail-openに残す範囲の決め方

ここまで読むと「全部フェールクローズにすればいい」となりそうですが、それは可用性を捨てる判断です。フェールクローズは誤停止を受け入れる設計なので、検査スクリプトのバグひとつで、本来通るべき操作まで全部止まります。無人運用なら、誰も気づかないまま夜間のパイプラインが全滅する形です。

私は倒す方向を操作の性質で分けています。

- **フェールクローズに置くもの**: 不可逆な操作と、境界の外に出る操作。外部への公開、本番デプロイ、削除、資格情報に触れる読み取り。失敗の損害が「止まった」では済まないもの。
- **フェールオープンを許すもの**: 読み取り専用で可逆な操作。コードの検索、ファイルの閲覧、ローカルのビルド。検査が落ちても、最悪「余計に読んだ」で済むもの。

そしてフェールクローズに倒した場所には、**止まったことに気づく経路**を必ずセットにします。止める設計は「止まったまま誰も知らない」と表裏一体だからです。うちでは公開系の操作をWorker側の回数制限とSlack通知で挟んでいて、公開の成否と結果の未反映をSlackへ通知・警告する形にしています。この多層の分け方は[権限設定4層の記事](/blog/claude-code-permission-layers)に書いた「渡さない・許す・止める・外側で強制」の整理とつながる話です。

## まとめ：ガードを棚卸しする3つの質問

フェールオープンとフェールクローズは、検査が壊れたときに通すか止めるかという設計方針の違いです。検査のロジックをどれだけ固くしても、この軸を決めていなければ安全装置は完成していません。Claude Codeの2026年10月の変更群は、この軸の既定を「止める」側へ寄せる動きでした。

自分のガードを棚卸しするなら、質問は3つで足ります。

1. **検問が評価できないとき、通るか止まるか。** 設定で明示しているか、プラットフォームの既定に任せているか。既定は今回のようにバージョンで変わります。
2. **止まる側に倒した場所で、止まったことをどう知るか。** 検知の経路がなければ、フェールクローズは静かな全停止と区別がつきません。
3. **開けたまま残す例外はどれか、理由を書いたか。** 全部閉じる設計は長続きしません。開ける場所を選んだ理由が書いてあれば、あとから見直せます。

フックを書いた日ではなく、フックが落ちた日の挙動を決めた日が、ガードが安全装置になった日です。
