結論から言うと、LLMのトークン数は送る前に数えられます。各プロバイダが公式の数え方を用意しているからです。ただし、数えた値で**コストを見積もることはできません**。事前カウントで確定するのは入力の、それも1ターン分だけ。本当の持ち場は見積もりではなく、「この入力は送れるのか」の検証と、「プロンプトの固定費が増えていないか」の回帰検知です。

想定読者は、LLM APIをアプリや自動化に組み込んでいて、トークンという課金単位を「だいたい文字数÷4」のような目安で扱っている実装者です。数える手段の整理から、数えた値で判断してよいこと・いけないことの境界までを扱います。

## トークンは請求の単位なのに、目安で扱われがち

LLM APIの請求は、リクエスト回数ではなくトークン数で決まります。入力に何トークン、出力に何トークン。実測値はレスポンスの`usage`フィールドに毎回返ってきます。

つまり「送った後」の数字は正確に分かります。問題は「送る前」です。

設計段階では、この文書を丸ごと読ませたら上限に収まるのか、このシステムプロンプトは何トークン食うのか、を知りたくなります。ここでよく使われるのが「英語なら1トークンおよそ4文字」といった換算の目安です。ただ、この目安は言語でもモデルでも揺れます。日本語・コード・JSONが混ざる実務の入力では、換算で出した数字はあくまで桁の確認程度にしかなりません。

揺れる目安で設計する必要はありません。各プロバイダは、送信前にトークン数を正確に数える手段を公式に用意しています。

## 数える手段はプロバイダごとに別物

まず押さえておきたいのは、**トークナイザ（文章をトークンに分割する仕組み）はモデル固有**だということです。同じ文章でも、ClaudeとGPTとGeminiではトークン数が違います。数える手段も、プロバイダごとに別々に用意されています。

**Anthropic（Claude）**は、Token Counting APIを提供しています。`POST /v1/messages/count_tokens`へ、実際のリクエストと同じ形で`messages`・`system`・`tools`を渡すと、そのリクエストの入力トークン数が返ります。

<LinkCard url="https://platform.claude.com/docs/en/build-with-claude/token-counting" title="Anthropic公式ドキュメント: Token counting" />

SDKからは1メソッドです。TypeScriptならこうなります。

```typescript
const count = await client.messages.countTokens({
  model: "claude-opus-5-5",
  system: systemPrompt,
  messages: [{ role: "user", content: documentText }],
});
console.log(count.input_tokens);
```

このAPIはステートレスで、数えるだけです。推論は走らないので、生成の課金は発生しません。公式ドキュメント上、返る値は推定値（estimate）という扱いで、請求時の実測とはわずかにずれることがあります。設計判断に使う分には十分な精度です。注意点は1つ、**カウントはモデル指定ごとに行う**こと。トークナイザはモデルに紐づくため、推論に使う予定のモデルIDをそのまま渡します。別のモデルで数えた値を流用すると、その時点で別の単位系の数字になります。

**OpenAI（GPT系）**は、APIではなく[tiktoken](https://github.com/openai/tiktoken)というトークナイザライブラリを公開しています。ローカルで動くので、ネットワークを介さずに数えられます。

**Google（Gemini）**は、[`countTokens`というAPIメソッド](https://ai.google.dev/gemini-api/docs/tokens)を提供しています。形はAnthropicと同じ「送る前に同じ内容を投げて数字をもらう」型です。

ここで実務上の落とし穴を1つ。tiktokenはOpenAIモデル用のトークナイザなので、**tiktokenでClaudeやGeminiの入力を数えてはいけません**。ローカルで手軽に動くぶん流用したくなりますが、出てくるのは「GPTに送った場合のトークン数」であって、実際に送る先のモデルの数字ではありません。多言語やコードではずれ幅も読めません。逆方向も同じです。

もう1つ、同じプロバイダ内でも油断できません。モデルの世代が変わるとトークナイザが変わることがあります。モデルを移行するときは、過去の計測値を引き継がず、新しいモデルIDで数え直すのが安全です。

## 数えた値に単価を掛けても、請求額にはならない

ここからが本題です。事前カウントの数字に単価を掛けて「このリクエストは◯円」と見積もりたくなりますが、この計算は**1ターン目の入力の項しか埋められません**。理由は3つあります。

**1つ目、出力は生成が終わるまで分からない**。しかも出力は高い。現行のClaudeモデルの価格表では、出力単価は入力の5倍です（例: Claude Opus 5.5は100万トークンあたり入力$4・出力$20、Claude Sonnet 5.5は$2・$10。2026年11月時点）。

<LinkCard url="https://platform.claude.com/docs/en/about-claude/pricing" title="Anthropic公式ドキュメント: Pricing" />

単価の重い側が事前に数えられない以上、事前カウント×単価は請求の主要な項を欠いた式になります。

**2つ目、エージェントではターン数が事前に決まらない**。1つの依頼が1リクエストで終わる構成なら話は単純ですが、ツールを呼ぶエージェントでは、モデルがツールを呼び、結果が次のターンの入力に積まれ、また呼ぶ、を繰り返します。何ターンで終わるかは実行してみるまで決まらず、入力は後半のターンほど膨らみます。最初の1回を数えても、合計は見えません。

**3つ目、キャッシュで実効単価が変わる**。プロンプトキャッシュが効くと、同じ入力トークンでも読み出し分は大幅に割り引かれ、キャッシュへの書き込みには割り増しが付きます。「トークン数×定価」の単純な積は、キャッシュが効く運用ほど実態から外れていきます。この仕組みは以前の記事で整理しました。

<LinkCard slug="what-is-prompt-caching" />

まとめると、こうなります。コストの見積もりは、事前カウントではなく**実測の仕事**です。レスポンスの`usage`（`input_tokens`・`output_tokens`・キャッシュの読み書きトークン）をログに残し、「このタスク1件あたり実測でいくら」という分布から見積もりを作ります。では事前カウントは何のためにあるのか。持ち場は2つあります。

## 持ち場1: 「送れるか」をエラーの前に判定する

1つ目の持ち場は、入力の検証です。

モデルのコンテキストウィンドウには上限があります。上限はモデルごとに違い、[公式のモデル一覧ドキュメント](https://platform.claude.com/docs/en/about-claude/models/overview)に載っています。プログラムから確認するなら、AnthropicのModels API（`GET /v1/models`）が返す`max_input_tokens`でも取得できます。長文のドキュメント処理やログの要約では、入力がこの上限を超えるかどうかが分岐点になります。

事前カウントがないと、この分岐は「送ってみてエラーで知る」になります。事前カウントがあると、ただの条件分岐になります。

```typescript
const count = await client.messages.countTokens({ model, system, messages });
if (count.input_tokens > LIMIT) {
  // 送る前に分割・要約・絞り込みへ回す
}
```

エラーハンドリングと事前検証の違いは、失敗のコストです。上限超過のエラーは、リクエストを組み立てて送った後に返ってきます。リトライ設計にも影響しますし、バッチ処理の途中で起きると切り分けに時間を食います。送る前に数えれば、超える入力は最初から分割処理の経路へ流せます。チャンク分割のサイズ設計も、文字数ではなくトークン数の実測で決められます。

## 持ち場2: プロンプト固定費の回帰を検知する

2つ目の持ち場は、繰り返し送る部分の定点観測です。

システムプロンプト、ツール定義、エージェントへの指示ファイル。これらは毎リクエストの入力に乗る固定費です。入力コストの観点でこの固定費がどう膨らむかは、Claude Codeを題材に以前整理しました。

<LinkCard slug="claude-code-context-cost" />

この固定費は、機能追加のたびに静かに増えます。ツールを1本足す、指示を3行足す。1回ごとの差分は小さいので、レビューでは気づきません。行数は見えてもトークン数は見えないからです。

事前カウントを使うと、ここが数えられるようになります。プロンプトやツール定義がファイルとしてバージョン管理されていれば、変更前後のファイルをそれぞれ`count_tokens`に通して引き算するだけです。

```typescript
const before = await countFile(client, "prompts/system.v1.md");
const after = await countFile(client, "prompts/system.v2.md");
console.log(`固定費の差分: ${after - before} トークン/リクエスト`);
```

この数字は「1リクエストあたり何トークン増えるか」なので、1日の実行回数を掛ければ日次の増分になります。CIに組み込めば、プロンプト変更のプルリクエストに「この変更は固定費を+800トークン/リクエスト増やします」という情報を添えられます。レビューの判断材料が行数からトークンに変わる、ここが事前カウントの一番おいしい使い方だと考えています。

キャッシュを使っている場合は、もう1つ意味が増えます。固定費部分の変更はキャッシュの無効化を意味するので、「どのファイルを変えるとキャッシュが切れるか」をトークン数と一緒に意識できるようになります。

## 送る前に数え、送った後に測る

整理します。トークンの計測には2つのタイミングがあり、役割が違います。

**送る前（事前カウント）**は検証に使います。上限に収まるかの判定、分割サイズの設計、プロンプト固定費の回帰検知。ここに単価を掛けて見積もりを作らない。確定していない出力とターン数の項が抜けているからです。

**送った後（`usage`の実測）**は見積もりと監視に使います。入力・出力・キャッシュ読み書きの実測をログへ流し、タスク1件あたりのコスト分布を作る。予算やアラートの閾値はこの分布から決めます。

コスト最適化の文脈では、読ませる量を減らす、モデルを使い分ける、支出に上限を置く、という手が既にあります。事前カウントはそのどれでもなく、全部の前段です。量を減らすにも、減ったことを数えられなければ確認できません。上限を決めるにも、正常値の分布が測れていなければ値を置けません。

「数える手段を言語とモデルに合わせて正しく選ぶ」「事前カウントは検証、実測は見積もり、と役割を分ける」。地味ですが、この2つを押さえておくと、トークンまわりの設計判断から当て推量が消えます。目安の換算で設計していた部分があれば、まず数えるところから始めてみてください。
