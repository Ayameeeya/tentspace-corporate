結論から書きます。MCP（Model Context Protocol）にはプロトコルバージョンという互換性の軸があり、クライアントとサーバーは接続のたびに「どの版で話すか」を合意しています。そしてこの合意の既定値は、サーバー作者が何もしなくてもクライアント側の都合で変わります。実際に2026年10月、Claude Codeのクラウドセッションで既定の版が`2026-07-28`へ上がり、その2日後に「特定の条件を満たすサーバーでツールが1本も出ない」不具合の修正が入りました。自作MCPサーバーを運用しているなら、「自分はデプロイしていないから壊れていないはず」という前提を外すのが今回の持ち帰りです。

対象読者は、自作MCPサーバーを運用している人と、MCP対応ツールをチームや自動化に組み込んでいる人。MCPそのものが初見の場合は、先に概要を押さえたほうが読みやすいと思います。

## プロトコルバージョンとは——接続のたびに「どの版で話すか」を合意する

MCPのプロトコルバージョンは、`2026-07-28`のような日付形式の文字列です。セマンティックバージョニング（1.2.3のような形式）ではなく、仕様の改訂日がそのまま版の名前になります。

合意のタイミングは接続の初期化時です。クライアントは`initialize`リクエストで自分が使いたいプロトコルバージョンを送り、サーバーは自分が対応している版を応答します。両者が同じ版で合意できればその版で会話が始まり、クライアントがサーバーの返した版に対応していなければ接続は成立しません。

<LinkCard url="https://modelcontextprotocol.io/specification/2026-07-28" title="Model Context Protocol 仕様（2026-07-28）" />

ここで押さえておきたいのは、この仕組みが「段階的に壊れる」ためのものではなく「最初に決める」ためのものだという点です。HTTPのように古いクライアントと新しいサーバーがなんとなく通じ合う世界ではなく、初期化時の合意がすべての前提になります。だからこそ、合意した版と実際の応答内容がずれたときの壊れ方は派手になります。これは後半の実例でそのまま出てきます。

## 2.1.299で、クラウドセッションの既定が2026-07-28へ上がった

2026-10-14のClaude Code 2.1.299で、クラウドセッションとRemote ControlのMCPコネクタが、プロトコルバージョン`2026-07-28`を既定でネゴシエートするようになりました。環境変数`MCP_PROTOCOL_NEGOTIATION=legacy`で従来の挙動へ戻せます。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code 公式changelog" />

同じリリースには、MCPまわりの変更がほかにも入っています。changelogから拾うと次のとおりです。

- claude.aiのコネクタプロキシと、クラウドセッションのMCPプロキシが、HTTPリダイレクトを追従しなくなった（コネクタ自身のサーバーによるリダイレクトは対象外）
- api.anthropic.comの一次MCPサーバーでは、ツール説明とinstructionsが4,096字で切られず全文届くようになった

この変更の何が重要か。サーバー作者の視点で言い直すと、**自分のサーバーに1行も変更を入れていないのに、ある日からクライアントが新しい版で話しかけてくる**ということです。版のネゴシエーションは接続のたびに行われるので、クライアント側の既定値が変われば、次の接続からサーバーが受け取る`initialize`の中身が変わります。デプロイ履歴をいくら眺めても、この変化は見つかりません。

## 2日後の修正——「版だけ対応」したサーバーでツールが全滅していた

ここからが本題です。既定の版上げから2日後、2026-10-16のClaude Code 2.1.302に、次のbug fixが入りました。

> MCPサーバーがプロトコル版2026-07-28をネゴシエートしながら、resultType・ttlMs・cacheScopeを省いたときに、ツールが表示されない、またはすべてのツール呼び出しが失敗する

出典は同じく[Claude Code公式changelog](https://code.claude.com/docs/en/changelog)です。changelogにはフィールド名までしか書かれていないため、3つのフィールドそれぞれの意味には立ち入りません。それでも、この1行から互換性の壊れ方について読み取れることが2つあります。

1つ目は、壊れ方が全滅型だったこと。「新しい版の新機能が使えない」という部分的な劣化ではなく、「ツールが1本も出ない」「すべての呼び出しが失敗する」という結果になっています。初期化時の版の合意は通っているのに、そのあとの応答の解釈で落ちる。版のネゴシエーションが「最初に決める」仕組みである以上、合意後のずれは途中で吸収されず、こういう形で現れます。

2つ目は、壊れたのも直ったのもサーバー側ではないこと。10-14にクライアントの既定が変わって問題が顕在化し、10-16にクライアント側の修正で解消しています。この間、該当するサーバーの作者は何もしていません。何もしていないのに壊れ、何もしていないのに直った。これが、MCPサーバー運用における互換性問題の典型的な時間の流れです。

接続トラブルの切り分け手順は以前整理しましたが、そのときの3段チェック（設定→接続方式→権限）に、今回の実例は「クライアントの版」という4つ目の軸を足してきたことになります。

## 2026-07-28の仕様で何が変わるのか

では、クライアントが既定で話し始めた`2026-07-28`という版には何が入っているのか。全部は追いませんが、方向を示す変更として、サーバー発信の通知（購読）の正式化があります。

仕様の`2026-07-28`では、クライアントがサーバーからの通知を購読する仕組みが`subscriptions/listen`として正式化され、従来の`resources/subscribe`とHTTP GETエンドポイントを置き換えています。クライアントが通知のフィルタで受け取りたい種別を明示し、サーバーは要求されていない種別を送ってはならない、という形です（[仕様のsubscriptionsのページ](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions.md)）。

エコシステム側はすでに動いています。Cloudflareは2026-10-13から、自社のAPI MCPサーバーでWorkersのエラー監視イベントを署名付きで配信し始めました（[Cloudflare公式changelog](https://developers.cloudflare.com/changelog/post/2026-10-13-cloudflare-mcp-events/)）。こちらは`events/list`・`events/subscribe`という独自拡張で、仕様のフィルタ集合とは一致していません。ベンダー拡張が仕様に先行して走っている状態で、この領域の版差はしばらく動き続けると見ておいたほうがよさそうです。

つまり`2026-07-28`は、ツールを呼ぶだけの世界から、サーバーが自発的に話しかけてくる世界への入り口にあたる版です。クライアント側がここへ既定を寄せてきたのは自然な流れで、今後も既定の版上げは繰り返されると考えて運用を組むのが現実的です。

## 自作サーバー側の点検——「自分は変えていない」を前提にしない

ここまでを踏まえて、自作MCPサーバーの運用に足しておきたい点検を4つにまとめます。並び順は、問題が起きたときに効く順です。

**1. どの版で合意したかをログに残す。** `initialize`でクライアントが送ってきた版と、自分が応答した版を記録します。今回のような問題が起きたとき、最初に知りたいのは「いつからクライアントの版が変わったか」です。これはサーバー側のログにしか残りません。デプロイ履歴には出てこない変化を観測できるのは、この1行だけです。

**2. 新しい版を受けるなら、応答の要件まで揃えてから受ける。** 今回の不具合の条件は「2026-07-28をネゴシエートしながら、必要なフィールドを省いた」でした。版の合意だけ新しくして中身が旧版のまま、という中途半端な対応が全滅を生んでいます。対応しきれていない版は受けずに、自分が完全に対応している版で合意するほうが安全です。ネゴシエーションで古い版に落ち着くのは劣化ではなく、互換性の仕組みが正しく働いている状態です。

**3. クライアント側のchangelogを監視対象に入れる。** サーバーの互換性を壊す変更は、サーバーのリポジトリの外からやってきます。Claude Codeのように更新頻度の高いクライアントと接続するなら、クライアントのchangelogはもう自分の運用の一部です。MCP関連の行だけ拾うのでも十分効きます。

**4. `MCP_PROTOCOL_NEGOTIATION=legacy`は一時しのぎと割り切る。** このフラグはクライアント側の設定であって、サーバーの修理ではありません。利用者全員に設定してもらうことは現実的でなく、既定が進む方向は変わらないので、退避している間にサーバー側の対応を進める、という使い方になります。

## まとめ——互換性はデプロイの外で動く

今回の流れを時系列で並べ直すと、こうなります。

- 10-14（2.1.299）: クラウドセッションの既定の版が`2026-07-28`へ。サーバー作者は何もしていない
- 10-16（2.1.302）: 版だけ合意して応答フィールドを省いたサーバーで、ツール全滅の不具合が修正される。サーバー作者はやはり何もしていない

MCPのプロトコルバージョンは、初期化時に一度だけ合意する設計です。だから壊れるときは部分劣化ではなく全滅に近い形で出ますし、壊すのも直すのも接続相手側であることが普通にあります。「自分のデプロイ以外で壊れない」という感覚は、MCPサーバーの運用では成り立ちません。

やることはシンプルです。合意した版をログに残す、対応しきれていない版は受けない、クライアントのchangelogを監視に入れる。この3つを回しておけば、次に既定の版が上がった日も、原因の特定までは最短で辿り着けるはずです。
