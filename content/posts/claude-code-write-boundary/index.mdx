Claude Code 2.1.314（2026-10-30）で、作業ディレクトリ外への書き込みを拒否する設定 `permissions.blockWritesOutsideWorkingDirectories` が入りました。結論から言うと、これは「どの権限モードで動かすか」に依存していた書き込み境界を、**設定ファイルで恒常的に宣言できる形**へ移すものです。bypassPermissionsでも効きます。ただし変更履歴が約束しているのはWrite・Edit・NotebookEditの3ツール経由だけで、シェル経由の書き込みは記載の範囲外。入れる価値は十分ありますが、これ1つで「書き込み境界は閉じた」と数えないのが私の読みです。

想定読者は、Claude Codeを定時実行やCIで無人運用している方と、エージェントに書き込みをどこまで許すかを設計する立場の方です。何が変わったか、実測で何が確認されているか、実務でどう扱うかの順に整理します。

## 何が変わったか: 拒否の根拠が「モード」から「設定」になった

[公式の変更履歴](https://code.claude.com/docs/en/changelog)によると、2.1.314のAddedに入ったのは次の内容です。`permissions.blockWritesOutsideWorkingDirectories` を有効にすると、Write・Edit・NotebookEditの各ツールは、**すべての権限モードで**作業ディレクトリ外のパスへの書き込みを拒否します。

「すべての権限モードで」が肝です。Claude Codeの権限モードには、確認を求める通常の動作から、確認を省略するbypassPermissionsまで幅があります。これまで「作業ディレクトリの外に書かせない」を担保したければ、確認が生きているモードを選ぶか、権限ルールやhooksを自分で書くか、でした。つまり境界の実体は「モードの選び方」と「自分のルールの書き方」に分散していた。この設定は、その境界を1行の宣言に寄せます。確認を省略する運用のまま、書き込み範囲だけを固定できる形です。

ちなみに同じリリースには、Claudeのファイルツールがサーバー管理設定のローカルコピーを編集する前に確認を取る変更や、16件の改善・81件のバグ修正も含まれています。書き込み境界まわりの手当てがまとまって入ったリリースと読めます。

## 実測で確認済みの範囲と、まだ白紙の範囲

公開翌日に検証記事が出ています。クラスメソッドの記事が、bypassPermissionsモードで実測し、設定が有効なら作業ディレクトリ外へのWriteがブロックされ、無効なら成功することを確認しています。

<LinkCard url="https://dev.classmethod.jp/articles/20261030-cc-updates-v2-1-314/" title="クラスメソッド: Claude Code 2.1.314 アップデート検証" />

この記事が誠実なのは、検証していない範囲を明記している点です。実測はWrite×bypassPermissionsの1ケースで、**Edit・NotebookEdit・シェル経由の書き込みは未検証**とされています。変更履歴の記載も3ツールのパス指定が対象なので、たとえばBashのリダイレクトで作業ディレクトリ外へ書く経路がどうなるかは、一次情報・実測のどちらにもまだ答えがありません。

境界の「内側」の定義も押さえておきます。ここで言う作業ディレクトリは、起動ディレクトリに加えて `--add-dir` や `/add-dir`、`permissions.additionalDirectories` で追加した分を含みます。一方、対になる読み取り側の設定 `permissions.blockReadsOutsideWorkingDirectories` では、`.claude/settings.json` のようなリポジトリ設定だけで追加したディレクトリは作業ディレクトリに数えない、という非対称があると同記事は報告しています。**同じ「追加ディレクトリ」でも、どの設定ファイルに書いたかで境界の内外が変わりうる**。ここは自分の構成で確かめるべきポイントです。

## 同じリリースの修正2件が、点検の必要性を教えてくれる

新設定そのものより考えさせられたのが、同じ2.1.314で直された2つのバグです。

1つ目は、`claude -p --resume` や `--continue` で再開してworktreeに入ったセッションに、サンドボックス保護が適用されていなかったという修正。2つ目は、Monitorツールが起動したシェルコマンドに、Bashマッチのフックが走っていなかったという修正です（修正後もフックができるのはblockとaskまでで、approveや入力の書き換えはできません）。

どちらも構図は同じです。**守りの仕組みは入れてあった。でも、特定の経路ではそれが発火していなかった**。通常の起動では守られ、再開経由では守られない。通常のBashでは検査され、別ツール経由のシェルでは検査されない。そして、守られていない間も処理は成功し続けるので、運用上は何も起きていないように見えます。

私は毎日、Claude CodeのRoutineを無人で回していて、hooksと権限ルールを検査系として使っています。この2件が刺さったのは、まさに「経路を変えると検査が発火しない」が自分のリスクそのものだからです。設定を足すことと、その設定がすべての経路で発火していることは、別の事実です。新しいツールや再開、worktreeのような**経路が増えるたびに、検査が本当に発火したかを数える側の仕組みが要る**。これは未検証の推測ではなく、今回2件の修正が存在したこと自体が根拠になります。

## 実務での扱い: 入れる価値と、閉じたと数えない理由

では、この設定をどう扱うか。私の整理は次のとおりです。

**入れる価値はあります。** 無人運用では、権限の確認を人間が返せないので、境界は事前の宣言だけが頼りです。これまで権限設計を「渡さない・許す・止める・外側で強制」の4層で組んできましたが、この設定は「止める」層に、モードの選び方に依存しない恒常的な1枚を足してくれます。denyルールの書き方ひとつで穴が開く世界なので、宣言が単純であることは、それ自体が価値です。

<LinkCard slug="claude-code-permission-layers" />

**ただし、これ1つで書き込み境界が閉じたとは数えません。** 理由は前述のとおり、変更履歴が約束しているのが3ツールのパス指定だけで、シェル経由の書き込みが同様に止まるかは記載も実測もまだ無いからです。ツール経由とシェル経由の二経路が残るなら、設定1つでは境界は閉じない、というのが私の未検証の推測です。シェル側の書き込みを含めてOSレベルで止めるのは、引き続きサンドボックスの仕事と考えています。

<LinkCard slug="claude-code-sandbox-settings" />

導入自体は小さい変更です。`settings.json` の permissions に `blockWritesOutsideWorkingDirectories: true` を足す。期待する結果は、作業ディレクトリ外へのWrite・Edit・NotebookEditが全モードで拒否されること。合わせて `additionalDirectories` に何を足しているか、それをどの設定ファイルに書いているかを棚卸ししておくと、読み取り側の非対称にも備えられます。戻すときは設定を `false` にするか行を消すだけで、ロールバックに他の作業は要りません。

私自身の採否は「入れる方向、ただし実測してから」です。Write・Edit・シェル経由のそれぞれで、ブロック時に何が返るかを自分の構成で確かめてから、本番のRoutineへ反映します。確認を省略するモードを使っていなくても、この設定は「モードを将来変えても境界が残る」保険として機能するはずです。

## 境界は宣言して終わりではなく、発火を数えて維持する

まとめます。

- 2.1.314の `permissions.blockWritesOutsideWorkingDirectories` は、Write・Edit・NotebookEditの作業ディレクトリ外書き込みを**全権限モードで拒否**する。境界の根拠をモードから設定へ移せる
- 実測で確認されているのは**Write×bypassPermissionsの1ケース**。Edit・NotebookEdit・シェル経由は未検証で、シェル経由は変更履歴の記載範囲外
- 追加ディレクトリは**どの設定ファイルに書いたか**で扱いが変わりうる。読み取り側の設定には非対称の報告がある
- 同じリリースで直ったworktree再開・Monitor経由の**適用漏れ2件**が示すとおり、設定を足すことと全経路で発火することは別。経路が増えたら発火を確かめる

書き込み境界の設計は、宣言した日に完成するものではなく、経路が増えるたびに点検して維持するものです。1行で宣言できるようになった分、浮いた手間はその点検に回すのがよいと思います。
