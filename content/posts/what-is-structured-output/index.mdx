結論から言うと、構造化出力（Structured Outputs）とは、**LLMの応答を、事前に渡したJSONスキーマへ必ず一致する形で返させるAPI機能**です。「JSONで返してください」とプロンプトでお願いする話ではありません。モデルが次のトークンを選ぶ段階で、スキーマに違反する選択肢そのものを候補から外す。だから出力は構文レベルで壊れようがない、という仕組みです。

そしてもう1つ、先に言い切っておきます。**スキーマが保証するのは「形」だけで、中身が正しいことは保証しません。** ここを取り違えると、パースエラーという分かりやすい失敗が消える代わりに、「型は合っているが値は創作」という見えにくい失敗に置き換わります。

この記事では、プロンプト指示・JSONモード・構造化出力の3段階の違い、制約付きデコーディングの原理、OpenAI・Claude・Geminiでの使い方、そして形が保証された後に残る設計の仕事までを整理します。想定読者は、LLMの出力をプログラムで受け取る処理——エージェント、データ抽出、パイプライン——を作っていて、「出力が時々壊れる」問題を根本から片付けたい方です。

## 「JSONで返して」には3段階ある

LLMからJSONを受け取る方法は、保証の強さで3段階に分かれます。まずここを区別しないと、ツール選定の会話が噛み合いません。

1. **プロンプト指示**: 「次のスキーマのJSONだけを返してください」と文章で頼む。保証はゼロ
2. **JSONモード**: APIパラメータで「出力はJSON」と宣言する。構文的に正しいJSONは保証されるが、**どんな形のJSONかは保証されない**
3. **構造化出力**: JSONスキーマそのものをAPIに渡す。構文に加えて、**スキーマへの一致まで保証される**

第1段階の「たいてい動くが、たまに壊れる」は経験のある方が多いはずです。Markdownのコードフェンスで包んで返してくる、先頭に「はい、承知しました」が付く、フィールド名が勝手に揺れる。壊れる頻度が数%でも、無人で回る処理では確実に事故になります。

この差をOpenAIは数字で示しています。構造化出力の発表時、複雑なJSONスキーマへの追従を測る社内評価で、プロンプト指示だけの従来モデル（gpt-4-0613）は40%未満、構造化出力を使ったgpt-4o-2024-08-06は100%というスコアでした。

<LinkCard url="https://openai.com/index/introducing-structured-outputs-in-the-api/" title="Introducing Structured Outputs in the API - OpenAI" />

第2段階のJSONモードは中間地点です。`JSON.parse` は通るようになりますが、`{"items": []}` を期待しているのに `{"result": "..."}` が返ることは防げません。現在はOpenAI・Anthropic・Googleの主要3社がいずれも第3段階の構造化出力を提供しているので、プログラムで受ける用途なら最初から第3段階を選ぶのが素直です。

## 仕組みは「賢くした」ではなく「選べなくした」

構造化出力の面白いところは、モデルを賢くして実現したのではない点です。使われているのは**制約付きデコーディング（constrained decoding）**という手法で、働くのはモデルの知性ではなくサンプリングの制約側です。

LLMは1トークンずつ、「次に来る候補の確率分布」から選んで文章を作ります。制約付きデコーディングは、渡されたJSONスキーマを「この位置ではどのトークンが合法か」という文法にあらかじめ変換しておき、**生成の各ステップで、文法に違反するトークンを候補から外（マスク）します**。`{"age":` まで出力した直後なら、数値かnull以外のトークンはそもそも選べない、という具合です。

この原理が分かると、構造化出力の細かい仕様にも説明がつきます。

- **初回リクエストが遅いことがある**: スキーマを文法へ変換する前処理が走るため。変換結果はキャッシュされ、2回目以降は通常の速度になります
- **スキーマに制限がある**: たとえばOpenAIのstrictモードでは、全フィールドを `required` に入れ、`additionalProperties: false` を指定する必要があり、ネストの深さやプロパティ数にも上限があります。JSON Schemaの全機能ではなく「文法に変換できるサブセット」だけが使える、と理解しておくと迷いません

対応しているスキーマ機能の範囲は各社・各モデルで差があり、更新も続いています。設計前に公式ドキュメントで手元のモデルの対応範囲を確認してください。

## 各社APIでの使い方

2026年時点で、主要3社の使い方はこう整理できます。名前は違いますが、「スキーマをリクエストに渡すと、応答がそれに一致する」という構造は共通です。

**OpenAI**は `strict: true` 付きのJSONスキーマをリクエストで渡します。Chat Completions APIでは `response_format`、現行のResponses APIでは `text.format` に指定します。

```json
{
  "type": "json_schema",
  "name": "extract_invoice",
  "strict": true,
  "schema": {
    "type": "object",
    "properties": {
      "invoice_number": { "type": "string" },
      "total": { "type": "number" }
    },
    "required": ["invoice_number", "total"],
    "additionalProperties": false
  }
}
```

**Anthropic（Claude）**は2025年11月に構造化出力をパブリックベータとして追加しました。リクエストの `output_format` にJSONスキーマを渡す形で、ベータヘッダー（執筆時点では `structured-outputs-2025-11-13`）の指定が必要です。同じベータで、ツール定義側の `strict` 指定（strict tool use）も入りました。

<LinkCard url="https://docs.claude.com/en/docs/build-with-claude/structured-outputs" title="Structured outputs - Anthropic公式ドキュメント" />

**Google（Gemini）**は `generationConfig` に `responseMimeType: "application/json"` と `responseSchema` を指定します（[公式ドキュメント](https://ai.google.dev/gemini-api/docs/structured-output)）。

実務では、スキーマをJSONで手書きするより、**PydanticやZodのモデル定義からスキーマを生成するSDKヘルパー**を使うのが主流です。アプリ側の型とAPIに渡すスキーマが同じ定義から生まれるので、「スキーマと受け取り側の型がずれる」事故ごと消せます。

## Function Callingとの関係——「ツールの引数」と「応答そのもの」

構造化出力を調べると、必ずFunction Calling（ツール呼び出し）が隣に出てきます。関係は単純で、**Function Callingのツール引数は、もともと構造化出力でした**。モデルが返す「この関数をこの引数で呼びたい」というJSONは、ツール定義のスキーマに沿って生成されます。strictモードはこのツール引数側にも適用でき、構造化出力が保証を「応答そのもの」へ広げた、と見るのが分かりやすいです。

使い分けの目安は次のとおりです。

- **モデルに何かをさせたい**（検索する、メールを送る、DBを引く）→ Function Calling。実行はアプリ側に残る
- **モデルからデータが欲しい**（抽出、分類、採点の結果をJSONで）→ 構造化出力。ツールという建て付けを経由せず、応答を直接スキーマに固定する

構造化出力が登場する前は、「ダミーのツールを1つ定義して呼び出しを強制する」のがスキーマ付き応答の定番ワークアラウンドでした。いま新規で作るなら、データ取得目的でツールを偽装する必要はありません。

## 形が保証されると、失敗は「見えない側」へ移る

ここからがこの記事でいちばん書きたかった話です。構造化出力を入れると、`JSON.parse` の失敗とリトライのコードが消えます。ところが、**消えたのは失敗ではなく、失敗の見えやすさ**です。

スキーマは、モデルに「分かりません」を言わせない方向に働きます。具体的にはこうなります。

- **requiredなフィールドは、根拠がなくても何かで埋まる**: 請求書画像に合計金額が写っていなくても、`total` が `required` なら数値が入ります。空欄という逃げ道を、スキーマ自身が塞いでいるからです
- **enumは最も近い選択肢へ吸着する**: カテゴリ分類で該当なしの入力が来たとき、「その他」の無いenumは、いちばんそれらしい誤答を必ず返します
- **スキーマ外の応答経路が残る**: たとえばOpenAIでは、安全上の理由で応答を拒否した場合、スキーマ準拠の出力ではなく `refusal` として返ります。「必ずスキーマ通り」を素朴に前提にすると、この経路でちゃんと壊れます

つまり、検証の仕事は消えずに**移動**します。構文検証（パースできるか）は不要になり、意味検証（値が業務的に妥当か）が残る。むしろ「パースが通ったから大丈夫」という誤った安心が生まれるぶん、意味検証を意識的に置かないと、以前より静かに間違えるシステムになります。

私もSNS運用をエージェントの無人実行で回していて、出力の受け口は「決定的なチェックで落とす層」と「LLMに判断させる層」の2層にしています。構造化出力はこの1層目を強くする部品であって、2層目を不要にする部品ではない、というのが運用しての整理です。

## スキーマ設計のコツ5つ

形の保証を活かしつつ、見えない失敗を減らすためのスキーマ設計の勘所です。

1. **「不明」を表現できる型にする**: 値が取れない可能性のあるフィールドは `["number", "null"]` のようにnullを許す、enumには `"unknown"` や `"other"` を足す。モデルに正直でいられる逃げ道をスキーマ側が用意します
2. **指示はdescriptionに書く**: フィールドの意味や判断基準はスキーマ各フィールドの `description` に書きます。プロンプト本文とスキーマで指示が分裂すると、片方だけ直して食い違う事故が起きます
3. **深いネストを避ける**: スキーマの表現力には上限があり、深く複雑なスキーマは精度面でも不利です。1段か2段の平坦な構造に分解できないか先に考えます
4. **判断の痕跡をフィールドにする**: `confidence`（確信度）や `evidence`（根拠の引用）を足しておくと、2層目の意味検証やログでの追跡がしやすくなります。結論フィールドより前に置くと、生成順の都合で根拠→結論の順に考えさせられます
5. **最初からstrictで作る**: 「まずJSONモードで雑に、あとでstrictに」は、スキーマ制約（全フィールドrequired化など）への手戻りが出ます。新規ならstrict前提で設計する方が結局速いです

## 構造化出力を使わない方がいい場面

最後に、向かない場面も挙げておきます。

- **出力が人間向けの文章そのもの**: 要約や回答文を `{"text": "..."}` で包んでも得るものはほぼなく、文章生成に不要な制約を1枚足すだけになりがちです
- **考える過程が品質に効くタスク**: 複雑な判断をいきなりスキーマへ直行させると精度が落ちることがあります。先に自由に考えさせてから整形する2段構成にするか、スキーマの先頭に思考用のフィールドを置いて対処します
- **スキーマで表現できない制約が本体の場合**: 「配列の合計が100になる」「日付Aは日付Bより前」のような制約はJSONスキーマの守備範囲外です。これは結局、受け取った後の意味検証で見ることになります

## まとめ

- 構造化出力とは、LLMの応答を事前に渡したJSONスキーマへ必ず一致させるAPI機能。プロンプトの工夫ではなく、制約付きデコーディングによる生成段階の保証
- 「プロンプト指示→JSONモード→構造化出力」の3段階で保証が強くなる。プログラムで受けるなら最初から構造化出力
- OpenAIは `strict: true` のJSONスキーマ、Claudeは `output_format`（2025年11月からベータ）、Geminiは `responseSchema`。構造は3社共通
- スキーマが保証するのは形だけ。requiredによる創作、enumへの吸着、拒否応答の別経路など、失敗は見えない側へ移る
- 検証は消えずに移動する。構文検証は不要になり、意味検証を設計する仕事が残る

スキーマの対応範囲やパラメータの正式仕様は、いまも更新が続いています。実装前に、一次情報で手元のモデルの最新仕様を確認してください。
