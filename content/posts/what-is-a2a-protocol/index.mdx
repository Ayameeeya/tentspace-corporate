A2A（Agent2Agent）プロトコルとは、AIエージェント同士が互いにやり取りするためのオープンな共通規格です。2025年4月にGoogleが発表し、同年6月にはLinux Foundationへ移管されました。MCPが「エージェントとツールをつなぐ規格」なら、A2Aは「エージェントとエージェントをつなぐ規格」。公式ドキュメントも、この2つを競合ではなく補完関係として説明しています。

この記事では、A2Aが解決しようとしている問題、Agent Card・Task・Artifactという中身の仕組み、MCPとの住み分け、そして実務で「いつ要るのか」の判断軸を、[公式仕様](https://a2a-protocol.org/)ベースで整理します。結論を先に言うと、1つのシステムの中でエージェントを分業させるだけならA2Aはまだ要りません。要るのは、エージェントが組織やベンダーの壁をまたぐときです。

## A2Aが解決する問題は「会社の壁」

1つのフレームワークの中でエージェントを連携させること自体は、すでに珍しくありません。Claude Codeのサブエージェントのように、親エージェントが子エージェントへ作業を振る仕組みは各社の開発ツールに標準装備されつつあります。

問題は、別のベンダー・別のフレームワーク・別の組織で作られたエージェント同士です。たとえば自社の調達エージェントが、取引先の在庫管理エージェントに問い合わせたいとします。相手の内部実装はこちらから見えませんし、見せてもらえるものでもありません。接続方法が規格化されていなければ、相手ごとに専用の接続コードを書くことになります。MCPが解決した「N×M問題」の再演が、今度はエージェント同士の間で起きるわけです。

A2Aはここに共通の口を用意します。設計上の特徴は、お互いの中身を見せ合わないまま協働できることです。A2Aで対話するエージェントは、内部のメモリ・ツール・思考過程を相手に公開しません。公開するのは「何ができるか」と「タスクの進捗・成果物」だけ。[発表時のGoogleのブログ](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/)は、50社以上のパートナーとともにこの構想を示しました。その後の[Linux Foundationへの移管](https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/)には、Amazon Web Services・Cisco・Microsoft・Salesforce・SAP・ServiceNowなども参画しています。特定ベンダーの持ち物ではなく中立の標準として育てる、という位置づけです。

## 仕組みの中心は Agent Card・Task・Artifact

A2Aの登場人物はシンプルで、依頼する側のクライアントエージェントと、依頼を受けるリモートエージェントの2者です。やり取りは次の部品で構成されます。

### Agent Card：エージェントの名刺

リモートエージェントは、自分の情報をJSONで公開します。これがAgent Cardです。名前と説明、提供できるスキルの一覧、接続先エンドポイント、要求する認証方式などが書かれていて、仕様では `/.well-known/` 配下の既知のパスに置く方法が示されています。クライアントはまずこのカードを読み、「このエージェントに何を頼めるか」「どう認証するか」を知ってから接続します。Webで言うところのサービスディスカバリを、エージェント向けに規格化したものです。

### Task：状態を持つ仕事の単位

A2Aのやり取りはTask（タスク）を中心に回ります。タスクには `submitted`（受付）、`working`（作業中）、`input-required`（追加入力待ち）、`completed`（完了）、`failed`（失敗）、`canceled`（中止）といったライフサイクル状態が定義されています。

ここがツール呼び出しとの大きな違いです。関数呼び出しは基本的に「呼んだら即結果が返る」モデルですが、エージェントへの依頼は数分・数時間かかることも、途中で「この条件で進めていいですか」と聞き返されることもあります。A2Aは最初から長時間・多往復の仕事を前提に、状態遷移として設計されています。

### Message・Part・Artifact：会話と成果物

タスクの中のやり取りはMessageで運ばれ、Messageは複数のPartでできています。Partにはテキスト・ファイル・構造化データの種類があり、テキスト専用ではありません。そしてタスクの成果物はArtifactとして返されます。これもPartの集まりなので、レポートの文章と添付ファイルとJSONデータを1つの成果物にまとめて返す、といった表現ができます。

## 通信の中身は意外なほど「普通のWeb」

エージェント間通信と聞くと、何か新しい通信技術が出てくるように思えますが、仕様を読むと逆です。中身は徹底して既存のWeb標準でできています。リクエストはHTTP(S)上のJSON-RPC 2.0、進捗のストリーミングはServer-Sent Events（SSE）、長時間タスクの完了通知はWebhookによるプッシュ通知、認証はOAuth 2.0やAPIキーといった標準的なHTTP認証をAgent Cardで宣言する方式です。

つまりA2Aの新しさは通信技術ではなく、「エージェントの能力の記述（Agent Card）」と「仕事の状態遷移（Task）」という語彙を共通化した点にあります。既存のWebインフラ（ロードバランサー、認証基盤、監視）がそのまま使えるのは、本番運用を考えると地味に効きます。新しい通信層を運用に乗せる作業が丸ごと不要だからです。

## MCPとの違い：つなぐ相手が違う

A2Aを調べる人の多くが最初に迷うのが、MCPとの関係だと思います。整理すると役割は明確に分かれています。

| | MCP | A2A |
|---|---|---|
| つなぐ相手 | エージェント ↔ ツール・データ | エージェント ↔ エージェント |
| 相手の性質 | 構造化された入出力を即座に返す | 自律的に判断し、時間をかけて進める |
| やり取りの形 | ツール呼び出し（関数的） | タスクの依頼と進捗・成果物（会話的） |
| 内部の見え方 | ツールの入出力スキーマを公開 | 内部実装は見せない（スキルと進捗だけ公開） |

公式ドキュメントはこの2つを補完関係として説明しています。1体のエージェントが、手元の道具（DB、検索、社内API）にはMCPでつなぎ、他のエージェントへの依頼はA2Aで出す、という絵です。

迷ったときの目安はこうです。相手が「決まったインターフェースで即応するもの」ならMCPのツールとしてつなぐ。相手が「進捗を返しながら自律的に進むもの」ならA2Aのエージェントとして扱う。MCP自体の仕組みは別記事で整理しているので、規格の層の違いを確認したい方はそちらをどうぞ。

## 「まだ早い」と「もう要る」の境目

ここまで仕組みを見てきて、では今すぐ使うべきかというと、私の答えは「構成によります」です。

自分のシステムの中だけでエージェントを分業させるなら、A2Aは要りません。同じプロセス・同じリポジトリの中のエージェント連携は、フレームワークのサブエージェント機構で完結します。実際、私が運用している自動化システムも、オーケストレーター1体に公開前レビュー専任のサブエージェントを分離した構成で、エージェント「間」のプロトコルは使っていません。境界をまたがないなら、規格のオーバーヘッドはただのコストです。

<LinkCard slug="claude-code-subagent-critic-review" />

A2Aが効き始めるのは、エージェントが信頼境界をまたぐときです。具体的には次の3つが目安になります。

1. **組織の外とやり取りする**。取引先・顧客・外部サービスのエージェントと連携する計画があるか。相手の内部実装に依存できない時点で、共通規格が前提になります。
2. **ベンダーを混ぜる**。社内でも、部門Aのエージェントと部門Bのエージェントが別フレームワークで作られているなら、間をつなぐ共通語が要ります。
3. **長時間タスクの進捗を外へ見せる**。「依頼を受けて数時間後に成果物を返す」型のサービスをエージェントとして提供するなら、Taskのライフサイクルはそのまま設計の土台になります。

逆に言えば、この3つのどれにも当てはまらない段階でA2A対応を要件に入れるのは早すぎます。仕様はまだ若く、バージョンアップで変わる部分も残っています。発注側の立場なら、「A2A対応」を今すぐの必須要件にするより、「エージェントの境界がどこにあるか」を先に設計し、境界をまたぐ計画が具体化した時点で対応を検討する順番をおすすめします。

## まとめ：規格は「境界」から順に効く

A2Aプロトコルの要点を整理します。

- A2Aはエージェント同士をつなぐオープン規格。2025年4月にGoogleが発表し、同年6月からLinux Foundation傘下で開発されています
- 中身はAgent Card（能力の公開）、Task（状態を持つ仕事の単位）、Artifact（成果物）。通信はJSON-RPC・SSE・Webhookという既存のWeb標準です
- MCPとは競合せず、つなぐ相手が違います。ツールにはMCP、エージェントにはA2A
- 1つのシステム内の分業には不要。組織・ベンダー・信頼の境界をまたぐときに検討する規格です

MCPのときもそうでしたが、規格は「全員が使うから価値がある」段階の前に、「境界を持つ人から順に効く」段階があります。自分のエージェントがどの境界をまたぐのかを先に見極めておくと、対応のタイミングを焦らずに判断できます。
