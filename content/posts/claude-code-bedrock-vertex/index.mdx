Claude Codeは、既定のAnthropic API直結のほかに、Amazon BedrockやGoogle Vertex AIを経由して動かせます。切替は環境変数で済み、請求と認証は自社のAWS / Google Cloud契約側へ移ります。結論から言うと、「社員にAPIキーを配りたくない」会社にとって、これが一番素直な導入経路です。ただし、切替そのものは数行でも、検討の本体は別の場所にあります。変わるのはモデルの置き場所ではなく、**認証の寿命と上限を誰が管理するか**。ここを設計しないまま経路だけ切り替えると、無人実行やCIで止まります。

想定読者は、Claude Codeの組織導入を検討している技術責任者・PMと、すでにAWSやGoogle Cloudの統制がある環境で動かしたい実務者です。切替の手順、切り替えると何が変わるか、どの経路を選ぶか、の順で整理します。なお、私自身の常用経路はAnthropic API直結で、Bedrock・Vertex経路での運用は未検証です。本稿は公式ドキュメントの仕様の整理と、導入設計の判断軸に絞ります。

## APIキーを配る構成は、審査と退職のたびに重くなる

個人で使う分には、Anthropic APIキーかPro / Maxサブスクリプションで困りません。組織に広げるときに詰まるのは、だいたい次の3つです。

1つ目は鍵のライフサイクル。発行、保管、ローテーション、そして退職や異動のたびの失効。配った鍵の数だけ管理対象が増えます。シークレット管理基盤に載せるとしても、「この鍵は誰のものか」の台帳は別に要ります。

2つ目は請求の分離。APIキー単位の利用額を部門やプロジェクトに配賦したいとなると、その集計の仕組みを新しく作ることになります。すでにクラウド側でコスト配分のタグ付けや予算アラートを運用している会社ほど、二重管理になるのがもったいない。

3つ目はデータ経路の審査。セキュリティレビューで見られるのは「どのエンドポイントへ何を送るのか」です。新しい外部APIの追加審査には時間がかかる一方、BedrockやVertex AIをすでに審査・承認済みの会社は少なくありません。審査済みの経路に載るなら、導入の稟議は一段軽くなります。

つまり、組織導入で先に詰まるのはモデルの性能ではなく、調達と統制です。そしてClaude Codeは、この問いへの答えを最初から持っています。

## 接続先は環境変数で切り替えられる

Claude Codeの接続先は、既定のAnthropic API（またはPro / Maxサブスクリプション）のほかに、Amazon Bedrock、Google Vertex AI、Microsoft Foundryがサポートされています。さらに、社内のLLMゲートウェイを間に挟む構成も公式に想定されています（[サードパーティ連携のドキュメント](https://code.claude.com/docs/en/third-party-integrations)に一覧があります）。コードや設定ファイルの書き換えではなく、環境変数で経路ごと差し替える方式です。

### Amazon Bedrockに載せる

前提が1つあります。利用するAWSアカウントのBedrockコンソールで、Anthropicモデルへのモデルアクセスを有効化しておくこと。これはClaude Code側ではなくAWS側の操作です。そのうえで、切替は次の2行です。

```bash
export CLAUDE_CODE_USE_BEDROCK=1
export AWS_REGION=us-east-1   # 利用するリージョンを明示する
```

認証には、AWS標準のクレデンシャルチェーンがそのまま使われます。`aws sso login`で取ったセッションでも、環境変数のアクセスキーでも、EC2やECSのインスタンスロールでも動く形です。ここが要点で、**「Claude Code用の鍵」というものが存在しなくなります**。アクセス制御はIAMポリシーの世界に統合され、退職時の失効もIAM側の運用に乗ります。

モデルを明示したい場合は`ANTHROPIC_MODEL`にBedrock側のモデルID（リージョンプレフィックス付きの推論プロファイル形式）を指定します。補助的な軽量タスク用に`ANTHROPIC_SMALL_FAST_MODEL`も別指定できます。利用可能なモデルIDはリージョンで異なるため、値は自分のアカウントのBedrockコンソールで確認するのが確実です。

<LinkCard url="https://code.claude.com/docs/en/amazon-bedrock" title="Claude Code公式ドキュメント: Amazon Bedrock" />

期待する結果は、起動したClaude Codeの推論リクエストがBedrockエンドポイントへ向かい、課金がAWSの請求に載ることです。戻すときは環境変数を外して起動し直すだけで、既定のAnthropic API直結に戻ります。

### Google Vertex AIに載せる

Vertex AIも構図は同じです。プロジェクトでVertex AIのAPIとClaudeモデルの利用を有効化したうえで、次を設定します。

```bash
export CLAUDE_CODE_USE_VERTEX=1
export CLOUD_ML_REGION=us-east5           # Claudeモデルを提供するリージョン
export ANTHROPIC_VERTEX_PROJECT_ID=my-project
```

認証はGoogle CloudのApplication Default Credentialsです。手元なら`gcloud auth application-default login`、サーバー上ならサービスアカウントが使われます。こちらも「配る鍵」はなく、権限はIAMに寄ります。

<LinkCard url="https://code.claude.com/docs/en/google-vertex-ai" title="Claude Code公式ドキュメント: Google Vertex AI" />

ちなみにCIでも同じ考え方が通ります。GitHub Actionsで動かす公式アクションは、APIキーのほかにBedrock・Vertex経由の実行をサポートしています。会社のモデル利用をクラウド経由に寄せた場合、対話利用とCIを同じ経路・同じ統制に揃えられます。

## 変わるのはモデルの置き場所ではなく、トークンの寿命と管理者

手順だけ見ると「環境変数を足して終わり」に見えます。私も最初はそう読みました。ただ、仕様を追っていくと、この切替の本体は推論の行き先ではなく、**認証と上限の管理者が変わること**だと分かってきます。運用側の目で、変わる点を4つ挙げます。

**1. 認証に寿命が生まれる。** Anthropic APIキーは、失効させない限り生き続けます。一方、SSOやADCのセッションには期限があります。人間が対話で使う分には再ログイン一回の話ですが、定時実行やCIのような無人運用では「認証をどう更新し続けるか」が独立した設計項目になります。インスタンスロールやCIのOIDC連携のように、実行環境自体に権限を持たせる形なら解決します。逆に、手元の`aws sso login`のセッションに依存したままcronへ載せると、セッションが切れた日から止まります。私は毎日Claude CodeのRoutineを無人で回している立場なので、経路を選ぶならここを最初に確かめます（前述のとおり、Bedrock経由の無人運用そのものは未検証です）。鍵を配らない構成とは、言い換えれば**期限切れが異常ではなく仕様になる**構成です。止まったことに気づける監視とセットで導入するものだと考えています。

**2. 機能の提供が接続先で分かれることがある。** Claude Code本体の新機能は、接続先ごとに提供時期や条件が異なる場合があります。たとえばauto modeの審査分類器がサーバー側実行へ移った変更では、Bedrock・Vertex・Foundry経由も対象に含まれた一方、間にゲートウェイを挟む構成では特定のリクエストフィールドを素通しさせることが条件として明記されました。経路を変えると、こうした「対象条件の読み合わせ」が更新のたびに必要になります。

<LinkCard slug="claude-code-auto-mode" />

**3. 上限の単位が変わる。** Bedrockのスループットはリージョン×アカウント単位のクォータで管理されます。つまりチーム全員とCIが同じ口を共有します。何人で使うとどの上限に先に当たるかは利用パターン次第なので、ここは見積もりで断定せず、導入初期に実測してクォータ引き上げを申請するのが筋だと思います。未検証の領域として正直に書いておきます。

**4. ゲートウェイを挟むなら、素通しの責任を持つ。** 複数のモデルプロバイダを一元化するLLMゲートウェイを使う構成では、`ANTHROPIC_BEDROCK_BASE_URL`や`ANTHROPIC_VERTEX_BASE_URL`で向き先をゲートウェイへ変え、ゲートウェイ側が認証を持つなら`CLAUDE_CODE_SKIP_BEDROCK_AUTH=1`のようなスキップ指定を合わせます。監査ログと鍵管理を1か所に集められる半面、ゲートウェイがヘッダや未知のフィールドを落とすと、上の2で触れたような機能が静かに使えなくなります。挟むなら「素通しの維持」を誰が担うかまで決めておく必要があります。

## どの経路を選ぶか: 判断基準は「統制がどこに既にあるか」

ここまでを判断基準に落とすと、次のようになります。

- **個人・数人のチーム**: 既定のまま（サブスクリプションかAPI直結）。切替で得られる統制より、認証・クォータ管理の運用コストのほうが高くつきます。
- **AWSに統制が寄っていて、個人へのAPIキー配布を避けたい**: Bedrock。IAM・請求・審査済み経路の3点がそのまま使えます。
- **Google Cloudが主戦場**: Vertex AI。考え方はBedrockと同じです。
- **複数プロバイダの一元管理や監査集中が要件**: 上のどれかに加えてLLMゲートウェイを検討。ただし素通し維持の運用責任込みで。

導入時の注意も1つ。最初の壁はClaude Codeではなく、たいていクラウド側です。モデルアクセスの有効化、Claudeモデルを提供するリージョンの選定、IAM権限の設計、クォータの確認。切替の2行より、この準備のほうが時間を使います。逆に言えば、ここさえ通れば開発者の手元の体験はほぼ変わりません。

## まとめ: 切替は数行、設計は認証と上限

- Claude Codeは`CLAUDE_CODE_USE_BEDROCK=1`や`CLAUDE_CODE_USE_VERTEX=1`で、Anthropic API直結からBedrock / Vertex AI経由へ切り替えられる。鍵の配布がなくなり、認証・請求・審査はクラウド側の統制に統合される
- 変わるのは置き場所ではなく管理者。**認証には寿命が生まれ、無人運用では更新の設計が必須**になる。実行環境に権限を持たせる形（ロール・OIDC）が基本
- 機能の提供条件やクォータの単位も経路で変わる。ゲートウェイを挟むなら、フィールド素通しの維持まで含めて責任を決める
- 選び方は「統制がどこに既にあるか」。小規模は既定のまま、AWSならBedrock、Google CloudならVertex AI

APIキーを配らない導入は、鍵の管理をなくす話ではなく、鍵の管理をIAMという既存の筋肉へ引っ越す話です。引っ越した先の作法（寿命・上限・審査）で設計し直す。それができれば、Claude Codeの組織導入はかなり現実的な選択肢になっていると思います。
