同じモデル、同じプロンプトのまま、LLMのAPI料金を半額にする枠があります。バッチ処理（Batch API）です。結果を急がないリクエストをまとめて投げ、あとで回収する代わりに、入力・出力トークンの両方が50%引きになります。Anthropic・OpenAI・Geminiの3社とも、この構図は同じです。

ただし先に線を引いておきます。半額にできるのは「互いに独立したリクエストの束」だけで、ツールを呼びながら一歩ずつ進むAIエージェントの本体ループは、この枠に乗せられません。「エージェントのコストが高いからBatch APIで半額に」という期待は、設計を確認した時点で崩れます。

この記事では、バッチ処理の仕組みと3社の条件、エージェント運用のどこが半額にできてどこができないのか、そして部分失敗を前提にした設計の要点を整理します。対象読者は、LLM APIの請求を下げたい実務者と、AI活用の運用コストを見積もりたい発注側の方です。

## Batch APIとは｜「待てる処理」をまとめて安く流す仕組み

通常のLLM API呼び出しは同期型です。リクエストを1件送ると、数秒から数十秒でレスポンスが返る。チャットUIやエージェントの応答はこれで動いています。

Batch APIはこの前提を捨てます。流れは3社ともほぼ共通で、次の形です。

1. リクエストを束にして投げる（数百〜数万件をひとつのバッチとして登録）
2. バッチのIDを受け取り、処理はプロバイダ側のキューに積まれる
3. 状態を確認しながら待ち、完了後に結果をまとめて回収する

「すぐ返さなくていい」という条件を受け入れる代わりに、料金が半額になります。プロバイダ側から見ると、バッチ分は空いた計算資源に都合よく割り付けられるため、割引を出せる構造だと考えられます。利用者側から見ると、これは純粋な交換です。差し出すのはリアルタイム性、受け取るのは50%の割引。技術的に何かを削る話ではなく、同じモデルの同じ出力が安くなります。

## 3社の条件比較

主要3社の条件を並べます（いずれも各社公式ドキュメント、2026-11-14確認）。

| | Anthropic | OpenAI | Gemini |
| --- | --- | --- | --- |
| 割引率 | 50% | 50% | 50% |
| 完了の目安 | 多くは1時間以内（上限24時間） | 24時間以内 | 目標24時間以内 |
| 1バッチの上限 | 100,000件または256MB | 50,000件または入力ファイル200MB | 入力方式（インライン/ファイル）で異なる |
| 投入形式 | リクエストの配列 | JSONLファイル | インラインまたはファイル |

細かい違いで実務に効くのは次の3点です。

- **Anthropicは結果を29日間保持**します。回収処理が多少遅れても結果は消えません。
- **OpenAIはバッチ用のレート制限が同期APIと別枠**です。夜間に大量のバッチを流しても、日中の同期呼び出しの枠を食いません。Chat CompletionsだけでなくEmbeddingsなど複数のエンドポイントがバッチ対象です。
- **Geminiはインライン投入とファイル投入の2方式**があり、少量ならファイルを作らずそのまま投げられます。

## 最小の実装イメージ

形をつかむために、Anthropicの例で最小の流れを示します。やることは「`custom_id`付きのリクエスト配列を登録して、あとで結果を取りに行く」だけです。

```python
from anthropic import Anthropic

client = Anthropic()

batch = client.messages.batches.create(
    requests=[
        {
            "custom_id": "review-0001",
            "params": {
                "model": "claude-sonnet-5-5",
                "max_tokens": 256,
                "messages": [
                    {"role": "user", "content": "次のレビューを3分類してください: ..."}
                ],
            },
        },
        # 以降、同じ形のリクエストを必要な件数だけ並べる
    ]
)
print(batch.id, batch.processing_status)  # 登録直後は in_progress
```

回収側は、状態が終了になってから結果をストリームで受け取ります。

```python
for entry in client.messages.batches.results(batch.id):
    if entry.result.type == "succeeded":
        save(entry.custom_id, entry.result.message)
    else:
        retry_queue.append(entry.custom_id)  # 失敗・期限切れは再投入へ
```

前提はPython SDKと環境変数のAPIキーだけで、同期APIで動いているコードがあれば、`params`の中身はそのまま流用できます。戻すのも簡単で、バッチ登録をやめて同期呼び出しに戻すだけです。OpenAIはこれがJSONLファイルのアップロードになり、GeminiはSDKのバッチ用メソッドになりますが、「登録→待つ→回収」の骨格は変わりません。

## 夜間に同期APIで回すのと何が違うのか

「急がない処理は深夜に同期APIで回せば同じでは」という案とも比較しておきます。電力料金と違って、LLM APIの単価には時間帯割引がありません。深夜に回しても同期APIは定価のままです。割引が付くのはバッチという契約形態に対してであって、実行時刻に対してではありません。

もうひとつの違いはリトライ運用の所在です。同期APIで1万件を自前で回すと、レート制限への配慮、429エラーの指数バックオフ、途中で落ちたときの再開位置の管理が全部こちらの実装になります。バッチでは、束の実行管理はプロバイダ側の仕事になり、こちらに残るのは後述する「結果の突合と再投入」だけです。大量処理の実行基盤を自前で持たなくてよくなる分、半額という数字以上の差が出る場面もあります。

## 半額にできないもの｜エージェントの本体ループ

ここで最初の線引きに戻ります。コスト最適化の文脈でBatch APIを調べ始めると、たいてい「ではエージェントの実行を全部これに乗せれば半額では」と考えます。私も見積もりの初手ではそう考えたくなります。しかし、これは成立しません。

Batch APIの前提は、**束の中の各リクエストが自己完結していること**です。1件ごとにプロンプトが確定していて、他のリクエストの結果に依存しない。だからこそプロバイダは順不同で都合よく処理できます。

一方、AIエージェントの本体は逐次の連鎖です。モデルが応答し、ツールを実行し、その結果をプロンプトに足して次の呼び出しをする。2手目のリクエスト内容は1手目の結果が返るまで確定しません。「次に何を聞くかが前の答えに依存する」処理は、原理的にバッチへ畳めないわけです。

つまりコスト最適化は役割分担になります。

- **エージェントの本体ループ**: バッチには乗らない。ここの削減はプロンプトキャッシュと「読ませる量の設計」の仕事
- **エージェントの周辺にある大量処理**: 独立したリクエストの束にできるなら、Batch APIで半額にできる

エージェント本体側のコスト設計は、プロンプトキャッシュの記事で扱っています。

## 向いている処理｜評価・分類・埋め込み・夜間レポート

では「周辺の大量処理」とは具体的に何か。バッチに向くのは、件数が多く、1件ずつの即答が不要で、失敗しても再実行できる処理です。典型は4つあります。

**1. 評価（LLM-as-a-judge）の一括実行。** エージェントやプロンプトの出力品質を、別のLLMに採点させる評価運用です。評価は本番応答と違って誰も待っていません。100件のテストセットを回すなら、100件の独立した採点リクエストの束になり、バッチの条件にそのまま一致します。

**2. ログ・テキストの大量分類と抽出。** 問い合わせのタグ付け、レビューの感情分類、ドキュメントからの構造化データ抽出。1件ずつは小さくても、月次でまとめると件数が支配的なコストになりがちな処理です。

**3. 埋め込み（エンベディング）の生成。** RAGの初期構築や再インデックスで、数万チャンクをベクトル化する処理。OpenAIはEmbeddingsエンドポイントがバッチ対象なので、インデックス構築費を素直に半額にできます。

**4. 夜間の要約・レポート生成。** 「翌朝に人が読む」成果物は、深夜のうちに終わっていれば十分です。完了が数時間ずれても誰も困りません。

共通点を裏返すと、判定条件は「この処理、明日の朝まで待てますか」という一つの質問に集約されます。待てるなら候補、待てないなら対象外です。

## 失敗前提で設計する3点

半額には運用上の代償もあります。同期APIでは考えなくてよかった失敗の形が増えるので、最初から織り込んで設計します。

**1. 突合IDを必ず付ける。** 結果は投入した順に返るとは限りません。AnthropicもOpenAIも、リクエストごとに`custom_id`を付けて、回収時に自分のデータと突合する前提です。連番でもハッシュでも、元データへ一意に戻れるIDを投入時に埋めます。

**2. 部分失敗と期限切れを再投入できる形にする。** バッチは全体の成功・失敗ではなく、リクエスト単位で成功と失敗が混ざって返ります。さらにAnthropicの場合、24時間以内に処理しきれなかった分は期限切れとして返る仕様です。「失敗・期限切れの分だけ抜き出して翌日のバッチに入れ直す」処理まで作って、はじめて運用に乗ります。同じリクエストを再投入しても壊れないよう、下流の書き込みは冪等にしておきます。

**3. ポーリングは完了目安に合わせる。** バッチの完了を知るには、基本的に自分で状態を確認しに行きます。数秒間隔で叩く意味はありません。「多くは1時間以内」のAnthropicなら数分間隔、24時間窓のOpenAIなら数十分間隔など、完了の目安に合わせた確認間隔にします。

ひとつ注意があるのはプロンプトキャッシュとの併用です。Anthropicはバッチ内でもプロンプトキャッシュを使えますが、キャッシュヒットはベストエフォートで保証されません。「バッチ50%引き×キャッシュ読み取り割引」を最大値で皮算用すると、見積もりが実請求とずれます。割引の重なりは保証分だけで計算し、キャッシュヒット分は上振れ扱いにしておくのが安全です。

## 使うか、使わないか

最後に判断基準をまとめます。

**使う**: 評価・分類・埋め込み・夜間レポートのような、独立したリクエストを大量に流す処理。とくに評価運用は「件数が多い・誰も待っていない・再実行できる」の三拍子がそろうので、最初の移行対象として分かりやすい位置にあります。

**使わない**: 対話応答、エージェントの本体ループ、下流が数分以内に結果を要するパイプライン。ここに無理にバッチを挟むと、半額の代わりに「いつ終わるか分からない」を抱え込みます。

導入の最初の一歩はコードではなく棚卸しです。いま同期APIで流しているリクエストを「人が待っている処理」と「実は誰も待っていない処理」に分ける。後者が一定量あるなら、Batch APIはモデルもプロンプトも変えずに効く、数少ないコスト削減手段になります。
