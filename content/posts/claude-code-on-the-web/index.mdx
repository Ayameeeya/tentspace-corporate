Claude CodeのWeb版は、CLIをブラウザに移植したものではありません。**実行場所ごと変わる、別の形態です。** ブラウザに見えているのは操作面だけで、エージェント本体はAnthropicが管理するクラウドの隔離コンテナで動きます。手元のマシンには何もインストールされず、何も触られません。

この違いを押さえると、Web版の性質は3行に要約できます。

1. **状態は残らない。** セッションの実行環境は使い捨てで、リポジトリは開始のたびに新しくcloneされます
2. **ネットワークは環境ポリシーが決める。** 外への通信の到達範囲は、実行環境を作るときに選んだポリシーに従います
3. **成果の持ち出しはgitだけ。** commitしてpushしたものだけが残り、それ以外は環境ごと消えます

この記事は、Claude CodeをCLIで使っている人と、ブラウザだけで試してみたい人に向けて、Web版（Claude Code on the web）の仕組みとセットアップ、ローカルの感覚のまま使うと踏む段差、CLI・GitHub Actionsとの使い分けを公式ドキュメントベースで整理します。

## ブラウザはリモコン、実行はクラウド

Claude Codeの提供形態は現在、ターミナルのCLI、デスクトップアプリ、Web版（claude.ai/code）、IDE拡張の4つがあります。このうちWeb版だけが、実行場所そのものが手元を離れる形態です。

仕組みはシンプルです。ブラウザでリポジトリを選んでタスクを指示すると、Anthropic側のクラウドに隔離されたコンテナが立ち上がり、その中へリポジトリがcloneされ、Claude Codeのエージェントが作業を始めます。進行はブラウザから追え、途中で指示を足すこともできます。作業が終わるとブランチへpushし、そのままプルリクエストを作らせる流れが基本線です。

Web版は2025年10月に公開されました。当初は研究プレビューとしての提供で、ブラウザに加えてモバイルアプリからもセッションを扱える形で始まっています（[公式発表](https://www.anthropic.com/news/claude-code-on-the-web)）。

CLIとの一番の違いは、**セッションと実行環境の寿命が一致している**ことです。ローカルのCLIでは、セッションを閉じてもファイルもブランチも手元に残ります。Web版では、コンテナは一定時間操作がないと回収され、pushしていない作業はそこで終わりです。「消えて困るものはpushする」ではなく、「pushしたものしか存在しなかったことになる」。この前提の逆転が、後述する使いどころのすべてに効いてきます。

## セットアップ——GitHub接続と最初のセッション

Web版の入口は2つの接続です。

**1つ目はGitHubアカウントの接続。** claude.ai/codeを開き、GitHubアカウントを連携します。

**2つ目はClaude GitHub Appのインストール。** エージェントがリポジトリをcloneしてpushするための経路で、リポジトリ単位でインストールします。組織のリポジトリなら、組織のオーナーにインストールしてもらう形になります。ここで選んだリポジトリだけがWeb版から見える、という境界の作り方です。

接続が済んだら、リポジトリを選んでタスクを文章で指示するだけでセッションが始まります。最初のタスクは、CLIの初回と同じ考え方で選ぶのがおすすめです。つまり、正解を自分が知っていて、失敗しても被害のない読み取り系や小さな修正から。この選び方は入門記事に書いた通りで、実行形態が変わっても変わりません（[Claude Code入門｜インストールから最初のタスクまで](/blog/claude-code-getting-started)）。

CLIと感覚が変わるのは並列度です。セッションはリポジトリごと、タスクごとに複数同時に走らせられます。手元のマシンと違ってセッション同士が資源を取り合わないので、「リファクタリングを2案並走させて良い方を採る」「別リポジトリの調査を裏で走らせておく」といった使い方が、追加の仕掛けなしで成立します。ローカルで同じことをするならgit worktreeで作業ツリーを分ける必要がありました。Web版は環境の分離が既定なので、この準備が要りません。

## 環境（environment）の設計——本体はネットワークポリシー

Web版には「環境（environment）」という設定単位があります。セッションが走るコンテナの仕様書にあたるもので、主に3つを持ちます。

- **ネットワークポリシー**: コンテナから外への通信をどこまで許すか。環境を作るときに選びます
- **環境変数**: ビルドやテストに必要な設定値
- **セットアップスクリプト**: セッション開始時に依存のインストールなどを行う初期化処理

この3つのうち、設計判断として重いのはネットワークポリシーです。制限を強くすれば、エージェントが想定外の外部と通信する経路は細くなります。一方で、依存パッケージの取得先やテストが叩く外部APIまで塞がると、作業自体が成立しません。「このリポジトリの作業に必要な宛先はどこか」を先に棚卸しして、環境をリポジトリの用途ごとに分けるのが現実的です。

ここはサンドボックス記事で書いた「壁の内側に何を持ち込むか」の議論とちょうど対になります。ネットワークポリシーは壁の外側との経路を決め、環境変数は壁の内側に置く持ち物を決める。強い壁の内側に本番の認証情報を置いたら、壁の意味は薄れます。Web版の環境変数に入れる値も、その作業に本当に必要な最小の権限に絞るのが基本です。

## ローカルの感覚で使うと踏む3つの段差

Web版を「便利になったCLI」と捉えたまま使うと、実行形態の違いがそのまま段差になります。仕組みから導ける段差が2つ、自社の運用記録に残っている段差が1つあります。

**段差1: 状態が残らない。** ローカルの癖で「後でまとめてcommitしよう」と作業を積むと、セッションが回収された時点で消えます。ビルドキャッシュや生成物も同じで、次のセッションはまっさらなcloneから始まります。対策は運用ではなく設計で、**タスクの完了条件を「pushされていること」まで含めて指示する**ことです。「修正して」ではなく「修正してブランチへpushして」まで言い切る。エージェントへの指示の言い回しの話に見えますが、実際は成果物の定義の話です。

**段差2: ネットワークの失敗がローカルと違う顔をする。** ローカルで通っていた依存の取得や外部APIの呼び出しが、Web版では環境のポリシーに阻まれて失敗することがあります。厄介なのは、エラーの見た目が「ネットワーク障害」や「パッケージレジストリの不調」に似がちなことです。ローカルでは通る処理がWeb版でだけ落ちるときは、先にコードではなく環境のネットワークポリシーを疑うと、切り分けが速くなります。

**段差3: 無人実行では、開始時点の設定がすべて。** これは自社の運用で実際に踏んだ段差です。SNS運用の日次処理をクラウドの定時実行で回しているのですが、あるとき、**定時実行の設定で対象リポジトリが選択されておらず、予定した処理を開始できなかった**ことがありました。人が画面の前にいれば「リポジトリが選ばれていませんね」で終わる話です。無人だと、そこには「実行されなかった」という結果だけが残ります。

この失敗から持ち帰ったのは、Web版・クラウド実行を無人運用に使うなら、**セッションが立った時点の前提条件を疑う検査を、実行される側に置く**という発想です。対象リポジトリはあるか、必要なツールへ接続できているか。人間が席にいないなら、その確認までを自動化の範囲に含める必要があります。

## CLI・GitHub Actionsとの使い分け

実行形態が3つ並ぶと選択に迷いますが、起動の契機と人の位置で整理すると分かれ目は明確です。

| 形態 | 実行場所 | 起動の契機 | 向く作業 |
| --- | --- | --- | --- |
| CLI / IDE拡張 | 手元のマシン | 人が対話で進める | 日常の開発、設計判断が絡む作業 |
| Web版 | Anthropic管理のクラウド | 人が投げて、待つ | 独立した定型タスク、並列実行、手元に環境がない場面 |
| GitHub Actions連携 | GitHubのランナー | イベント（メンション・PR） | レビュー対応、Issue駆動の修正 |

**手を動かしながら判断する作業はCLI**です。設計の分岐で都度止めて方向を変えるような作業は、対話の密度が高いほど手元が向きます。

**「投げて、待って、PRで受け取る」が成立する作業はWeb版**です。テストの追加、依存の更新、明確なバグ修正、リポジトリ横断の調査。指示が1段落で書き切れて、成果がPRの形で検証できるものほど向きます。手元のマシンを汚さない・占有しないので、重い作業を裏で走らせる使い方とも相性が良いです。

**リポジトリ上のイベントに反応させたいならGitHub Actions連携**です。@claudeメンションで動く形やCIからの自動実行は、別記事で整理しています。

境界が曖昧になりやすいのはWeb版とActionsです。どちらもクラウドで動きますが、Web版は人がブラウザから投げる（またはスケジュールされた）タスクの箱、Actionsはリポジトリのイベントに紐づく箱、と捉えると迷いません。定時実行の自動化という意味では`claude -p`をcronに載せる選択肢もありますが、あちらは実行環境の用意が自分持ちです（[ヘッドレスモード入門](/blog/claude-code-headless-mode)）。Web版はその環境ごと借りる形になります。

## 受け取りはPRに固定する

Web版を実務に組み込むときに1つだけ運用の型を決めるなら、**成果の受け取り口をプルリクエストに固定する**ことをおすすめします。理由は3つあります。

**1つ目は、検証の場所が定まること。** Web版の作業は手元で動いた過程を見ていないので、「何をしたか」の確認はどこかで必ず必要になります。受け取りがPRなら、差分・テスト結果・説明文という検証の材料が毎回同じ場所に揃います。セッションのログを遡るより、PRを読む方が習慣として続きます。

**2つ目は、CIがそのまま安全弁になること。** リポジトリに既にあるlintやテストのCIは、人間のPRとエージェントのPRを区別しません。Web版の成果にも同じ検問が自動でかかるので、受け取り側の負担を増やさずに品質の床を作れます。エージェント用に検査を別立てするより、既存のCIに乗せる方が確実です。

**3つ目は、並列と相性が良いこと。** セッションを複数走らせると、成果も複数返ってきます。ブランチとPRが1タスク1本で切られていれば、採用する案だけマージして残りは閉じる、という選別がGitHubの画面だけで済みます。

逆に言うと、**PRとして受け取れない粒度のタスクはWeb版に向いていません**。「リポジトリ全体をいい感じに改善して」のような指示は、返ってきた巨大な差分を検証できず、レビューが形骸化します。1セッション1PR、1PRはレビューできる大きさまで。ここはエージェントに限らないPR運用の原則が、そのまま効く場所です。

## まとめ——「作業マシン」ではなく「使い捨ての実行環境」

Claude CodeのWeb版を整理しました。

1. Web版はCLIのブラウザ移植ではなく、Anthropic管理の隔離コンテナで動く別の実行形態
2. 入口はGitHubアカウント接続とClaude GitHub Appのインストール。見せるリポジトリはApp側で絞る
3. 環境（environment）の設計の本体はネットワークポリシー。作業に必要な宛先を先に棚卸しする
4. 状態は残らない前提で、タスクの完了条件を「pushまで」で定義する
5. 無人運用に使うなら、開始時点の前提条件の検査を実行される側に置く

ローカルのCLIが「自分の作業マシンに来てもらう」形だとすると、Web版は「使い捨ての実行環境ごと借りる」形です。道具としては同じClaude Codeでも、設計の作法はかなり違います。まずは失敗しても困らない定型タスクを1つ投げて、pushまで届く感覚を確かめるところからが良いと思います。
