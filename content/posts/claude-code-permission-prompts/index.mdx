Claude Code 2.1.319（2026-11-06）で、許可プロンプトで待つはずのツール呼び出しを拒否してターンを続行する設定 `permissions.denyInsteadOfPrompting` が入りました。結論から言うと、無人実行での許可待ちの扱いは「止める」「拒否して進む」「事前に決めて通す」の3択が出そろった形です。ただし、どれを選んでも成立条件は同じで、**止まった・拒否されたという事実を後から数えられること**。選択肢そのものより、この観測の設計が本体だというのが私の読みです。

想定読者は、Claude Codeを定時実行やCIで無人運用している方と、エージェントに確認をどこまで求めるかを設計する立場の方です。何が変わったか、3つの扱いの違い、実務での採否の順に整理します。

## 何が変わったか: 「許可待ちで止まる」以外の既定を選べるようになった

[公式の変更履歴](https://code.claude.com/docs/en/changelog)によると、2.1.319のAddedに入ったのは次の内容です。`permissions.denyInsteadOfPrompting` を有効にすると、許可プロンプトで待機するはずのツール呼び出しは拒否され、ターンはそのまま続行します。対象はターミナルセッション、サブエージェント、teammatesです。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code 公式変更履歴" />

前提を補足します。Claude Codeの権限は、設定ファイルのallow・deny・askのルールと権限モードの組み合わせで決まります。denyに当たる操作は拒否、allowに当たる操作は実行、そして**どのルールにも当たらない操作やaskに当たる操作が、実行してよいかを人に尋ねる許可プロンプトになります**。画面の前に人がいれば、これはただの確認です。しかし定時実行やCIのように誰も答えられない実行では、尋ねた時点でターンが進まなくなる。つまり無人実行における許可プロンプトは、実質「停止」として働いてきました。ルールの書き方そのものは以前整理したので、本記事は「尋ねる場面に出会ったとき、どう振る舞わせるか」に絞ります。

<LinkCard slug="claude-code-permission-layers" />

今回の設定は、その「停止」を「拒否して続行」に差し替えます。許可を求める場面で呼び出しは失敗扱いになり、エージェントは失敗を前提に残りの作業を続けます。止まらない代わりに、その操作は実行されません。

## 無人実行の許可待ちは、3つの扱いに分かれた

この設定が入ったことで、許可プロンプトに出会ったときの挙動は選択式になりました。整理すると3つです。

**1つ目は、止める。** 既定のままの挙動です。安全側に見えますが、無人実行では「確認」と「停止」が同義になります。同じ構図の変更が2.1.318（2026-11-04）にもあって、「メッセージがフラグされたときモデルを切り替える」設定が「毎回確認」のとき、サブエージェントはモデルを切り替える代わりに停止するようになりました。人が返事をできない場所では、確認を求める設計はすべて停止として振る舞う。これはClaude Codeに限らない話です。

**2つ目は、拒否して進む。** 今回の `denyInsteadOfPrompting` です。ターンが最後まで走るので、1つの操作が引っかかっても残りの工程は成立します。一方で、止まっていたことで防げていた誤動作が、形を変えて後工程へ流れる可能性があります。たとえば、ある書き込みが拒否されたまま後続の集計や通知が走れば、欠けた前提の上に結果が積み上がる。ここは未検証の推測ですが、「止まらない」は「正しく動く」を意味しません。

もう1つ気にしているのは、対象にサブエージェントとteammatesが含まれている点です。サブエージェントの中で起きた拒否は、親エージェントが受け取る要約の書き方しだいで、人の目にはさらに届きにくくなります。審査や調査をサブエージェントへ分離する構成を使っているほど、「どこかの階層で何かが拒否されたが、全体としては完走した」という状態が起きやすくなるはずです。これも推測ですが、階層が深いほど観測の要件は上がると考えています。

**3つ目は、事前に決めて通す。** 許可ルールで明示的にallowするか、操作の是非を実行時に審査へ委ねるかです。審査側も既定が動いていて、2.1.318では `managed-agents-onboard` で作られる新規エージェントの組み込みツールとテンプレートのMCPツールに、auto権限ポリシー（リスクのある操作を審査する設定）が既定で付くようになりました。外すには「run without asking」と伝える形です。さらに2.1.319では、autoモードの安全チェックが使えないときにクライアント側の分類器へフォールバックせず、「聞くか拒否」になる変更も入っています。既定は提供側の判断で動き続けるので、無人実行の起動経路には「どの扱いで動くか」を明示しておくのが安全です。

## 「どれが安全か」を考えていたら、先に観測の穴が直っていた

3択のどれを選ぶかを考えながら変更履歴を読んでいて、順番が逆だと気づきました。選択肢の議論より先に、**止まった・拒否されたことが外から見えない穴**が、この2週間で2件直っています。

1件目は2.1.316（2026-10-31）の修正です。autoモードがサーバーから安全判定を得られずターンを止めたとき、クラウドセッションとクラウドの定期タスクがfailedとして記録されていませんでした。つまり、止まったのに帳簿の上では失敗になっていない。2件目は2.1.319の修正で、安全チェックがないために行動が拒否された `claude -p` が、終了コード0を返していました。拒否されたのに、呼び出し元から見れば成功です。

どちらも構図は同じです。**止める・拒否するという安全側の動作は入っていた。でも、その事実が成功と区別できない形で外に出ていた。** 止めた側の判断が正しくても、観測がなければ運用上は「何も起きていない」ように見えます。

私も同じ形の事故を記録しています。日次のRoutineで、対象リポジトリが選択されておらず、予定した処理がそもそも開始できていなかったことがありました。エラーで落ちたのではなく、始まらなかっただけ。止まることが安全だとしても、止まったことに気づく仕組みが別にないと、停止は「静かな欠落」になります。拒否して進む場合も同じで、拒否が成功ログに紛れれば「静かな間引き」になる。選択肢の安全性を比べる前に、どの選択肢でも観測が成立しているかを先に確かめるべきでした。

もう1つの含意は、観測をどちら側に置くかです。failed記録も終了コードも、実行クライアントの帳簿であり、提供側の更新で直りも壊れもすることが今回の2件から分かります。私の運用では、投稿や公開のような取り消しにくい副作用を自作のWorker経由に集約し、成否の通知をそのWorker側から出す構成にしています。クライアントの帳簿も使いますが、最終的な成否は副作用にいちばん近い場所で数える。エージェントの成功報告をそのまま信じない、という以前からの整理に、今回の修正履歴は材料を2つ足してくれた形です。

## 実務での扱い: 拒否を数えられるまで、この設定は入れない

では3択をどう使い分けるか。私の整理は次のとおりです。

**`denyInsteadOfPrompting` は、拒否された呼び出しを数えられる状態を作るまで入れません。** 止まらないことの価値は理解しつつ、拒否が増えても外形上は毎回「完走」に見えるからです。終了コードの修正が入った経緯自体が、拒否は放っておくと成功に紛れるという根拠になっています。入れるなら、どの呼び出しが拒否されたかをログから拾う確認手順とセットで入れます。

**先に効かせるのは3つ目の「事前に決めて通す」です。** 無人実行では、許可プロンプトが出た時点で設計の漏れと考えます。定型の操作は許可ルールとして宣言し、書き込み範囲のような境界は設定で固定する。この「モードや成り行きではなく宣言で決める」方向は、作業ディレクトリ外への書き込みを全モードで止める設定が入ったときに整理したものと同じ系列です。

<LinkCard slug="claude-code-write-boundary" />

**「止める」は、止まったと分かる通知とセットでだけ使います。** 私の運用では、公開前審査に落ちた原稿を2回まで修正し、それでも通らないものは隔離して全体の流れは止めない構造にしています。審査キューの滞留が新規作成まで止めた失敗を経て変えた形です。止める場所は意図して絞り、止めた事実は通知で外へ出す。承認ボタンを増やすのではなく既定値と境界で作るという考え方は、以前にまとめたものから変わっていません。

## 入れる場合の試し方: 本番より先に、拒否の見え方を確かめる

それでも「止まらないこと」が要る工程はあります。入れると決めた場合に、本番のRoutineへいきなり足すのではなく、先に確かめておく手順を書いておきます。私自身もこの設定は未検証なので、これは導入前の検証計画です。

前提は、壊れてもよい使い捨てのリポジトリを1つ用意すること。確かめたいのは機能の有無ではなく、**拒否が自分の環境でどう見えるか**です。

1. 許可プロンプトに必ず当たるタスクを1つ作ります。askルールに当てた操作や、どのルールにも書いていない操作を含む手順で十分です。
2. まず設定を入れない状態で非対話実行し、許可待ちで止まることを確認します。これが比較の基準になります。
3. `permissions.denyInsteadOfPrompting` を有効にして同じタスクを実行し、3点を記録します。ターンが最後まで走ったか。対象の操作は拒否されたか。そして**終了コードと出力のどこに、拒否の痕跡が残ったか**です。
4. 最後に設定を外し、元の「止まる」挙動に戻ることを確認します。戻し方が設定1行の削除で済むのは、この種の検証のやりやすい点です。

このうち本当に見たいのは3の3点目だけです。拒否の痕跡が、後からログで数えられる形で残るなら、入れたあとの運用で「拒否件数」を定点観測に足せます。残らない、あるいは自分の収集経路から見えない形なら、見える化を先に作るのが順番だと考えています。安全チェック起因の拒否で終了コードが0になっていた不具合が直ったのは2.1.319ですから、手元のバージョンがそれより古い場合は、終了コードを成否の根拠にしないことも補足しておきます。

まとめると、こうなります。

| 扱い | 挙動 | 無人実行での注意 |
| --- | --- | --- |
| 止める（既定） | 許可プロンプトで待機 | 停止と同義。止まったと分かる通知が要る |
| 拒否して進む | 呼び出しを拒否してターン続行 | 拒否が成功に紛れる。件数を数える手順が要る |
| 事前に決めて通す | 許可ルール・審査で事前に決定 | 既定値が更新で動く。起動経路に明示する |

新しい設定が増えるたびに「入れるか、入れないか」を考えたくなりますが、無人実行で先に確かめるべきは観測のほうです。止まったら止まったと分かるか。拒否されたら拒否されたと数えられるか。この2つに答えられる構成なら、3択のどれを選んでも致命傷にはなりません。逆に答えられないうちは、どれを選んでも同じ事故が形を変えて起きる。次の一歩としては、自分の実行経路で「最後に許可プロンプトが出たのはいつか」をログから言えるかを確かめるのがおすすめです。言えなければ、まだ選択の段階ではないはずです。
