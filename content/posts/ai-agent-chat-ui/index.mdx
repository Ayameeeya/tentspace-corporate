AIエージェントの人間側の接点は、チャットUIが既定ではありません。やらせる仕事が決まっているなら、チャットより「状態が残る面」——データベースと通知——のほうが仕事をします。私はSNS運用とブログ公開をエージェントに任せていますが、この系にチャットの画面は1つもありません。人間の接点はNotionのデータベースとSlack通知だけです。ただし面をデータベースに寄せると、チャットには無かった弱点も生まれます。通知が嘘をつくと、系全体が正常に見えてしまう。この記事では、チャットを面にしなかった判断と、引き換えに何を失ったか、そして作業面を選ぶときの3つの質問を整理します。

## チャットが既定になったのは「最初にクリックされたもの」だったから

きっかけは、GitHubの公式ブログに2026年9月24日に出た記事です。タイトルは「When chat is the wrong UI（チャットが間違ったUIであるとき）」。書いたのはGitHubのBurke Hollandで、チャットUIが支配的になった理由をこう説明しています。「it was the first thing that people clicked with」——人々が最初にクリックしたものだったから、と。

<LinkCard url="https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/" title="GitHub Blog: When chat is the wrong UI" />

つまりチャットは、AIの用途がまだ分からなかった時期の汎用解だった、という整理です。そして記事はこう続けます。「as the user you know what you're going to do with it, and at that point chat is often the wrong UI」——ユーザーとして何をするか分かっているなら、その時点でチャットはしばしば間違ったUIになる。

代わりに提示されるのが「canvas」です。記事の説明では、canvasは「a little full-stack application that runs inside of the GitHub Copilot app with no browser chrome」——ブラウザの枠を持たず、Copilotアプリの中で動く小さなフルスタックアプリケーションで、エージェントがそのサーバー側と双方向に通信します。例として挙がっているのは、Connect 4のゲーム、Wingetのパッケージ管理UI、入力補完付きでSQLiteを操作する画面、Jekyllの記事エディタ、そして人間のチェックポイントを挟む「Agent Loop」というcanvasです。

要するに「その用途の専用画面をエージェントに作らせて、それを面にすればいい」という提案です。この方向自体には賛成です。ただ、読みながら考えていたのは別のことでした。用途が決まっているとき、面は必ずしも「画面」である必要すらないのではないか。私の運用がまさにそれで、チャットどころか専用画面も無く、面はデータベースと通知だけで回っています。

## 無人運用の人間側の接点は、NotionのDBとSlack通知だけ

私の構成を具体的に書きます。SNS投稿とブログ記事の作成・公開を、日次の定時実行エージェントに任せている系です。人間がこの系と接する場所は2種類しかありません。

- **Notionのデータベースとページ**。投稿キュー、記事の仮説と検証ログ、キーワードの台帳、週次の振り返りページ。エージェントは状態をここへ書き、人間は見たいときにここを見ます
- **Slack通知**。公開の成否、審査の不合格、上限到達など、イベントの発生だけが人間へ飛んできます

チャットの画面はありません。エージェントに「あの記事どうなった？」と聞く場所は無く、代わりにキューの行を見ます。行には状態（下書き・承認済み・公開済み・隔離）と履歴が残っているので、聞かなくても分かります。

チャットを面にしなかった理由は単純で、**この系は人間の返事を待てない**からです。チャットは「向こうが何か言ったら、こちらが返す」という同期の面です。ところが定時実行の無人運用では、エージェントが動いている時間に人間が席にいる保証がありません。人間の応答を面の設計に組み込んだ瞬間、系のスループットは人間の応答速度が上限になります。承認ボタンを置かずに境界の設計で統制を作る話は、別の記事に書きました。

<LinkCard slug="ai-agent-human-in-the-loop" />

面をデータベースにすると、非同期が自然に手に入ります。エージェントは人間がいなくても状態を進め、人間は3日ぶりに見ても現在地が1行で分かる。会話ログを遡って「どこまで進んだんだっけ」と探す作業がそもそも発生しません。

もう1つの利点は、**面がそのまま次のエージェントの入力になる**ことです。チャットログは人間には読めますが、構造がないので機械の入力には向きません。データベースの行なら、状態遷移・修正回数・審査の指摘がフィールドとして残り、翌日のエージェントがそのまま読んで続きから動けます。複数のエージェントが同じキューを取り合うときの排他制御も、行の状態遷移で作れます。

## 面をDBにすると、人間の仕事は「返事」から「台帳の手入れ」に変わる

チャットの面を持たないと、人間の仕事の形も変わります。チャットでは人間の仕事は「返事をすること」でした。データベースの面では、人間の仕事は台帳の手入れになります。

私の運用で人間側に残っている操作は、だいたい次の3つです。まず、エージェントが判断の根拠にしてよい事実の記入。自社の情報は正データのファイルに書かれたものしか使わせない決まりにしているので、新しい事実を書けるのは人間だけです。次に、統制側のファイル——審査基準や権限設定——の変更のマージ。エージェントは変更の提案までで、確定は人間が行います。最後に、隔離された失敗作の処分。審査に2回落ちた原稿は隔離ステータスへ移されて通知が飛ぶので、気が向いたときに眺めて、直すなり捨てるなりします。

3つに共通するのは、**どれも即答を求められない**ことです。返事と違って、台帳の手入れは1日遅れても系は止まりません。エージェント側は「無ければ無いなりに進む」よう設計してあるからです。事実が未記入なら、その素材を使う記事を書かずに別の題材へ進む。隔離された原稿は、人間の対応を待たずに次の新規作成へ進む。人間を面から外すというのは、人間を系から外すことではなく、人間の関与を「いつやってもいい仕事」に変換することでした。

## 通知が嘘をつくと、面ごと正常に見える

ここまでは良いことずくめに聞こえますが、実際に運用して分かった弱点があります。面をデータベースと通知に寄せるということは、人間の目を「過程」から外して「結果の要約」に置くということです。そして要約する層が誤ると、面全体が誤ります。

実例があります。2026年8月24日、この系でブログ記事のカバー画像が欠落したまま公開される事故が起きました。原因は1つではなく三段の連鎖で、審査の即興判断の揺れ、外向き通信のブロック、そして寛容すぎるフォールバックが重なった結果、**欠落が正常完了に見える状態**になっていました。通知は「公開成功」と言い、キューの行も完了を示していて、面のどこにも異常が出ていなかったのです。

これがチャットの面だったらどうだったか。人間が対話しながら進めていれば、「カバー画像はどうなった？」という一往復のどこかで違和感に気づけた可能性はあります。チャットは過程を人間に見せ続ける面なので、途中の欠落を拾うチャンスが多い。データベースと通知の面は、その過程を意図的に捨てて要約だけを見せる設計なので、要約に乗らなかった異常は静かに沈みます。

似た構図は他にもありました。Threadsの公開処理では、HTTP 400にsubcode `4279009`（Media not found）が付く失敗が間欠的に起き、Instagramでもcode 9007（Media is not ready）で投稿が欠便したことがあります。どちらも「完全な失敗」ではなく、少し待てば成功する境界線上のエラーです。この手の失敗は、過程を見ている人間なら「もう一回試せば通るやつだ」とすぐ分かりますが、結果の要約しか見せない面では「失敗した」か、悪くすると「何も起きなかった」に丸められてしまいます。対処として、これらは同一subcodeに限定した1回だけの再試行としてWorker側に実装しました。人間が過程で拾っていた判断を、コードに書き写した形です。

つまり、面の選択はUIの好みの問題ではなく、**人間が何を検知できるかの選択**です。チャットを捨てて非同期とスループットを取るなら、「過程の違和感を人間が拾う」という検知経路も一緒に捨てることになります。カバー画像の事故の後、系には「完了フラグではなく成果物の実在で判定する」検査を足しました。生成に成功したのにURLを渡せない状態を「カバー欠落事故」として明示的にSlackへ報告させ、正常完了として扱わない。要約する層そのものに、嘘をつきにくい形を強制する方向です。

## チェックポイントを見せる面と、見せない面

GitHubの記事に戻ると、例の中に「Agent Loop」というcanvasがありました。エージェントの作業の途中に人間のチェックポイントを挟むための画面です。これは私の系と正反対の設計で、並べると分かれ目がはっきりします。

- **チェックポイントを人間に見せる設計**（Agent Loop型）: 人間がその場で判断を返せる状況で強い。開発中のコードレビューのように、人間が席にいて、判断の質が人間側にある仕事
- **チェックポイントを機械に任せて、人間には通知だけ見せる設計**（私の系）: 人間が席にいない前提の仕事で強い。判断基準をルーブリックとして固定できて、毎回同じ検査を確実に通したい仕事

どちらが正しいという話ではなく、「人間がその場で判断を返せるか」と「判断基準を事前にファイルへ書き切れるか」で決まる使い分けです。私の系では公開前の判定を読み取り専用の審査エージェントに任せ、基準はルーブリックのファイルに固定しています。人間はその結果の通知を受け取るだけです。逆に、基準を書き切れない判断——たとえば審査基準そのものの変更——は、人間のレビューとマージに残しています。

## 作業面を選ぶ3つの質問

最後に、エージェントの作業面をどこに置くか迷ったときの質問を3つにまとめます。

1. **人間は返事を待てる位置にいるか。** その場で返せるならチャットやcanvasの同期の面が使えます。待てないなら、面は非同期の状態置き場（データベース）に寄せるべきです
2. **残すべきは会話か、状態か。** 探索や壁打ちなら会話そのものに価値があります。定型の仕事を回すなら、価値は現在の状態と履歴にあり、会話ログは邪魔にすらなります
3. **人間は何を検知する係か。** 過程の違和感を拾わせたいなら、過程が見える面が要ります。結果の異常だけ拾わせるなら通知で足りますが、その場合は「要約する層が嘘をつかない」ための検査を先に作る必要があります

チャットは、1が同期・2が会話・3が過程のときの正解です。無人の定時運用は3つとも逆に倒れるので、私の系にはチャットの面がありません。GitHubの「チャットはしばしば間違ったUI」という提起は、専用画面を作る話として読まれると思いますが、実務ではもう一歩先があります。用途が決まっているなら、面は画面である必要すらない。データベースの行と通知で足りることは多く、足りなくなる境目は「人間に何を検知させたいか」が変わったときです。
