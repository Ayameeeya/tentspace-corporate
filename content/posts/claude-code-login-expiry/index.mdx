結論から言うと、Claude Codeのサインイン期限はコマンドのJSON出力で事前に読めるようになっています。`claude auth status` の `loginExpiresAt`、ヘッドレス実行なら `claude -p --output-format json` の結果に含まれる `credential_expires_at` です。ただしこの値は「記録上の失効日」で、実際の失効は最大3日早いことがあり、ターミナルに出る警告はstderrにしか出ません。つまり、スケジュール実行やCIのような誰も画面を見ていない経路では、警告に頼らず値そのものを読んで、手前にしきい値を置く設計が必要です。

想定読者は、Claude Codeを定時実行やCIに組み込んでいて「ある朝、全部認証エラーで落ちていた」を避けたい方。それから、これから無人実行を組む前に、認証の寿命をどう扱えばいいか知っておきたい方です。

## サインイン失効は「落ちてから気づく」障害だった

Claude Codeをサブスクリプションのサインイン（OAuth）で使っている場合、そのサインインには有効期限があります。対話で使っている分には、期限が切れても再ログインすれば済む話です。面倒なのは無人実行で、期限が切れた瞬間からすべてのジョブが認証エラーで落ち始め、人がそれに気づくのは通知を見たときか、成果物が届かなくなったときです。

これまで厄介だったのは、失効の「予定日」を機械的に取る方法がなかったことです。残り日数を数えられなければ、監視は「落ちたことの検知」にしかなりません。Claude Code 2.1.318でサインイン期限の値がコマンド出力に追加され、この状況が変わりました。

この期限値の挙動を、DevelopersIOの検証記事（西村祐二さん・2026-11-14）がダミー資格情報とUbuntuコンテナ、Claude Code 2.1.322で細かく実測しています。本記事の数値はこの実測と、Claude Code公式の変更履歴に基づきます（確認日: 2026-11-16）。

## 期限を読める場所は2つある

実測で確認されている取得経路は2つです。

- **`claude auth status`**: JSON出力に `loginExpiresAt` が含まれます。認証状態の確認用コマンドなので、監視ジョブから定期的に叩く用途に向きます。
- **`claude -p --output-format json`**: ヘッドレス実行の結果JSONに `credential_expires_at` が含まれます。普段のジョブ実行の返りから「ついでに」期限を回収できるのがポイントです。

ヘッドレス実行側の例です。実行のたびに結果JSONへ期限が載ってくるので、専用の監視ジョブを増やさなくても、既存ジョブの後処理で残り日数を計算できます。

```bash
claude -p "ping" --output-format json > result.json
# result.json に credential_expires_at（UTC）が含まれる
# ここから「残り日数」を計算し、しきい値を切ったら通知する
```

注意点が2つあります。日付はUTC表示なので、JSTで運用しているなら9時間のずれを頭に入れておくこと。そして、この値が出るのはサブスクリプションのサインインだけで、認証方式によっては出ないことです（後述します）。

`claude -p` の組み込み方自体は別記事にまとめています。

## 警告は「人がターミナルを見ている」前提で出る

値を読まなくても、Claude Codeは失効が近づくと警告を出します。ただ、実測で分かったその出方が、無人実行にとっては絶望的です。

- 警告はテキストモードで**stderrへ1行**出るだけ。stdoutにも、`--output-format json` のJSON出力にも出ません。
- 出始めるのは終了10日前から。実測では10日ちょうどでは出ず、10日を1分切ると「in 7 days at the earliest」、残り5日で「in 2 days at the earliest」、残り2日で「can end at any time」、失効後は「may have ended」と変わっていきます。

つまりこの警告は、人が毎日ターミナルを開いて作業している使い方なら十分に機能します。逆に、stderrを捨てているスケジュール実行や、JSONだけをパースするパイプラインには、設計上届きません。「警告が出るはずだから大丈夫」は、無人経路では成立しないわけです。

警告文の「at the earliest（早ければ）」という言い回しにも意味があります。残り7日と言われて7日あるとは限らない。これが次の話につながります。

## 値が読めても、そのまましきい値にはできない

ここが今回いちばん面白かったところです。期限値が取れるようになった、ではその日付までは安全かというと、そうではありませんでした。

検証記事がAgent SDKの型定義（v0.3.323）から確認した仕様によると、この日付は**サインインの記録上の失効日**です。アクセストークンが更新されても日付は動かず、**実際の失効はこの日付より最大3日早いことがある**。しかも判定はローカルの記録に基づくもので、サーバーへ照会した結果ではありません。

つまり `credential_expires_at` は「この日まで使える保証」ではなく、「遅くともこの日には切れる」側の値です。しきい値を期限ちょうどに置くと、3日分の早期失効に踏み抜かれます。残り日数の判定は、少なくとも3日、警告文の挙動も踏まえるならもう数日、手前へ置くのが安全です。

なお検証記事自身も、実際のサインイン有効期間がどれくらいか、更新で日付が本当に動かないか、失効済みのログインが実際に拒否されるかまでは未検証として明示しています。断定できるのは「値の意味」と「出方」までで、その誠実な線引きごと参考になる検証でした。

## 残り日数の計算は、自分のコードで持つ

値の意味が分かったところで、実際に数える側の例です。ポイントは、Claude Codeの出力に判定させるのではなく、期限の文字列だけを受け取って、残り日数の計算としきい値判定を自分のスクリプトに持たせることです。

```bash
# ジョブ実行の結果JSONから期限を取り出す（キーの位置はバージョンで変わりうるため
# パスを決め打ちせず、キー名で拾う守りの書き方にしておく）
expires=$(grep -o '"credential_expires_at":"[^"]*"' result.json | head -1 | cut -d'"' -f4)

if [ -n "$expires" ]; then
  remaining_days=$(( ($(date -d "$expires" +%s) - $(date +%s)) / 86400 ))
  # 実際の失効は記録上の期限より最大3日早いことがあるため、手前で切る
  if [ "$remaining_days" -le 7 ]; then
    echo "サインイン残り${remaining_days}日（記録上）。再ログインを予定してください" | notify
  fi
else
  echo "期限値が取得できない構成です。別の数え方が必要です" | notify
fi
```

しきい値を7日にしているのは、「最大3日の早期失効」を引いてもまだ数日の猶予が残る位置だからです。再ログインは人の操作が要るので、猶予は営業日で数えておくくらいが実務的だと思います。

もう1つ地味に大事なのが `else` 側です。期限値が「取れない」のはエラーではなく、後述するとおり認証方式によっては仕様として出ません。取れないことを静かに無視すると、数えているつもりで何も数えていない監視になります。

## 認証方式ごとに、数え方が違う

もう1つ実務で効くのが、この期限値が**サインイン方式のときしか出ない**ことです。実測では次の整理になっています。

- **サブスクリプションのサインイン**: `loginExpiresAt` / `credential_expires_at` が出る。値を読んで数える。
- **APIキー・`CLAUDE_CODE_OAUTH_TOKEN`・他プロバイダー経由**: 日付が出ない。そもそもこの仕組みでは数えられない。
- **`claude setup-token` で発行した長期トークン**: 有効期間は約1年だが、期限表示がない。**発行日を自分で記録しておく**しかない。

表にするとこうです。

| 認証方式 | 期限値の有無 | 数え方 |
| --- | --- | --- |
| サブスクリプションのサインイン | 出る | JSON出力から機械的に回収 |
| APIキー / `CLAUDE_CODE_OAUTH_TOKEN` / 他プロバイダー | 出ない | キーのローテーション設計側で管理 |
| `claude setup-token` の長期トークン | 出ない（約1年） | 発行日を台帳に記録して逆算 |

無人実行の認証をどの方式にしているかで、「期限を数える場所」が変わります。サインイン方式なら実行結果から機械的に回収できる。setup-tokenなら発行日の台帳管理という地味な運用が必要になる。APIキーならキー自体に自然失効はない代わり、失効管理は自分のローテーション設計の問題になります。方式を選んだ時点で、監視の形も決まっているわけです。

ちなみにこの期限キーは2.1.317には存在しません。バージョンを固定して運用している場合は、まず手元のバージョンで値が出ることを確認してからです。

## 無人実行に組み込むなら、判定は呼び出し側に置く

以上を踏まえると、無人実行での設計はこうなります。

1. **残り日数の判定をジョブの呼び出し側に置く**。Claude Codeの警告はstderr行きで届かないので、`credential_expires_at` を実行結果から読み、自分のコードで日数を計算して通知する。
2. **しきい値は期限より3日以上手前に置く**。値は「遅くともこの日」側で、実際の失効は最大3日早くあり得るため。
3. **認証エラーでの失敗を、他の失敗と区別して通知する**。期限を数えていても、数え漏れや早期失効はゼロにならない。落ちたときに「認証切れだ」と一目で分かるだけで、復旧はまるで速くなります。

3は認証に限らない話で、エージェントの失敗をどう観測するかは別記事に書きました。

## 「落ちてから気づく」を「数えて待つ」へ

整理します。Claude Codeのサインイン期限は、2.1.318から `claude auth status` の `loginExpiresAt` と `claude -p --output-format json` の `credential_expires_at` で読めます。ただし警告はstderrにしか出ず、値は実際の失効より最大3日遅い側。だから無人実行では、警告に期待せず、値を読んで手前のしきい値で判定する——これが現時点の結論です。

認証の失効は、無人運用の障害の中では珍しく「予定日があらかじめ分かる」障害です。予定が読めるものまで「落ちてから気づく」側に置いておくのは、もったいない。値が取れるようになった今が、監視を仕込むタイミングだと思います。
