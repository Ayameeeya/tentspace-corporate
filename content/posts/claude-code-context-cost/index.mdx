定時実行エージェントのAPIコストを下げたいとき、プロンプトキャッシュのヒット率を上げる前にやることがあります。**毎ターン必ず読まれる量そのものを減らすこと**です。毎ターン乗る分の大半は会話ではなく、ツール定義とシステムプロンプト。キャッシュに乗っても無料にはならず、しかも接続を足すたびに静かに増えます。

この記事では、Claude Codeの定時実行Routineを日次で回している自分の環境を例に、入力コンテキストの「固定費」がどこで増えるか、2026年11月のClaude Code 2.1.319に入った「読ませる量を減らす」方向の変更、そして削減の順番を整理します。

想定読者は、Claude CodeやAIエージェントを定時実行・常駐で運用していてAPIコストが気になる方、MCPサーバーを足すたびに裏で何が増えているのか知りたい方です。

## 入力トークンの大半は、会話ではない

LLMのAPIはリクエストのたびに、モデルへ渡すものを全部送り直します。Claude Codeのようなエージェントの場合、その内訳はおおまかに3つです。

- **システムプロンプト**: ハーネスの指示、CLAUDE.mdなどのプロジェクト指示
- **ツール定義**: 接続しているツールすべての名前・説明・入力スキーマ
- **会話履歴**: これまでのやり取りとツール実行結果

このうちシステムプロンプトとツール定義は、1ターン目でも50ターン目でも全量が乗る「固定費」です。会話履歴はターンが進むほど増えますが、固定費は最初から満額。つまり、短いタスクほど総コストに占める固定費の割合が大きくなります。

自分の環境で数えてみると、SNS運用を自動化している日次Routineは、自作のMCPサーバー（Cloudflare Workers上で動かしています）だけでツールが55本あります。ここに公式のNotion MCPとGitHubのMCPサーバーを足すと、セッションに接続されるツール定義は合計150本を超えます。各ツールには説明文とJSONスキーマが付いているので、1本あたり数百トークン規模。使うかどうかに関係なく、接続していれば毎リクエストの候補として展開されます。あくまで概算ですが、仮に1本300トークンとすれば150本で4万5千トークン。会話を1文字も進めていない時点で、すでにこの量を毎ターン読ませている計算になります。

プロンプトキャッシュに乗せれば、この固定費の読み取りは通常入力の[約10分の1になります](https://docs.claude.com/en/docs/build-with-claude/prompt-caching)。ただしゼロではありませんし、もうひとつ見落としやすい影響があります。**コンテキストウィンドウの消費**です。固定費が大きいほど履歴に使える残り幅が狭くなり、長く走るRoutineでは文脈の圧縮が早く走ります。圧縮が走れば履歴が書き換わるので、キャッシュの再構築コストも発生します。キャッシュの仕組み自体は入門記事にまとめています。

## ツール定義は「置いてあるだけ」で読まれる

ツール定義が入力トークンを消費することは、Anthropic自身が[コンテキストエンジニアリングの解説](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)や[エージェント向けツールの書き方](https://www.anthropic.com/engineering/writing-tools-for-agents)で繰り返し注意している点です。ツールを増やすほどモデルの選択肢は増えますが、同時に毎ターンの読み込み量と、似たツール同士の選び間違いも増えます。

Claude Code側にも、この固定費を下げる仕組みが入っています。MCPツールの**オンデマンド読み込み**です。対象のツールは実際に必要になるまで定義の全文を読み込まず、呼ばれた時点で展開されます。[公式の変更履歴](https://code.claude.com/docs/en/changelog)を読むと、2.1.319（2026年11月6日）では`/context`の表示でも、未呼び出しのオンデマンド読み込みMCPツールはサーバー単位に畳んで表示されるようになりました（確認日 2026-11-10）。

ここで、ツール定義とキャッシュの位置関係を押さえておきます。[プロンプトキャッシュの公式ドキュメント](https://docs.claude.com/en/docs/build-with-claude/prompt-caching)によると、キャッシュは**前方一致**で効き、プロンプトはツール定義 → システムプロンプト → 会話という順に組み立てられます。つまりツール定義はプロンプトの最前列にいて、ここが1バイトでも変わると、後ろに続くシステムプロンプトと履歴のキャッシュまで全部切れます。固定費のかたまりが、同時にキャッシュ全体の土台でもあるわけです。

だから注意したいのが、ツール一覧を**会話の途中で**変えることと、**最初から**絞ることの違いです。途中で変えるとプロンプトの先頭側が書き換わるので、キャッシュが切れて逆に高くつきます。固定費の削減はセッションの開始前に決めておく話で、走っている最中にいじる話ではありません。この罠は別記事で分類しています。

## コンテキストを測るコマンドが、コストを足していた

ここまでは「読ませる量を減らす」という素直な話でした。設計が覆ったのは、その量を測るための道具の側です。

Claude Codeには、いまコンテキストに何がどれだけ乗っているかを一覧表示する`/context`コマンドがあります。固定費の棚卸しをするなら最初に打つコマンドです。ところが2.1.319のバグ修正には、こう読める項目が入っていました。**`/context`が自分のビジュアルグリッド全体を、その後の毎ターン、モデルへ送り続けていた**というものです（修正済み。グリッドがどれだけのトークンだったかは変更履歴に記載がなく不明です）。

つまり、コンテキストの内訳を調べるためにコマンドを打つと、その表示自体が以降の会話に残り、毎ターンの入力トークンとして課金され続けていた。測定が測定対象を増やしていたわけです。同じリリースでは表示自体もスリム化され、各リストは上位10行までに短縮されています。

これが今回いちばん持ち帰りたい教訓です。**観測もコンテキストに乗る**。`/context`に限らず、エージェントに状態を確認させるコマンド、デバッグのために読ませるログ、進捗を逐一報告させる指示は、すべて履歴に残って以降の毎ターンに課金されます。実は`/context`のトークン計上自体も、2.1.261で「追加の小型モデル呼び出し」から「ローカル推定」へ変わっており、測ることのコストを下げる変更が続いています。測ってから減らすのは正しい順番ですが、測る側のコストも設計に含める必要があります。

## 減らす順番は「接続 → 遅延読み込み → キャッシュ → 手順書分割 → 履歴」

固定費の削減でやることを、効果が大きい順に並べます。

### 1. 接続するサーバーを仕事ごとに絞る

いちばん効くのは、そもそも接続しないことです。MCPサーバーはセッション単位で接続が決まるので、Routineごとに「この仕事で本当に呼ぶサーバーはどれか」を数えます。自分の環境では、ブログ執筆のRoutineが実際に呼ぶのは自作Workerの55本のうち数本と、Notionの読み書きだけでした。全部入りの接続を全Routineに使い回すのは、便利なぶん固定費の無駄が大きい構成です。

### 2. 遅延読み込みに任せる

接続自体は必要でも、定義の読み込みは遅らせられます。前述のオンデマンド読み込みが効いている環境なら、呼ばれていないツールの定義は展開されません。自作MCPサーバー側でも、ツール1本ごとの説明文とスキーマを「モデルが選ぶのに必要な最小限」まで削ると効きます。説明を丁寧に書くほど良いと思いがちですが、全ツールの説明が毎ターン読まれる前提では、長さはそのままコストです。

### 3. 残った固定分は先頭で凍らせる

ここまでやって残る固定費は、プロンプトキャッシュで約10分の1に落とします。条件は、固定分がリクエストの先頭側で**毎回バイト単位で同一**であること。システムプロンプトにタイムスタンプを入れない、ツール一覧を途中で変えない、という地味な規律の話になります。

### 4. 手順書も分割して、使う時だけ読ませる

システムプロンプト側の固定費にも同じ発想が使えます。自分の運用では、全Routine共通の原則（公開ポリシー、データ境界、禁止事項）だけを1枚の指示書に集約し、ブログ執筆、SNS投稿、調査、計測といったRoutineごとの実行手順は、それぞれ個別のスキルファイルへ分割しています。ブログ執筆のRoutineを走らせた日に、調査Routineや計測Routineの手順まで読む必要はないからです。

さらに階層を1段分けていて、スキルファイル本体には手順の骨格だけを書き、frontmatterの仕様書や文体ガイドのような参照資料は本体へ書き写さず、別ファイルに置いて「実行中に必要になった時点で読む」構成にしています。仕様書のたぐいは分量が多いわりに、使う工程が限られます。最初から全部読ませるのではなく、書く段になったら読む。人間の仕事の進め方と同じ形に寄せると、コンテキストも同じように節約されます。全Routineの手順を1枚の指示書に書くと、どのRoutineを走らせても全Routine分の手順が毎ターン乗ります。分割しておけば、乗るのは今日使う分だけです。

### 5. 履歴は「圧縮に期待しない」側へ寄せる

会話履歴は固定費ではありませんが、放っておくと圧縮が走り、圧縮にもトークンとキャッシュ再構築のコストがかかります。長いログや大きなファイルをそのまま読ませず、要点だけ返すツール設計にしておくと、履歴の伸びが遅くなり圧縮も遠のきます。自作Workerで画像生成の結果をbase64ではなくURLで返しているのも、この一環です。

## 固定費 → キャッシュ → 計測の順で棚卸しする

まとめます。定時実行エージェントの入力コストは、次の順番で見ると詰まりにくいです。

1. **固定費を数える**: 接続しているMCPサーバーとツール本数、システムプロンプトの構成を一覧にする。`/context`で内訳を見る（2.1.319以降なら表示自体の負担も軽い）
2. **減らす**: 仕事ごとに接続を絞り、遅延読み込みに任せ、手順書を分割する
3. **凍らせる**: 残った固定分を先頭に固めて、キャッシュで読み取り単価を落とす
4. **計測の口を残す**: `/cost`にはキャッシュの読み書きの行があり、削減が効いたかを金額側から確かめられます（使い方は入門記事で扱いました）。ただし観測もコンテキストに乗ることを忘れない

自分の環境でも、Routine別にキャッシュの内訳まで突き合わせる実測はこれからで、まずは接続の棚卸しと手順書の分割から始めています。コンテキストを「何を読ませ、何を読ませないか」の設計として扱う考え方は、概念編として別記事にまとめているので、あわせてどうぞ。
