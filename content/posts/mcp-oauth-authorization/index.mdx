MCP（Model Context Protocol）のOAuth認可で、これまで実務の既定だった「接続時にスコープを一括付与する」形に、別の選択肢が加わりました。最小スコープで繋ぎ、足りなくなったときだけ昇格する**step-up認可**です。2026年10月19日、CloudflareのAPI MCPサーバーがこれに対応しました。

先に結論を言うと、step-up認可は「同意画面が賢くなった」話ではありません。昇格のゲートを押しているのはクライアントではなくサーバー側で、**「このツールにはこのスコープが要る」と宣言し、足りないときに断る判定がサーバーに置かれている**ことが本体です。そして、この仕組みが手元に来ても、自作MCPサーバーへそのまま入れるかは別の判断になります。私は現時点で入れない側を選びました。

この記事では、MCPの認可がOAuthで仕様化されている構図、一括付与の何が問題か、step-up認可の仕組み、自作サーバーでの採否の判断基準を順に整理します。対象読者は、MCPサーバーを自作・運用しているエンジニアと、チームでMCP接続の許可方針を決める立場の人です。

## MCPの認可はOAuth 2.1で仕様化されている

まず土台の確認から。MCPの仕様は、HTTPトランスポートで繋ぐMCPサーバーの認可を**OAuth 2.1ベース**で定めています。構図としてはこうです。

- MCPサーバーは、OAuthでいう**リソースサーバー**として振る舞う
- クライアントは認可サーバーからアクセストークンを取得し、リクエストの`Authorization`ヘッダで送る
- トークンには「何ができるか」の範囲が**スコープ**として紐づく

<LinkCard url="https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization" title="MCP仕様: Authorization（公式）" />

一方で、ローカルでstdioで繋ぐサーバーはこの枠の外で、環境から資格情報を取る整理です。つまり「MCPの認可=OAuth」が常に成り立つわけではなく、**HTTPで外に出すサーバーをどう守るかの標準**がOAuthに寄せられている、と読むのが正確です。

もうひとつ現実の話をすると、仕様がOAuthを定めていても、実装がOAuthとは限りません。利用者が自分だけの自家用サーバーなら、固定のBearerトークン1本で動かす構成は普通にあります。うちの自作サーバーもそうで、これは後半で「入れない判断」として取り上げます。

## 「接続時に全部渡す」が実務の既定だった

OAuth対応のMCPサーバーに繋ぐときの典型的な体験は、こうでした。同意画面が開き、サーバーが要求するスコープの一覧が出て、承認を押すと接続が完了する。以後、そのトークンで全ツールが動く。

この「接続時に一括付与」には、運用してみると引っかかる点が3つあります。

**1つ目は、渡した権限を使われる瞬間まで思い出せないことです。** 接続した日の自分は同意画面を読んでいます。でも実際にそのスコープを使うのは、数日後、数週間後のエージェントです。渡した側の記憶が薄れた頃に、渡された側だけが権限を覚えている。この非対称が、無人運用では特に効いてきます。

**2つ目は、最小権限にしようとすると接続のやり直しになることです。** 最初に絞って繋ぐと、後から必要になったスコープのために接続を作り直す。面倒なので「とりあえず全部付与」へ流れる。最小権限の原則が、運用の摩擦に負ける構造です。

**3つ目は、スコープが実質的な最後の防衛線になっている場面が多いことです。** 以前の記事で、クライアント側の承認ゲートがツールの自己申告（説明文や「読み取り専用」のような分類）を判定材料にしている限り、申告が嘘になった瞬間に守りが消える話を書きました。その構成では、嘘をついたツールを最終的に止められるのは「トークンにそのスコープが無い」ことだけです。その防衛線が接続時から全開になっているのが一括付与です。

## Cloudflareのstep-up認可は何を変えたか

2026年10月19日、CloudflareはAPI MCPサーバーがstep-up認可に対応したと発表しました（確認日: 2026-10-21）。

<LinkCard url="https://developers.cloudflare.com/changelog/post/2026-10-19-cloudflare-mcp-step-up/" title="Cloudflare changelog: MCP server support for step-up authorization" />

一次情報に書かれている動きを整理すると、次のとおりです。

1. クライアントは接続時に**最小のスコープだけ**を渡して繋げる。`https://mcp.cloudflare.com/mcp`への接続時、同意画面でMinimalを選ぶと最小権限から始められる
2. 未付与のスコープが必要なツール呼び出しが来ると、サーバーは**そのスコープ名を挙げたチャレンジ**を返す
3. MCPクライアントがそれを受けて、利用者へ追加の承認を求める
4. 承認されると追加スコープが付与される。**既に付与済みのスコープは保持されたまま**なので、昇格のたびに最初からやり直しにはならない

前提がひとつあって、この流れはstep-up認可に対応したMCPクライアントで利用できます。サーバーが対応しても、クライアントがチャレンジを解釈できなければ昇格のフローは始まりません。

技術的な背景を補足すると、OAuthのBearerトークン仕様（RFC 6750）には、権限不足を`insufficient_scope`というエラーコードで伝える型がもともと定義されています。「トークンはあるが、この操作には範囲が足りない」をサーバーが機械可読に言える仕組みです。step-up認可は、この「足りないと言える」型をMCPのツール呼び出しに載せた形と読めます。なお、Cloudflareの実装がどのエラー形式を使っているかまではchangelogに記載がないため、ここは一般論としての補足です。

<LinkCard url="https://datatracker.ietf.org/doc/html/rfc6750" title="RFC 6750: The OAuth 2.0 Authorization Framework: Bearer Token Usage" />

## 昇格のゲートを押しているのはクライアントではなかった

step-up認可のニュースを最初に読んだとき、私は「同意画面のUXが良くなる話」だと思いました。読み直して気づいたのは、**判定の主語が逆**だということです。

「このツールにはこのスコープが要る」と宣言しているのはサーバーです。足りないときにチャレンジを返すのもサーバーです。クライアントの仕事は、そのチャレンジを利用者に見せて承認を取り次ぐこと。つまりstep-up認可は、クライアントの承認ゲートが賢くなる仕組みではなく、**サーバー側に置いたツールとスコープの対応表が、承認ゲートを駆動する**仕組みです。

これは、守りの判定材料をツールの自己申告（クライアントから見えるメタデータ）に置かず、呼ばれる側のサーバー実装に置く、という以前からの整理と同じ構図です。承認ゲートの見た目は同じでも、発火の根拠が「ツールが自分で書いた説明文」なのか「サーバーが持つスコープ要求」なのかで、守りの強さはまったく違います。step-up認可が広がるなら、それは後者が標準の型になっていく動きだと受け取っています。

## 自作MCPサーバーにstep-upを入れない判断

では自分のサーバーに入れるか。うちのSNS運用システムのMCPサーバー（Cloudflare Workers上で稼働）は、結論としてOAuthもstep-upも実装していません。構成は次のとおりです。

- 認証は**固定のBearerトークン1本**。タイミング攻撃に配慮した比較で検証し、不一致には`WWW-Authenticate: Bearer`付きの401を返す
- スコープの代わりに、**副作用のあるツールは`confirm: true`を必須にする入力スキーマ**を置く。スキーマ上`true`のリテラルだけを受けるので、フラグを渡さない呼び出しは入力検証で落ちる
- 公開系ツールは**Worker側のKVで回数制限**をかける。全チャネル合算で60分に3件、プラットフォーム別の日次上限つき。仮にトークンが漏れても、公開できる回数の天井は変わらない

この構成でOAuthを選ばなかった理由は、利用者が自分と自分のエージェントだけの**単一テナント**だからです。スコープの動的な昇格は「誰に・どこまで渡すか」が可変なときに効く仕組みで、渡す相手が1人なら、トークン発行・更新・失効を含むOAuthサーバーの実装コストに見合う複雑さの削減がありません。守りたいもの（勝手に公開しない、回数の天井を超えない）は、サーバー側の断る実装で既に守られています。

資格情報の置き場所や、認証前に副作用を残さない設計は別記事にまとめているので、サーバーを自作する人はそちらもどうぞ。

逆に、**入れる側に回る条件**もはっきりしています。他人のトークンを預かる構成、あるいは複数の利用者に接続させるMCPサーバーを出すなら、接続時の一括付与はやめたい。そのときにstep-up認可対応のクライアントが前提にできるかを確認する。発注側として外部のMCP対応サービスを評価する場合も、「接続時に何を要求され、後から足せるのか」は確認項目に入れる価値があります。

## 接続とサーバーを棚卸しする3つの質問

最後に、いま動いている構成を見直すための質問を3つ置きます。

**1. 接続しているMCPサーバーに、どのスコープを渡したか言えるか。** 言えないなら同意画面を見直すところからです。Minimalのような選択肢を出すサーバーなら、最小で繋ぎ直して、困ったときに足す運用へ切り替えられます。

**2. そのスコープを最後に使ったのはいつか。** 接続時に「念のため」で付与した権限は、使われないまま残りがちです。使っていないスコープは、いざ事故が起きたときの影響範囲だけを広げます。

**3. スコープを剥がしたとき、何が壊れるか把握しているか。** これに答えられない状態は、権限とツールの対応をサーバー任せにも自分の記録にもしていない状態です。サーバーを自作している側なら、ツールとスコープ（または自前の制限）の対応表をサーバー側に持ち、読み取り系と書き込み系を分けるところから始められます。

step-up認可はまだ、対応クライアントが前提の新しい動きです。手元の環境で昇格フローを実測できたわけではないので、挙動の細部は未検証です。それでも、「最初に全部渡すか、必要になったときに渡すか」という問いが選べる問いになったこと自体が変化だと考えています。対応クライアントが手元に来たら、実測を足して続きを書きます。
