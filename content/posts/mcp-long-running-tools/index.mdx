画像生成やデプロイのような、数十秒から数分かかる処理をMCPツールにするとき、最初に悩むのはタイムアウトを何秒にするかだと思います。ただ、実際に運用してみると、これは**タイムアウトの長さの問題ではなく「誰がどこで待つか」を決める問題**でした。選択肢は3つあります。呼び出しの中で待ち切る。受付と完了を分けて、あとから取りに行く。そしてクライアントに待ちを肩代わりさせる。

3つ目は少し前まで存在しませんでした。2026年11月6日のClaude Code 2.1.319で、MCPサーバーがタスクとして実行したツール呼び出しをクライアントが即座にバックグラウンドへ移す挙動が追加され、「待たない」がクライアント側の既定になりつつあります。この記事では、自作MCPサーバーを無人運用している立場から、3つの待ち方の使い分けと、この変更をすぐに採用するかどうかの判断を整理します。

想定読者は、MCPサーバーを自作している・しようとしている方と、AIエージェントの自動化パイプラインに長い処理を組み込みたい方です。

## MCPツールは同期RPCの顔をしている

MCPのツール呼び出しは、関数を呼べば結果が返ってくる、昔ながらのRPC（遠隔呼び出し）の形をしています。`tools/call`を送ると、結果が1つ返ってくる。クライアントもモデルも、基本的にはその結果を待ってから次の行動を決めます。

この形は、数秒で終わる処理なら何も困りません。問題は、そこに画像生成、動画の合成、ビルドとデプロイ、外部サービスのバッチ処理といった「終わるまでの時間が読めない処理」を乗せたときです。待っている間、会話は進みません。クライアントやゲートウェイのタイムアウトに当たれば、処理はサーバー側で生きているのに呼び出しだけが死に、結果が宙に浮きます。宙に浮いた結果をモデルは知らないので、「失敗した」と判断してもう一度呼ぶ。副作用のある処理なら二重実行です。

つまり長時間実行の設計とは、タイムアウトとの戦いではなく、**結果とツール呼び出しの寿命を切り離すかどうか**の判断です。切り離さないなら呼び出しの中で待ち切る。切り離すなら、誰かが完了を確認しに行く必要があります。

## 呼び出しの中で待ち切る設計は、単純さで勝つ

1つ目の選択肢は、切り離さないことです。処理の開始から結果の確定までを1回のツール呼び出しに収めます。

私が運用しているSNS自動化の自作MCPサーバー（Cloudflare Workers上で動かしています）では、ブログのカバー画像生成をこの形にしています。画像モデルでの生成、ストレージ（R2）への保存、配信URLの確定までを1つのツールの中で終わらせて、モデルにはURLだけを返す。生成された画像のbase64をモデルへ戻さないのは文脈の節約ですが、それ以上に「このツールが成功を返したなら、URLの先に画像が必ず在る」という状態を作るためです。

この設計の利点は、結果の取り逃しが構造的に起きないことです。呼び出しが返ったら結果は確定している。返らなかったら失敗。途中の状態がありません。無人運用では、この単純さがそのまま監視のしやすさになります。

限界もはっきりしています。処理時間が呼び出しの寿命に収まる見込みがあるものにしか使えません。数十秒の画像生成までは待ち切れても、数分を超えるバッチをこの形にすると、今度はタイムアウトの延長合戦が始まります。そうなったら次の形へ移る合図です。

## 受付と完了を分けると、「まだ無い」が正常になる

2つ目の選択肢は、受付だけ即座に返して、完了は別のツールで確認しに行く形です。アップロードを受け付けてIDを返し、状態確認ツールで「処理中か、終わったか」を聞く。SNSのメディア系APIがだいたいこの形なので、それを包むMCPツールも自然と同じ形になります。

この形に移った瞬間に、エラーの意味が変わります。実際に踏んだ例でいうと、Threadsへの公開処理で、HTTP 400・subcode `4279009`（Media not found）が間欠的に発生しました。アップロード直後のメディアがまだ参照できる状態になっておらず、少し待ってから見れば存在する。「見つからない」というエラーの顔をしていますが、実体は「まだ」です。対処としては、コンテナの状態確認と、**この同じsubcodeに限った1回だけの再試行**をWorker側へ追加しました。のちにInstagramの配達でもcode 9007「Media is not ready」で同系統の欠便が起き、同じ型の限定再試行を足しています。

受付と完了を分ける設計を選ぶなら、この「失敗」と「まだ」の区別を、エラーコードの完全一致のような機械的に判定できる形で持つ必要があります。雰囲気で「エラーならリトライ」とやると、本当に失敗している呼び出しまで追いかけ続けることになります。このあたりの失敗の分類は別の記事にまとめました。

## 2.1.319で、「待たない」がクライアントの既定になった

ここまでの2つは、どちらもMCPサーバーを実装する側の工夫でした。待ち方はサーバーの設計で決まり、クライアントはそれに従うだけ。その前提が、2026年11月6日のClaude Code 2.1.319で変わりました。

変更履歴によると、MCPサーバーがツール呼び出しをタスクとして実行した場合、Claude Codeはその呼び出しを**即座にバックグラウンドへ移し、完了した時点で結果をモデルへ伝える**ようになりました。モデルは待たずに別の作業を進められます。従来どおり呼び出しの中で待たせたい場合は、環境変数`CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`を設定します。機能そのものを無効にする`CLAUDE_CODE_DISABLE_MCP_TASKS=1`も用意されています。同じリリースで、feature flagを取得しない経路——Bedrock・Vertex・Foundry・LLMゲートウェイ経由や`DISABLE_TELEMETRY`設定時——でもMCP tasksが動くようになったことも明記されています。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code 公式changelog（2.1.319）" />

設計の観点で重要なのは、新機能そのものより、**待ち方の決定権がサーバー実装の外へ出た**ことです。これまで「このツールは同期で返す」と設計すれば、どのクライアントから呼ばれても挙動は1つでした。これからは、同じサーバー・同じスクリプトでも、クライアントのバージョンと環境変数の組み合わせで、結果が「呼び出しの戻り値として届く」のか「あとからバックグラウンド完了として届く」のかが変わり得ます。環境ごとに結果の届くタイミングが変わるはず、というのが現時点の読みですが、ここは自分の環境ではまだ実測していません。未検証の部分は未検証と書いておきます。

## 無人運用では、まず待機側に固定して「取り逃し」を数える

では自分の運用でMCP tasksをすぐ既定にするかというと、答えは「まだ」です。人が画面を見ている対話セッションなら、長い処理の間に別の作業が進むのは純粋に体験の改善です。一方で誰も見ていない定時実行では、非同期化は**失敗が見えなくなる面積**を増やします。

これは一度痛い目を見ています。2026年8月、カバー画像の欠落が正常完了に見える事故が起きました。審査の即興判断の揺れ、ネットワーク遮断、そして寛容すぎるフォールバックが重なって、画像が無いまま処理全体は「成功」として完走していた。フォールバックは失敗を成功に変換する装置なので、発動を数えて申告させる必要がある、というのがそのときの学びです。結果が「あとから届く」仕組みも、構造としては同じ危うさを持っています。届かなかったことは、届いた結果を数えている側からしか見えません。

なので採否はこう置いています。無人の定時実行の経路では、まず`CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`で従来どおり待機側に固定する。そのうえで、バックグラウンド化を許すとしたら、完了結果の取り逃しを数える監査——期待した結果の件数と実際に届いた件数の突き合わせ——を先に用意してからにする。機能を先に入れて監視をあとから足すと、取り逃しに気づくのは欠落が成果物に現れたときになります。

## 3つの置き場所と、選ぶ順番

最後に、長時間実行の置き場所を選ぶときの自分の順番をまとめます。

- **呼び出しの中で待ち切る**: 処理時間が呼び出しの寿命に収まるなら最優先。結果の取り逃しが構造的に起きず、無人運用と相性がいい
- **受付と完了を分ける**: 時間が読めない・分を超える処理はこちら。「失敗」と「まだ」をエラーコードの完全一致で区別し、再試行は同一コード限定・回数固定にする
- **クライアントのタスク化に任せる**: 人が見ている対話セッションから。無人経路では、結果回収の監査を用意できてから解放する

順番に意図があります。下に行くほど体験は良くなり、同時に「結果が届かなかったこと」を検出する仕組みを自前で持つ必要が増えます。待ち方の自由度は、回収の責任とセットです。

MCPサーバー側の実装自体は、過去に自作の構成をまとめているので、これから作る方はそちらが入口になるはずです。

クライアントが賢く待ってくれる時代になっても、「このツールが返ったとき、結果はどこに在るのか」を言い切れることが設計の土台だと思います。タイムアウトの秒数をいじる前に、まず誰が待つかから。
