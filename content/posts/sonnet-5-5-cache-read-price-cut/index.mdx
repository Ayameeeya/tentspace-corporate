2026年10月7日、Claude Sonnet 5.5のキャッシュ読み取り（cache read）単価が半額になりました。100万トークンあたり$0.20から$0.10へ。ただし、請求の総額が半分になるわけではありません。値下げされたのは読み取りだけで、入力・出力・キャッシュ書き込みの料率は据え置き。総額がどれだけ下がるかは「請求のうちcache readが何割を占めているか」で決まります。第三者の実測では、20ターンの連続会話で下げ幅は20.0%でした。

この記事では、改定の中身、実測が示す下げ幅の構造、そして自分の構成で効き幅を見積もる手順を整理します。対象読者は、Claude APIやAmazon BedrockでSonnet 5.5を使っている開発者と、Claude Codeを定時実行や長時間セッションで運用している人です。プロンプトキャッシュの仕組みそのもの（プレフィックス一致、読みと書きの非対称）は[入門記事](/blog/what-is-prompt-caching)に書いたので、ここでは改定の読み方に絞ります。

## 何が変わったか：読み取りだけが半額、ほかは据え置き

まず事実の整理から。確認できている改定点は1つだけです。

| 項目 | 改定前 | 改定後 |
| --- | --- | --- |
| cache read | $0.20 / MTok | **$0.10 / MTok** |
| 入力（通常） | $2.00 / MTok | 据え置き |
| 出力 | $10.00 / MTok | 据え置き |
| cache write（5分TTL） | $2.50 / MTok | 据え置き |
| cache write（1時間TTL） | $4.00 / MTok | 据え置き |

Amazon Bedrockでは2026年10月7日適用で、Globalおよびus-east-1が$0.20→$0.10、Geoリージョンが$0.22→$0.11と確認されています（出典は次節の実測記事）。

Claude Code側もこの改定に追随しています。公式changelogによると、2.1.296（2026-10-09）で `/cost`・ステータスライン・`--max-budget-usd`・SDKのコスト表示が、Sonnet 5.5のcache readを$0.10/MTokとして計算するよう更新されました。観測側の注意点は後の節でまとめます。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code公式changelog（2.1.296でcache read単価の計上を更新）" />

ちなみに、[プロンプトキャッシュ入門](/blog/what-is-prompt-caching)では「読みは基準の0.1倍」という目安を書きました。この改定で、Sonnet 5.5に限ってはその目安が0.05倍になっています。目安の数字は、こうやって静かに動きます。

## 実測が示す構造：cache readが40%なら、半額で総額20%減

「半額」という率と、実際の請求がどう結びつくか。クラスメソッドの検証記事（2026-10-09公開）が、Bedrock上のSonnet 5.5で改定前後の総額を実測しています。

<LinkCard url="https://dev.classmethod.jp/articles/bedrock-sonnet-5-5-cache-read-price-cut/" title="Claude Sonnet 5.5 で cache read 価格が半額に改定、値下げ効果を実測してみた（DevelopersIO）" />

条件は、約16,400トークンの固定システムプロンプトに短い日本語の質問を20件、Converse APIで連続送信（maxTokens=300）というもの。累計トークンは出力5,302、cache read 350,380、cache write 20,681でした。結果の総額はこうです。

- 改定前の料率で計算: **$0.1750**
- 改定後の料率で計算: **$0.1399**（−$0.0350、**20.0%減**）

半額になったのに2割しか下がらない。種明かしは内訳です。このシナリオでは、値下げ前の総額のうちcache readが約40%を占めていました。その40%が半分になったので、全体では約20%下がる。それだけの算数です。

一般化すると、**総額の下げ幅 ≒ cache readの金額比率 × 50%**。比率が40%の構成なら20%下がり、10%しかない構成なら5%しか下がりません。長い固定プロンプトを高頻度で使い回すエージェント用途ほど比率が高く、値下げがよく効く。逆に、毎回内容が変わる単発の処理ではほとんど効きません。

同記事には参考値として、同条件のSonnet 5が$0.1787という計測も載っています。改定後のSonnet 5.5（$0.1399）は、この形の処理なら前世代より安い。「新しいモデルは高い」という感覚も、キャッシュの料率1つで逆転します。

なお、この実測はus-east-1のGlobalエンドポイント・1シナリオのみで、記事自身も「多くのagenticタスクで約20%」という見立ては独立検証されていないと明記しています。20%という数字をそのまま自分の構成に当てはめるのではなく、「比率×50%」の式のほうを持ち帰るのが正しい読み方です。

## 見出しは半額、でも損益分岐はほぼ動かない

今回の改定でいちばん面白いのは、ここだと思っています。

同じ実測の1ターン目を見ると、キャッシュ有りが$0.0433、キャッシュ無しが$0.0354。**キャッシュを使ったほうが高い**。初回はキャッシュ書き込みの割増（5分TTLで通常入力の1.25倍）を先払いするためで、この構造は値下げ後も変わっていません。書き込み側の料率が据え置きだからです。

据え置きの料率から、元を取る条件を計算してみます。100万トークンあたりで、キャッシュ読み1回の節約額は「通常入力$2.00 − cache read単価」。改定前は$1.80、改定後は$1.90です。一方、先払いする書き込み割増は5分TTLで+$0.50、1時間TTLで+$2.00のまま。

- 5分TTL: 割増$0.50に対して節約$1.90。**再利用1回**で元が取れる（改定前も1回）
- 1時間TTL: 割増$2.00に対して節約$1.90。1回では足りず、**再利用2回**で元が取れる（改定前も2回）

つまり、損益分岐に必要な再利用回数は改定前後で変わりません。「この処理にキャッシュを効かせるべきか」という採否の判断は、今回の値下げでは動かない。動いたのは、採用済みの構成で回し続けたときの総額だけです。

だから、1回で終わる短い実行に1時間TTLのキャッシュを効かせない、実行間隔がTTLより長い定時処理では書き込み割増が掛け捨てになる、といった従来の判断はそのまま使えます。値下げのニュースを見て「とりあえず全部キャッシュに乗せよう」と動くのは、方向としては逆です。

20ターン続けた累計では、キャッシュ有り$0.1399に対して無しは$0.7950。約82%安くなっています。ターンが進むほど差は開く。キャッシュが効く形の処理では圧倒的に得で、効かない形では初回の割増だけ払う。この非対称も改定前と同じです。

## 自分の構成で効き幅を見積もる3ステップ

値下げが自分の請求にどれだけ効くかは、次の順で出せます。

**1. 内訳を出す。** APIレスポンスのusageにはキャッシュ読み取りと書き込みのトークン数が別々に返ってきます。それぞれに単価を掛ければ、総額に占めるcache readの金額比率が出ます。Claude Codeなら`/cost`のキャッシュ行で確認できます（前述のとおり、新単価での計上は2.1.296以降）。

**2. 比率×50%が下げ幅。** たとえば月$100の請求でcache readが$40を占めていたなら、改定後は$20下がって$80になる計算です。cache readが$10しかない構成なら、下がるのは$5だけ。同じ「半額」のニュースでも、構成によって効きは4倍違います。ここで出た数字が、予算やクライアントへの見積もりを引き直すときの根拠になります。

**3. 下げた見積もりを上限として固定しない。** 単価は今回のように動きますし、計上する側（ツールのバージョン、ゲートウェイの集計）も更新で挙動が変わります。そして総額を単価より大きく動かすのはヒット率のほうです。会話の途中でツール一覧が変わるとキャッシュが切れる、といった構成起因のミスは[別記事](/blog/claude-code-cache-miss-tool-changes)に書いたとおりで、ヒット率が崩れた状態では単価が半分になっても請求は下がりません。見積もりは一度引いて終わりではなく、内訳の実測で更新し続けるものとして扱うのが安全です。

## Claude Codeの表示で観測している場合の注意

コストの内訳をClaude Codeの表示で見ている運用では、改定とほぼ同時期に観測側も動いているので、3点だけ確認しておくと混乱しません。いずれも公式changelogに記載されている変更です。

**表示のバージョン。** 新単価での計上は2.1.296（2026-10-09）からです。それより前のバージョンの`/cost`やステータスラインは、Sonnet 5.5のcache readを旧単価の$0.20で計算しています。改定前後の数字を比べるなら、どちらの料率で数えた表示かを先に揃える必要があります。

**計測経路の変更。** 1つ前の2.1.295（2026-10-08）では、Amazon Bedrockのゲートウェイ配下でのトークン計測が、1トークンのモデルリクエストを投げる方式からAWSのCountTokens APIを使う方式へ変わりました。`/context`や大きなファイル読み取りがこの計測を使い、利用には`bedrock:CountTokens`の権限付与が必要です。計器の数字の出どころ自体が変わっているので、この前後をまたいだ比較は同条件になりません。

**内訳に混ざる別モデル。** 同じ2.1.295で、ゲートウェイ配下の背景リクエストはセッションのモデルではなくHaiku 4.5を使うようになりました（ゲートウェイがHaiku 4.5を出さない構成ではセッションのモデルへフォールバック）。請求の内訳にはSonnet 5.5以外の行が混ざるのが正常で、「比率×50%」の式を当てるのはSonnet 5.5のcache read行だけです。

単価の改定、計上料率の更新、計測経路の変更、モデルの振り分け。この4つが2026年10月の1週間に集中して動いています。表示される数字を鵜呑みにせず、どのバージョンの、どの経路の計測かをセットで記録しておくのが、この時期の再見積もりでは特に効きます。

## 値下げ後も変わらない設計原則

最後に、改定で変わらなかった条件を並べておきます。キャッシュが効く前提は従来どおりです。

- **プレフィックスの完全一致**。送信内容の先頭から前回と一致している部分だけが再利用されます。先頭に可変の値を置けば、その後ろは全部ミスになります
- **最低キャッシュ単位**。Sonnet 5.5では512トークンが下限です。指示を細かいファイルに分割しすぎると、個々の断片がキャッシュに乗らない方向へ働きます
- **TTL内の再利用**。5分または1時間のTTL内に次の読みが来なければ、書き込み割増は掛け捨てです

読みの単価が下がったことで「キャッシュに乗せる価値」自体は上がりました。ただ、乗せ方の設計は何も変わっていません。Claude Codeの運用でキャッシュを切らさないための具体的な設計判断は[プロンプトキャッシュ入門（Claude Code編）](/blog/claude-code-prompt-cache)にまとめています。

価格改定のニュースは「半額」という率で流れてきます。でも財布に効くのは率ではなく、内訳×率。見積もりの基準線を引き直すなら、最初に見るのは単価表ではなく、自分の請求の内訳です。
