Claude Codeの「メモリ」は、会話をまたいで自動で学習してくれる機能ではありません。実体は、セッション開始時にコンテキストへ読み込まれる**CLAUDE.mdというMarkdownファイル**です。そして置き場所が3階層あり、どこに置くかで「誰に、どのプロジェクトで効くか」が決まります。

つまりメモリの設計とは、文章術ではなくファイル配置の設計です。この記事では、CLAUDE.mdの読み込み階層と範囲、`@`インポートによる分割、`#`での素早い追記という仕組みの全体像を公式ドキュメントベースで整理し、最後に「書いたのに守られない」ときにメモリの外へ逃がす判断までまとめます。

## メモリの正体は、起動時に読み込まれるファイル

Claude Codeは起動時に、所定の場所にあるCLAUDE.mdを探して読み込み、以後そのセッションのコンテキストの一部として扱います。コーディング規約、よく使うコマンド、プロジェクトの構成説明など、毎回伝え直したくない情報をここに書いておくのが基本の使い方です。

<LinkCard url="https://docs.claude.com/en/docs/claude-code/memory" title="Claude Code公式: Manage Claude's memory" />

押さえておきたいのは、メモリがチャット履歴と独立している点です。

- 会話で伝えた好みや指示は、ファイルに書かない限り次のセッションへ持ち越されません。`/clear`で区切れば消えます。
- 逆にCLAUDE.mdに書いた内容は、`/clear`しても新しいセッションでも、毎回読み込まれます。

「さっき言ったのに忘れた」の多くは、メモリに入れたつもりで会話にしか存在しなかったケースです。残したいものはファイルへ。これが出発点になります。

## 置き場所は3階層。どこに置くかで効く範囲が決まる

CLAUDE.mdには複数の置き場所があり、公式ドキュメントでは階層として整理されています。上位のファイルほど先に読み込まれ、優先されます。

- **エンタープライズポリシー**: 組織の管理者が配布する全ユーザー共通の指示。macOSでは`/Library/Application Support/ClaudeCode/CLAUDE.md`、LinuxやWSLでは`/etc/claude-code/CLAUDE.md`に置きます。
- **プロジェクトメモリ**: リポジトリ直下の`./CLAUDE.md`。gitにコミットして、チーム全員とそのリポジトリで動くエージェントに効かせます。
- **ユーザーメモリ**: `~/.claude/CLAUDE.md`。すべてのプロジェクトで、自分にだけ効きます。

以前は「プロジェクト内・自分専用」の`CLAUDE.local.md`もありましたが、現在は非推奨で、後述するインポートでの代替が案内されています。

この3階層は、効く範囲がそのまま使い分けの基準になります。チームで共有したい規約はプロジェクトへ、自分のエディタや口調の好みはユーザーへ、組織として外せないルールはエンタープライズへ。「どう書くか」より先に「どこへ書くか」を決める方が、後で迷いません。

## 読み込み範囲はカレントディレクトリだけではない

見落としやすいのが読み込みの範囲です。Claude Codeは起動したディレクトリのCLAUDE.mdだけを読むわけではありません。

- 起動ディレクトリから**親ディレクトリをルート直前まで遡り**、途中にあるCLAUDE.mdをすべて読み込みます。モノレポで`repo/apps/web`から起動すると、`repo/CLAUDE.md`と`repo/apps/web/CLAUDE.md`の両方が載る、ということです。
- 逆に**サブディレクトリのCLAUDE.mdは起動時には読まれず**、そのサブツリーのファイルをClaudeが触ったときに読み込まれます。

モノレポなら、リポジトリ直下に全体の規約、各パッケージ直下にそのパッケージ固有の注意を置く構成が素直です。全体用のファイルに全パッケージの事情を詰め込む必要はありません。

いま何が読み込まれているかは`/memory`で確認できます。「書いたはずの指示が効かない」ときは、まずここで対象ファイルが一覧に出ているかを見るのが早道です。

## @インポートで分割する。1枚岩のCLAUDE.mdをやめる

CLAUDE.mdは`@パス`の記法で他のファイルを取り込めます。

```markdown
プロジェクトの概要は @README.md を参照。

# 追加の指示
- git のワークフローは @docs/git-instructions.md に従う
- 個人の好み: @~/.claude/my-project-instructions.md
```

仕様のポイントは3つです。

- 相対パスと絶対パスの両方を使え、ホームディレクトリ配下のファイルも取り込めます。リポジトリにコミットしたくない個人用の指示を混ぜる手段として、公式が`CLAUDE.local.md`の代替に挙げているのがこの形です。
- インポートは再帰的に解決され、**深さは最大5ホップ**までです。
- コードスパンやコードブロックの中にある`@`は評価されません。`@anthropic-ai/claude-code`のようなパッケージ名が誤ってインポート扱いされない、ということです。

私の運用リポジトリでは、この仕組みを使ってCLAUDE.mdを`@AGENTS.md`の1行だけにし、指示の実体をAGENTS.mdへ一本化しています。複数のエージェントCLIを併用しても指示書が分裂しない構成で、その経緯と中身は別記事に書きました。

## 覚えさせる操作は3つ。#、/memory、/init

ファイルを直接編集する以外に、Claude Codeには覚えさせるための操作が用意されています。

- **`#`で始めて入力する**: 入力欄の先頭に`#`を付けて指示を書くと、どのメモリファイルに保存するかを選ぶプロンプトが出ます。作業中に「これは毎回言いたくない」と気づいた瞬間に、その場で追記できる最短ルートです。
- **`/memory`**: 読み込まれているメモリファイルを一覧し、エディタで開いて編集できます。まとまった整理や削除はこちらで行います。
- **`/init`**: コードベースを調べてCLAUDE.mdの雛形を生成します。ゼロから書き始めるより、生成されたものを削る方が早いです。

書き方は公式ドキュメントの推奨がそのまま実用的です。1項目を具体的な箇条書きにする（「コードをフォーマットする」ではなく「2スペースインデントを使う」）、関連する項目は見出しでグループ化する。曖昧な一般論は読み込まれても効きません。

形にすると、たとえばこの程度の素っ気なさで十分です。

```markdown
# ビルドとテスト
- 検証一式: npm run check（typecheck + lint を含む）
- テストは変更したパッケージだけ実行する

# コーディング規約
- インデントは2スペース
- 型は明示する。any を新規に書かない

# このリポジトリの注意
- content/ 配下は生成物を含むため直接編集しない
```

散文で丁寧に説明するより、コマンドと規則を言い切りで並べる方が読み込まれたときに効きます。人間向けのREADMEと役割が違う、と考えると書き分けやすいです。

## settings.jsonとの境界。設定は機械が読み、メモリはモデルが読む

CLAUDE.mdと混同しやすいのが`settings.json`です。どちらも「Claude Codeの挙動を変えるファイル」ですが、読む主体が違います。

- **settings.json**は、Claude Code本体が機械的に解釈する設定です。ツールの許可・拒否ルール、環境変数、hooksの登録など。書いたとおりに、確実に適用されます。
- **CLAUDE.md**は、モデルがプロンプトとして読む指示です。従うかどうかは最終的にモデルの解釈に委ねられます。

だから「このコマンドは必ず止めたい」をCLAUDE.mdに書くのは筋が悪く、settings.jsonの拒否ルールかhooksに書くべきです。逆に「コミットメッセージは日本語で」のようなニュアンスを含む指示はsettings.jsonでは表現できず、メモリの出番になります。settings.jsonの置き場所と優先順位は[別記事](/blog/claude-code-settings-json)で整理しているので、権限まわりを固めたい場合はそちらをどうぞ。

## メモリに書かないものを先に決める

運用を続けると、CLAUDE.mdには「書かない」判断の方が効いてきます。私が線を引いているのは次の3つです。

- **シークレット・認証情報**: プロジェクトメモリはリポジトリにコミットされ、さらに毎セッションのコンテキストに載ります。トークンやAPIキーを書くと、履歴とログの両方に残り続けます。値は環境変数やシークレットストアに置き、メモリには「どこにあるか」だけを書きます。
- **長大なドキュメントの全文**: `@`インポートは便利ですが、取り込んだ内容は毎回コンテキストに載ります。たまにしか参照しない仕様書は、`@`を付けずにパスだけ書いておけば、Claudeが必要になったときに自分で読みます。常時必要かどうかで`@`の有無を分けるのが目安です。
- **会話の下書きや一時メモ**: その場の作業メモは`/clear`で消える会話に置けば十分です。メモリに入れると、関係ない次のタスクにも毎回付いてきます。

## 読み込まれることと、守られることは別問題

ここまでが仕組みの話ですが、運用してみると気づくことがあります。メモリに書けば解決、ではないのです。

CLAUDE.mdの中身はあくまでプロンプトの一部で、強制力はありません。モデルの指示追従は確率的で、一定の割合で読み飛ばしや解釈違いが起きます。しかも項目を書き足すほどコンテキストに占める指示が長くなり、1行あたりの重みはむしろ下がっていきます。「守られないから書き足す」を繰り返すと、悪化する方向に進むわけです。

私はSNSとブログの運用パイプラインをClaude Codeの無人実行で回していて、この性質を前提に置き場所を3つに分けています。

- **事実・構成・好みの説明** → メモリ（CLAUDE.md / AGENTS.md）。守られなくても壊れない情報。
- **繰り返す作業手順** → スキルやスラッシュコマンド。必要なときだけ読み込ませる。
- **破られたら戻れない禁止事項** → [hooksでコードとして強制](/blog/claude-code-hooks-bash-guard)。mainへの直接pushのような一線は、メモリに書くのではなく実行時にブロックします。

「覚えさせたのに守らない」と感じたら、書き方を磨く前に、その指示がメモリに置くべきものかを疑う。これが運用して一番効いた判断でした。

## メモリは毎セッション、コンテキストを先に消費する

もうひとつ運用側の注意です。読み込まれたメモリは、毎セッションの先頭でコンテキストウィンドウを消費します。CLAUDE.mdが肥大化するほど、本来の作業に使える残り容量が最初から削られるということです。

どのくらい占めているかは`/context`で確認できます。読み込みの内訳と、肥大化したときの整理の考え方は別記事にまとめました。

<LinkCard slug="claude-code-context-management" />

定時実行や無人運用では、この消費が毎回発生する固定費になります。読む人間がいない分、「とりあえず書いておく」が積もりやすいので、`/memory`での棚卸しを定期的に入れるのが現実的です。

## まとめ: 置き場所の決め方

メモリの設計は、次の順で決めると迷いません。

- このリポジトリでチーム全員に効かせたい → `./CLAUDE.md`（コミットする）
- 全プロジェクトで自分にだけ効かせたい → `~/.claude/CLAUDE.md`
- このリポジトリで自分にだけ効かせたい → ホーム側のファイルを`@`インポート
- 組織として全員に配布したい → エンタープライズポリシー
- 破られたら困る禁止事項 → メモリではなくhooksへ

最初の1枚は`/init`で生成し、日々の運用では気づいた瞬間に`#`で追記、月に一度`/memory`で棚卸し。このサイクルに乗せると、CLAUDE.mdは「書いて終わりの設定ファイル」ではなく、プロジェクトと一緒に育つドキュメントになります。
