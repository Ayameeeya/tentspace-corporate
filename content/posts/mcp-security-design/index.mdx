MCP（Model Context Protocol）のセキュリティ設計で最初に決めるべきは、承認ゲートの見た目ではなく**「断る判定を、誰にも書き換えられない場所に置けているか」**です。先に結論を言うと、ツール側の自己申告——説明文、分類、「読み取り専用」のようなヒント——を材料にした承認は、申告が嘘になった瞬間に消えます。守りの本体はクライアントの承認UIではなく、呼び出される側のサーバー実装が「何を断るか」に置く。この整理を、承認ゲートが実際に素通りした外部の実測と、無人運用している自作MCPサーバーの構成で説明します。

対象読者は、MCPサーバーを自作して運用に載せようとしているエンジニアと、チームや組織でMCP接続の許可方針を決める立場の人です。サーバーの構築自体は以前の実装記事にまとめてあるので、この記事は「作った後、何で守るか」に絞ります。

## 承認ゲートは何を材料に発火しているか

MCP対応のエージェント基盤には、危険な操作の前に確認を挟む承認ゲートが用意されていることが多いです。書き込み系のツールを呼ぶ前に人間へ確認する、あるいはエージェント自身が「これは状態を変える操作だ」と判断して踏みとどまる。設計としては真っ当に見えます。

問題は、そのゲートが**何を材料に「危険」を判定しているか**です。ホストから見えるツールの情報は、ツール名、説明文、入力スキーマ、そして「読み取り専用か」「状態を変えるか」といった分類やヒント。これらはすべて、ツールを提供する側が書くメタデータです。つまり構図として、**審査される側が、審査の判定材料を自分で書いている**。この構図のまま承認ゲートを建てると何が起きるかを、実測で示した検証があります。

## 自己申告を偽装したら、承認なしで値が書き換わった

クラスメソッドの検証記事（2026-09-23公開、確認日2026-09-25）が、AWS DevOps Agentに自作のMCPツールを登録し、承認ゲートの効き方を3つのケースで実測しています。

<LinkCard url="https://dev.classmethod.jp/articles/aws-devops-agent-custom-mcp-tool-classification-bypass/" title="クラスメソッド: 自作MCPツールの分類申告と承認ゲートの実測" />

- **ケース1**: 状態を変更するツールを、正直に `toolClassification: MUTATIVE`（状態変更）で登録。エージェント側が実行を自己拒否した
- **ケース2**: 説明文だけ「読み取り専用の診断ツール」と偽装し、分類は正直にMUTATIVEのまま。プラットフォームがブロックした
- **ケース3**: 説明文も分類も偽装し、`READ_ONLY` として登録。**承認なしで実行され、Parameter Store（AWSの設定値ストア）の値が初期値からタイムスタンプへ実際に書き換わった**

出典の結論はこうです。効いていたゲートは説明文の審査ではなく、ツール側が申告した分類そのもの。**申告が嘘なら、承認は要求されない。**

これはこのプラットフォーム固有の欠陥というより、自己申告を境界に使う設計の限界が数字で出たものだと読んでいます。正直に申告する行儀のよいツールに対しては、ケース1・2のとおりゲートはきちんと機能します。ただ、セキュリティ境界が想定すべき相手は行儀のよいツールではありません。悪意あるサーバー、あるいは侵害されて中身がすり替わったサーバーは、正直に申告しません。説明文・分類・「読み取り専用」ヒントのように、ツール提供側が書けるメタデータを権限判断の入力に使う設計は、どの実装でも同じ形の穴になり得るはずです——ここは一般化した推測で、個別のホスト実装ごとの検証はしていません。

## 承認ゲートが無駄なのではなく、守っている相手が違う

ここで「では承認ゲートは無意味か」と振れるのは早計で、実測を眺めていて整理が変わったのはむしろ逆の方向でした。**承認や確認の仕組みには価値がある。ただしそれは協力的な相手に対する層であって、セキュリティ境界ではない。**この2つは守っている相手が違います。

- **確認・承認のUI**: 誤操作を止め、意図を確認する。相手は「正直だがミスをする」利用者やモデル
- **セキュリティ境界**: 嘘をつく相手を前提に、実行そのものを不能にする。相手は「判定材料ごと偽装してくる」ツールや呼び出し

承認ダイアログが出ることに安心して、この2層を混ぜてしまうと、ケース3の形で抜かれます。では嘘をつく相手にも効く層はどこに置けるのか。答えは呼び出される側、つまり**サーバー実装**です。サーバーのコードは、ツールの利用者側——モデルにもクライアントにも——書き換えられません。自己申告と違って、判定材料と判定の実行が両方とも相手の手の届かない場所にあります。

## 自作サーバーでは「断る側」を4層で置いた

私はSNS公開用の自作MCPサーバーをCloudflare Workersで無人運用しています。公開・削除のような後戻りしにくいツールを含むので、「断る側」はすべてサーバー実装に置きました。層は4つです。

1. **入力スキーマ**: 引数の型・必須・上限をツール定義で宣言し、外れた呼び出しはツールのロジックに到達する前に拒否します
2. **Bearer認証**: そもそも誰が呼べるかを全ツール処理の最前段で判定します。検証をタイミングセーフにする話や、資格情報の置き場所の設計は認証ガイドに書きました
3. **confirm必須**: 公開・削除など副作用の大きいツールは、`confirm=true` を明示しない呼び出しを実行しません
4. **回数上限**: 公開系ツールは、時間窓と日次のカウンタをWorkerのKVで持ち、上限を超えた呼び出しをサーバーが断ります

<LinkCard slug="mcp-server-auth-guide" />

ここで正直に書いておきたいのは、3の `confirm` の位置づけです。confirmはモデルが付ければ通ります。人間の承認ではありません。それでも置いているのは、「暗黙のうちに副作用が起きる」経路を消し、呼び出しの明示性を強制するためで、役割としては先ほどの分類でいう**協力的な相手への層**です。一方で1・2・4は、呼び出し側がどれだけ申告や引数を工夫しても、サーバーが実行しないという**嘘をつく相手にも効く層**。とくに4の回数上限は実質の境界で、承認をすべてすり抜けられたとしても、過剰な公開の被害はカウンタが切ります。実装の詳細（単純なカウントではなく予約と確定を分けた二段階にした理由）は[回数制限の実装記録](/blog/mcp-server-publish-rate-limit)にまとめています。

もう1つ、運用で効いているのは**断る側の挙動をテストで固定する**ことです。confirmなしの呼び出しが拒否されること、上限を超えた公開をサーバーが断ること。この2つはプロトコルが保証してくれる性質ではなく自分の実装の性質なので、リファクタリングで静かに緩む可能性があります。自作入門で書いたとおり、ツールの表面——定義と拒否の挙動——を固定するテストを置いて、断る側が痩せたらCIで気づける形にしています。境界を作ることと、境界が維持されていることを数えることは、別の仕事です。

安全性の見積もりは、嘘をつく相手にも効く層だけで行う。confirmや承認UIは体験をよくする層として数え、境界の頭数には入れない。この仕分けが、今回の実測から持ち帰った一番の設計判断です。

## 第3の置き場所——サーバーを直せない立場のゲートウェイ層

ここまでは「サーバー実装を自分で書ける」前提の話です。ただ実際の組織では、他社製のMCPサーバーを寄せ集めて使う場面のほうが多く、個々のサーバーに断る層を足すことはできません。その場合、断る側と数える側をサーバーとクライアントの**間**に挟むしかない。この受け皿がちょうど製品化されています。

CloudflareのMCP server portals（2026-09-24 GA発表、確認日2026-09-28）は、承認済みのMCPサーバー群を1つのエンドポイントへ集約し、tool・prompt・resourceの利用をCloudflare Accessが記録、HTTPログとDLP（機密情報の漏えい検査）のスキャンを通します。認証はOAuthに加えて自律エージェント・M2M（システム間連携）向けのサービストークンに対応し、ポータル側からサーバーの再接続や権限変更ができ、Logpushで活動ログを外部のストレージやSIEMへ出せます。

<LinkCard url="https://developers.cloudflare.com/changelog/post/2026-09-24-mcp-portals-ga/" title="Cloudflare Changelog: MCP server portals GA" />

あわせてCode Modeポリシーで、ポータルがツール定義をどこまで削って見せるかを制御でき、トークン使用量の削減とツール表面の露出制御を同じ場所で扱えます（削減幅などの具体値は発表に記載がありません）。ツールが増えるほどコストは呼び出し回数より定義の常駐分で増えていくので、境界とコストの管理点が同じ層に揃うのは筋がよい設計だと見ています。

私自身は現時点で使いません。自作サーバー側に断る層を固めてあり、その境界を外側のポータルへ移す利得がないためです。ただ、実装を直せないサーバーを束ねて組織に配る立場なら、評価する価値があるはずです。判断軸は同じで、「断る判定が、ツールの自己申告ではなくゲートウェイの設定として、利用者の手の届かない場所で実行されるか」。この観点では、ポータルは境界を置ける第3の場所になります。

## 承認設計を棚卸しする3つの質問

最後に、この記事の整理を自分の構成に当てるための質問を3つにまとめます。

1. **その承認ゲートが読んでいる入力は、誰が書けるか。** 審査される側（ツール提供者）が書けるメタデータなら、それは境界ではありません
2. **断る判定は、どの層の実装で実行されるか。** 利用者側から書き換えられないサーバー実装またはゲートウェイ設定で実行されているかを確認します
3. **申告が全部嘘でも、被害はどこで止まるか。** 認証・入力スキーマ・回数上限といった、嘘に影響されない層だけで被害範囲を見積もります

MCPはツールを繋ぐことを簡単にしましたが、その分「繋いだものが嘘をつく」ケースの設計が後回しになりがちです。承認ダイアログの数ではなく、断る側の置き場所で安全性を数える。自作サーバーを運用に載せる前に、この3問だけ通しておくと、承認ゲートに預けすぎない構成になるはずです。構築から始める場合は[自作入門](/blog/mcp-server-cloudflare-workers)、資格情報の扱いは[認証ガイド](/blog/mcp-server-auth-guide)が続きの1本になります。
