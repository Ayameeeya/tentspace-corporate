AIエージェントの本体は、驚くほど小さいです。「モデルがツールを呼び、結果を見て次の行動を自分で決めるループ」。これだけ。だから作り方の勘所は、フレームワークをどれにするかではなく、ツールの設計と止め方の設計にあります。

この記事では、エージェントを構成する最小の4要素（モデル・ツール・ループ・停止条件）と作る順番を整理します。SNS運用を丸ごとエージェントに任せている自分の運用経験から、「動かし始めると工数がどこへ移るか」も先にお伝えします。

## まず「エージェント」と「ワークフロー」を区別する

作り始める前に、1つだけ決めることがあります。いま作ろうとしているものは、本当にエージェントなのか。

Anthropicが2024年12月に公開した「Building effective agents」は、この2つをはっきり分けています。ワークフローは、LLMとツールをあらかじめ決めたコードの経路で組み合わせるもの。エージェントは、LLMが自分の処理手順とツールの使い方を動的に決めるものです。

<LinkCard url="https://www.anthropic.com/engineering/building-effective-agents" title="Anthropic: Building effective agents" />

この区別が最初に来る理由は単純で、手順が事前に決められるタスクなら、ワークフローのほうが安く、速く、予測可能だからです。同ガイドも「できる限りシンプルな解を探し、必要なときだけ複雑さを足す」ことを繰り返し勧めています。

目安はこうです。

- 入力が来たら要約して保存する、毎朝データを集計して通知する → 手順が固定。ワークフローで足ります
- 「このバグを直して」「この調査をまとめて」→ 何手かかるか、どのツールを何回使うかが事前に決まらない。エージェントの出番です

私の運用でも両方を使い分けています。毎日決まった時刻に決まった集計をする部分はほぼワークフロー、記事の執筆や調査のように手数が読めない部分だけがエージェントです。

## 最小のエージェントループを書いてみる

エージェントの中身を知る一番の近道は、フレームワークなしで一度ループを書いてみることです。Claude APIのツール使用（tool use）を使うと、骨格はこれだけになります。

```typescript
const messages = [{ role: "user", content: task }];
let turns = 0;

while (turns < MAX_TURNS) {
  const res = await client.messages.create({ model, messages, tools });

  // モデルがツールを要求しなければ、タスク完了と判断して抜ける
  if (res.stop_reason !== "tool_use") break;

  // 要求されたツールを実行し、結果を会話に積んで次のターンへ
  messages.push({ role: "assistant", content: res.content });
  messages.push({ role: "user", content: await runTools(res.content) });
  turns++;
}
```

ここに魔法はありません。登場しているのは4つだけです。

1. **モデル**: 次に何をするかを毎ターン判断する頭脳
2. **ツール**: モデルが外の世界に触る手足。検索、ファイル操作、API呼び出し
3. **ループ**: ツールの実行結果をモデルに返し、次の判断をさせる繰り返し
4. **停止条件**: モデル自身の「完了」判断と、外側から強制する上限

フレームワークが提供しているのは、この骨格の周りの便利さ（会話履歴の管理、リトライ、並列化、観測）であって、骨格そのものではない。これを一度手で書いて知っておくと、後でフレームワークを選ぶときに「何を肩代わりしてほしいのか」を具体的に言えるようになります。

### ループはコンテキストを毎ターン積み増す

コードを見ると分かるとおり、ツールの実行結果は毎ターン `messages` に追記され、次の呼び出しで全部まとめて送り直されます。つまりエージェントのAPIコストはターン数に比例ではなく、累積で増えます。10ターン目のモデル呼び出しは、それまでの9ターン分の履歴を全部抱えて走ります。

ここで2つの設計が効いてきます。

- **ツール結果を小さく返す**: 検索結果を丸ごと返すのではなく、次の判断に必要な部分だけに絞る。次節で触れる「応答の情報密度」は、品質だけでなくコスト対策でもあります
- **プロンプトキャッシュを切らさない**: 会話の前半が毎回同じなら、キャッシュが効いた部分は大幅に安くなり、実質的に差分中心の課金になります。逆に、途中でツール定義を差し替えるとキャッシュが無効になり、静かにコストが跳ねます

このコスト構造は、作る前に知っておくと設計が変わるところです。キャッシュが切れる条件の詳細は[プロンプトキャッシュの記事](/blog/claude-code-prompt-cache)にまとめています。

## ツールの設計がエージェントの実質のUIになる

4要素のうち、品質への効きが一番大きいのはツールです。

エージェントは画面を見ません。ツールの名前、説明文、入力スキーマだけを頼りに世界を認識します。つまりツール定義は、人間にとってのUIに相当します。説明文が曖昧なツールは、ボタンにラベルのない画面と同じです。

Anthropicが2025年9月に公開した「Writing effective tools for agents」も、ツールは数を絞って目的特化にすること、応答には次の判断に必要な情報だけを高密度で返すこと、そして「良さそう」ではなく評価タスクで測って改善することを勧めています。出典はこちらです: [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)。

実運用でもう1つ効いたのは、**禁止事項をプロンプトではなくツール実装の側に置く**ことでした。私はSNS運用を自作のMCPサーバー経由でエージェントに任せていますが、投稿のような取り返しのつかない操作には確認フラグを必須にし、公開回数の上限はサーバー側で数えて超過を拒否しています。「投稿しすぎないでね」とプロンプトに書くのではなく、ツールが断る。この設計の詳細は別記事にまとめています。

## 難所はループではなく「止め方」だった

ここが、作る前の予想と一番違ったところです。

着手前は、エージェントループそのものが難所に見えていました。実際には、骨格のループは半日で動きます。そこから先の工数は、ほぼすべて「止め方」と「観測」に移りました。

停止条件は、最低でも次の4種類を別物として設計します。

- **ターン上限**: ループの回数そのものの上限。暴走の最後の砦
- **予算上限**: トークン・API費・実行時間。回数は少なくても1ターンが重い場合を止める
- **失敗の止め方**: リトライは何回まで許すか。私の運用では、公開前審査に2回落ちた原稿は自動修正を打ち切って隔離し、Routine全体は止めずに先へ進める設計にしています
- **人間へのエスカレーション**: 判断材料が足りないとき、無理に進めず止まって引き継ぐ経路

既製のエージェントも同じ構造を持っています。たとえばClaude Codeを非対話で動かす `claude -p` には `--max-turns` という上限フラグがあり、自動化に組み込むときはこれが暴走と費用の上限設計になります。詳しくは[ヘッドレスモードの記事](/blog/claude-code-headless-mode)に書きました。

逆に言うと、停止条件を後回しにしたエージェントは、本番で初めて「止まらない」「静かに失敗し続ける」という形で問題を教えてくれます。ループより先に、止め方を書く。順番はこちらが安全です。

## 観測と評価は後付けにしない

止め方と並ぶもう1つの工数の行き先が観測です。

エージェントは同じ入力でも毎回同じ手順を踏みません。だから「何を実行したか」だけでなく「なぜそう判断したか」が追える形でログを残さないと、失敗したときに直す場所が分かりません。最低限、各ターンのツール呼び出しと引数、そしてタスクの成功を数える定義（何をもって完了とするか）を最初に決めておきます。

さらに運用を続けると、成果物のレビューだけでは捕まらない劣化があることに気づきます。出力は全部PASSしているのに、指示した運用ルールが守られていない、という回帰です。これを数えるのがハーネス評価の役割で、別記事で実例と設計をまとめています。

人間の関与のさせ方も観測の一部です。すべての操作に承認ボタンを置くと、人間が形式的に押すだけの装置になって機能しません。どこを自動で進め、どこで止めるかは[ヒューマンインザループ設計の記事](/blog/ai-agent-human-in-the-loop)で整理しています。

## フレームワークとSDKを使う判断

最小ループを一度書いた後なら、フレームワークやSDKの選定は「機能比較」ではなく「どの肩代わりに価値があるか」で判断できます。

- **Messages APIを直接使う**: ループが小さく、ツールが数本なら十分。依存が増えない分、挙動の説明責任を全部自分で持てます
- **Claude Agent SDK**: Claude Codeの中身（ループ、コンテキスト管理、権限制御）をそのまま自分のエージェントに流用する選択肢。ループを自作せずに、ツールと指示の設計へ集中できます
- **ワークフローツール**: 手順が固定の部分はn8nのようなツールに寄せ、エージェントは手数が読めない部分だけに絞る分担も現実的です

<LinkCard slug="claude-agent-sdk" />

判断の軸は冒頭のガイドと同じで、追加の複雑さは、それに見合う成果を示せるときだけ足す。フレームワークから入ると、この判断をする前に複雑さが固定されてしまいます。

## 作る順番のチェックリスト

最後に、この記事の内容を作業の順番に並べ直します。

1. ワークフローで足りないかを最初に確認する（足りるなら作らない）
2. 任せるタスクを1つに絞る
3. ツールを最小本数で定義する。説明文だけ読んで使い方が分かるかを人に確認する
4. 停止条件（ターン・予算・失敗・エスカレーション）をループより先に書く
5. 最小ループを書いて動かす
6. ツール呼び出しのログと「成功の定義」を入れる
7. 取り返しのつかない操作の禁止・制限を、プロンプトではなくツール実装側に置く
8. ここまで動いてから、フレームワークやSDKへの乗り換えを検討する

エージェント開発の情報はフレームワークの話題から始まりがちですが、本体は4つの要素だけです。小さく書いて、止め方と観測に投資する。遠回りに見えて、これが一番速い作り方でした。
