既存のREST APIをエージェントから使えるようにしたいとき、MCPサーバーを書くのはもう唯一の道ではありません。**OpenAPI仕様に注釈を2種類足すだけでMCPツール化する経路が、クラウド側に生まれています。** ただし、自作サーバーを55ツールまで手書きして運用してきた実感から言うと、宣言生成で消えるのは「ツールを生やす」工数だけです。手書きで本当に時間を使った部分は、生成では置き換わりません。

この記事は、手元にREST API資産があって「エージェント対応のためにMCPサーバーを書くべきか」を考えている人に向けて、宣言生成と手書きの2つの経路を比較し、分かれ目を整理します。

## 宣言生成: API GatewayがOpenAPI注釈からツールを出す

2026-09-24、Google Cloud API GatewayのMCP対応がPublic Previewになりました。一次情報はGoogle Developers Blogです。

<LinkCard url="https://developers.googleblog.com/turn-your-rest-apis-into-mcp-tools-with-google-cloud-api-gateway/" title="Google Developers Blog: Turn your REST APIs into MCP tools with Google Cloud API Gateway" />

仕組みは宣言的です。すでにデプロイしているOpenAPI仕様に対して、API管理側の有効化フラグ `x-google-api-management.mcp: true` を立て、各operationに説明付きの `x-google-mcp-tool` を付ける。この2種類の注釈でデプロイすると、既存のRESTのoperationがそのままMCPツールとしてエージェントから見えるようになります。原文の表現では「annotate the OpenAPI spec you already deploy, deploy it, and your existing REST operations are available as agent-ready MCP tools」。ツール発見はJWT認証で保護でき、追加インフラのプロビジョニングは不要（no extra infrastructure to provision）とされています。

ミドルウェアを1行も書かずに済む。これは既存API資産を持つ側には素直に強い話です。エージェント対応のためだけに、REST APIと同じ意味のことをするMCPサーバーをもう1つ書いて保守する——この二重管理が丸ごと消えます。

## 先に制約を数える——公式が明記している範囲

飛びつく前に、公式ブログが明記している制約を並べます。Public Previewの現時点で、次が書かれています。

- **OpenAPI 2.0は非対応**。3.0.x / 3.1.xが対象
- **HTTP 204など空ボディを返すoperationは露出されない**
- **深くネストしたスキーマは `tools/list` に完全には出ないことがある**
- **1ゲートウェイあたり最大1,000ツール**
- **MCPとmodel routingは同一API configで併用不可**
- **MCP resources / prompts / レスポンスストリーミング / Model Armorのペイロード検査は予定段階で未提供**

実務目線で効くのは1つ目と2つ目です。古いAPIほどSwagger 2.0のまま止まっているので、「注釈を足すだけ」の前に3.0系への移行という別の工事が挟まる場合があります。204を返す削除系・更新系のoperationが出てこない点も、CRUDのD（削除）だけツールにならない、のような歯抜けを生みます。

## 手書き側の実感: 時間を使ったのは「生やす」部分ではなかった

比較のもう一方、手書きの側は私の運用実感で書けます。SNS運用を自動化する自作MCPサーバーを、公式TypeScript SDKとCloudflare Workersで書いて、ツール55本まで育てて無人運用しています。実装の中身は以前の記事にまとめました。

<LinkCard slug="mcp-server-cloudflare-workers" />

55本を手書きしてきて振り返ると、ツールを「生やす」部分——エンドポイントを叩いてJSONを返す層——に使った時間は、実はそれほど多くありません。時間を使った価値があったのは**断る側**です。入力スキーマで受け付ける形を固定する。Bearer認証で呼び出し元を絞る。公開系ツールに `confirm` を必須にして、渡されない呼び出しを実行前に落とす。公開回数の上限をKVに置いて、時間窓を超えた呼び出しをサーバー側で拒否する。

つまり手書きの工数の本体は「APIをツールとして見せること」ではなく「エージェントに何をさせないかをサーバー実装で固定すること」でした。ここが今回の比較の分かれ目になります。

## 分かれ目: 生成で消える層と、消えない層

宣言生成が置き換えるのは、露出の層です。I/Oの形をエージェントに見せる部分は、OpenAPIにすでに書いてあるのだから、そこから生成するのは理にかなっています。手書きでこの層を作っていた分の工数は、素直に消えます。

一方で、手書きに残る層が2つあると考えています。

**1つ目はツール表面の選別です。** 宣言生成はoperationとツールが原則1対1なので、APIの全operationがそのままツール候補になります。1,000ツール上限という数字自体が、この設計の裏返しです。ただ、エージェントに1,000本のツールを見せる運用はまずしません。どのoperationを見せて、どれを見せないか。露出の工数が消えた分、**選別が独立した設計作業として浮上します**。これは推測ではなく構造の話で、注釈を付けるoperationを選ぶ作業がその選別そのものです。ツールを数える話は、MCP対応ツールの評価軸の記事でも書きました。

<LinkCard slug="mcp-write-tools-evaluation" />

**2つ目は実行前の判定です。** confirm必須のような「引数が揃っていても条件を満たさなければ実行しない」判定や、回数上限のような状態を持つ拒否は、I/Oの形の宣言では表現しきれない層です。注釈だけでどこまで表現できるかは私は未検証ですが、少なくとも現時点の公式ブログにこの層の記述はありません。ゲートウェイの外側——バックエンド側か、間に挟む層——のどこかに、結局は書くことになるはずです。

## 判断基準——どちらから始めるか

整理すると、選び方は資産と要件で決まります。

1. **OpenAPI 3.0系のREST資産があり、読み取り中心でエージェントに見せたい**: 宣言生成から始めるのが速いです。サーバーを書く理由がありません
2. **資産がSwagger 2.0のまま**: 移行工事が先です。その規模次第では、必要なツールだけ手書きした方が早い場合があります
3. **副作用のある操作（公開・削除・課金）をエージェントに渡す**: 実行前判定と回数上限をどこに置くかを先に設計してください。この層はどのみち生成されないので、ここが要件の中心なら手書きの比重が上がります
4. **ツール本数が多くなる**: 生成でも手書きでも、先に「見せない側」のリストを作ってください。露出が楽になるほど、選別の規律が効き目を決めます

私自身の環境は3が中心なので、いまの手書きサーバーを宣言生成へ移す判断はしていません。逆に、もし手元にあるのが社内の読み取り系REST API群なら、サーバーを書き起こす前にまず宣言生成を試すと思います。

「もうMCPサーバーを書かなくていい」は、露出の層に限れば正しい。ただしエージェントに仕事を任せる本番運用では、書かなくてよくなった層の下に、書くべき層がそのまま残っています。どちらの経路を選ぶにしても、消えた工数ではなく残った層から設計を始めるのが、遠回りに見えて近道です。
