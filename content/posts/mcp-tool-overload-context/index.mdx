MCPサーバーを足すほどエージェントは賢くなる——そう思って接続を増やしていくと、途中から逆のことが起きます。ツール定義はそのセッションで一度も呼ばれなくてもコンテキストに載る固定費で、増やした分だけ本題に使える領域が減るからです。

対策は「ツールを減らす」だけではありません。2026年10月のClaude Codeの更新で、起動時に常駐させる説明は既定4,096字まで、tool search（ツール検索）経由で後から読み込む説明は16,384字までという、2段構えの上限がはっきりしました。つまり設計の軸は、**選ぶための短い説明を常駐させ、使うための詳細は必要になってから読ませる**という書き分けです。この記事では、ツール定義がコンテキストを消費する仕組み、消費量の見積り方、そしてMCPサーバーを自作・運用する側のdescription設計とサーバー分割の実務を整理します。

## ツール定義は「使わなくても」毎セッション載る

MCPクライアントはサーバーに接続すると、ツールの一覧を取得します。このとき各ツールについて渡るのは、名前、何をするかのdescription、そして引数の構造を定義した入力スキーマです。モデルがツールを「選べる」ようにするには、この定義一式をモデルに見せておく必要があります。

ここが本題です。ツール定義は、そのツールを使う・使わないにかかわらず、セッションの頭でコンテキストに入ります。会話が始まる前から消費されている、純粋な固定費です。

- 10ツールのサーバーを1つ足せば、10ツール分の定義が全セッションに載ります
- そのセッションで1回も呼ばれなくても、載った分は返ってきません
- サーバーを3つ、4つと足すと、固定費は素直に合算されていきます

コンテキストウィンドウは有限なので、固定費が膨らむほど、コード・ドキュメント・会話履歴といった本題に使える残りが減ります。さらにコンテキストの前半が長くなるほど、応答のたびに処理する入力トークンも増える。「便利そうだから入れておく」を繰り返した結果、どのセッションでも使わないツール群に毎回支払っている、という状態は簡単に起きます。

MCPそのものの仕組みは入門記事（[MCPとは？](/blog/what-is-mcp)）で整理しているので、ここでは割愛します。押さえるべきは1点だけ。**接続＝定義の常駐**だということです。

## 消費量は「ツール数 × 定義の長さ」で決まる

固定費の大きさは、ツールの本数と、1本あたりの定義の長さの掛け算です。そして経験上、膨らみ方が読みにくいのは後者のほうです。

descriptionの長さは書き手の裁量ですが、入力スキーマは機能を正確に定義しようとするほど太ります。フィルタ条件のネスト、enumの選択肢、プロパティごとの説明文。丁寧に作られたツールほど、スキーマは長くなります。つまり「ちゃんと作ったサーバー」ほど固定費が高い、という少し皮肉な構造があります。

私は[Cloudflare Workersで自作したMCPサーバー](/blog/mcp-server-cloudflare-workers)にSNS公開系のツールをまとめて運用していますが、公開・計測・管理と用途の違うツールを1つのサーバーに同居させると、どの作業のセッションにも全ツールの定義が載ります。計測しかしない日も、公開ツールの定義分を払う。接続の単位がサーバーなので、同居はそのまま「抱き合わせの固定費」になります。

対策を考える前に、まず測るのが先です。Claude Codeなら`/context`でコンテキストの内訳を確認でき、ツール定義がどれだけ占めているかをセッション開始直後に見られます。感覚で「重そう」と削るのではなく、開始時点の占有を数字で見てから手を打つ。この観測の話は[コンテキスト管理の記事](/blog/claude-code-context-management)でも書いたとおりで、削減はいつも計測の後です。

## 「削る」方向で考えていたら、クライアント側は「2段構え」に進んでいた

ここからが、この題材を記事にしようと思った理由です。ツール定義の固定費問題への答えを、私はずっと「descriptionを短く削る」「ツールを減らす」という引き算で考えていました。ところがClaude Code側の直近の変更を追うと、進んでいる方向が違いました。全部を常駐させない、という構造側の答えです。

Claude Codeには、接続したMCPツールの定義をすべて起動時に送り込むのではなく、必要になったときにtool search（ツール検索）経由で定義を読み込む仕組みがあります。そして2026年10月の連続した更新で、この2つの層の上限がそれぞれ別の方向に動きました。

- **2.1.295（2026-10-08）**: tool search経由でモデルが読み込むMCPツールのdescriptionの打ち切りが、2,048字から**16,384字**に拡大
- **2.1.296（2026-10-09）**: 起動時にモデルへ送るMCPツールのdescriptionとMCPサーバーのinstructionsの既定上限が、2,048字から**4,096字**に変更

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code 公式changelog" />

もともと両方とも2,048字だった上限が、常駐側は4,096字、検索側は16,384字と、4倍の差をつけて分かれた。この非対称こそが設計のメッセージだと読んでいます。**常駐枠は「どのツールを選ぶか」を判断できる最小限のため、検索枠は「選んだツールをどう使うか」の詳細のため。** 説明をどちらの枠に載せるかを、サーバーを書く側が意識できるようになったわけです。

逆に言うと、常駐枠の拡大は2倍にとどまっています。「説明を長く書けるようになったから全部常駐で説明しよう」ではなく、長い説明はそもそも検索側に置く前提。固定費を減らす主導権の半分は、クライアントの機能ではなくサーバーのdescriptionの書き方にあります。

## descriptionの前半は「選ぶため」、後半は「使うため」に書く

この2段構えを前提にすると、自作MCPサーバーのdescriptionの書き方は次のように整理できます。

### 冒頭の1〜2文に選別基準を置く

常駐枠に確実に入るのは説明の先頭です。だから冒頭の1〜2文には、何をするツールかに加えて、**いつこのツールを選ぶべきか（そして、いつ選ぶべきでないか）**を書きます。

```text
悪い例:
「記事データを柔軟に取得できる汎用APIです。多彩なオプションを
サポートしています。（以後、全オプションの詳細が延々と続く）」

良い例:
「公開済み記事のメタデータ一覧を返します。本文が必要な場合は
articles_getを使ってください。——（詳細はここから後半へ）」
```

モデルがツールを取り違える原因の多くは、似たツールの選別基準が説明の奥に埋まっていることです。選別に効く情報が先頭にあれば、常駐枠が小さくても誤選択は減らせます。

### 詳細・制約・使用例は後半に寄せる

引数の使い方の例、ページネーションの作法、エラー時の挙動、レート制限。こうした「選んだ後に必要になる」情報は、説明の後半に寄せます。tool search経由なら16,384字まで読まれるようになったので、以前のように「2,048字で切られるから書けない」と諦めていた詳細を、置ける場所ができました。

私の自作サーバーのツール説明も、この変更を受けて仕分けし直す対象です。基準は「常駐枠に入るべき情報か、検索枠でよい情報か」。書きたい詳細を全部足すのではなく、置く先を選ぶ。ここを雑にやると、せっかくの2段構えが「長いdescriptionが2層に増えただけ」になります。

### サーバーのinstructionsも同じ扱い

サーバー全体の使い方を伝えるinstructionsも、起動時送出の既定上限4,096字の対象です。ツール横断の前提（認証の作法、全ツール共通の制約）だけに絞り、個別ツールで説明できることを重複して書かない。instructionsは全セッション・全ツール利用者が毎回払う、いちばん高い固定費だからです。

## 「手順を配る」ならツールではなくskillという選択肢も規格側に乗った

もうひとつ、置き場所の選択肢が増えています。2026年10月10日、CloudflareがAPI向けMCPサーバーでskill（エージェント向けの手順書ファイル群）の配信を始めました。「Skills over MCP」という拡張で、対応クライアントは`skills/list`でskillを発見し、`skill://`のURIで必要なファイルを読みにいく形です。

<LinkCard url="https://developers.cloudflare.com/changelog/post/2026-10-10-cloudflare-mcp-skills/" title="Cloudflare changelog: Skills now available via the Cloudflare API MCP server" />

以前に[MCPサーバーとスキルの使い分け](/blog/mcp-vs-skills)を書いたときは、「実行が要るならツール、手順の知識ならスキル」という軸で分けました。その軸は変わりませんが、同じMCPサーバーからツールもskillも配れるとなると、境界線の引き方がもう一段はっきりします。**実行の有無に加えて、「常駐させる価値があるか」が分け目になる。** 毎セッション選択肢に出ていてほしい操作はツールとして常駐させ、必要になってから読めばいい長い手順はskillとして配る。どちらも配布経路は同じMCPで済む、という形です。

ツールのdescriptionに運用手順を詰め込んでいるサーバーは、その手順をskill側へ逃がせないかを検討する価値があります。定義は軽く、知識は遅延読み込みで。方向はtool searchの2段構えと同じです。

## サーバーの分割と、接続の絞り込み

書き分けと並ぶもう1本の柱が、接続の単位の設計です。

- **用途でサーバーを分ける。** 公開系・計測系・管理系が1サーバーに同居していると、どの作業にも全部の固定費が付いてきます。分かれていれば、その日の作業に要るサーバーだけ接続できます
- **接続はプロジェクト単位で選ぶ。** Claude CodeならMCPサーバーの登録に[スコープの使い分け](/blog/claude-code-mcp-setup)があり、プロジェクトごとに接続する顔ぶれを変えられます。全プロジェクト共通で全サーバー、はいちばん高くつく構成です
- **「とりあえず接続」を定期的に棚卸しする。** 直近の作業ログでそのサーバーのツールを呼んだ形跡がなければ、外す候補。外しても、必要になったら足し直せばいいだけです

書き手としてdescriptionを磨くのがミクロの対策なら、接続の顔ぶれを絞るのはマクロの対策。1本ずつの説明をどれだけ削っても、要らないサーバーが1つ常駐していれば簡単に打ち消されます。効き目が大きいのは後者です。

## まとめ: 固定費は、測って、書き分けて、絞る

最後に、この記事の設計指針を並べます。

1. **測る**: セッション開始直後にツール定義の占有を確認する。削減の判断は数字の後
2. **選別基準を先頭に**: descriptionの冒頭1〜2文で「いつ選ぶか・選ばないか」を言い切る。常駐枠（既定4,096字）に入るのは先頭から
3. **詳細は後半に**: 使用例・制約・エラー作法は説明の後半へ。tool search枠は16,384字まで広がった
4. **instructionsは共通事項だけ**: 全セッションが払う最高額の固定費。個別ツールと重複させない
5. **手順はskillへ**: 常駐する価値のない長い手順書は、Skills over MCPのような遅延読み込みの経路を検討する
6. **接続を絞る**: サーバーは用途で分割し、プロジェクトごとに要るものだけ接続する

ツールを足せば足すほど賢くなる、は半分だけ正しくて、固定費の設計を伴わない追加はどこかで本題の領域を侵食し始めます。クライアント側の仕組みは「全部常駐させない」方向へ進みました。サーバーを書く側・接続を選ぶ側も、同じ方向に揃えるのが2026年10月時点の答えだと考えています。
