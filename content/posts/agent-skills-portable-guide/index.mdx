結論から言うと、Agent Skills（SKILL.md）の移植性を決めるのは、何を書くかより**何を書かないか**です。スキル本体に書くのは手順・判断基準・完了条件だけ。ツールの実体、プロジェクト固有の文脈、権限はスキルに書かず、実行するホスト側へ残します。GitHubが2026年11月に公開した実務ガイドも、この線引きを設計の中心に置きました。

想定読者は、Claude CodeやGitHub Copilotでスキルを書き始めた実装者と、チームへスキルを配る形を考えている方です。スキルの作り方そのものは一度書けるようになったけれど、気づくと特定のプロジェクトでしか動かないファイルになっている——その段階に向けて、13個のスキルを無人運用で回している構成から「書かない」規律の作り方を整理します。

## Agent Skillsとは——繰り返す作業を、レビューできるファイルにする

Agent Skillsは、エージェントに特定の作業のやり方を教えるファイル一式です。中心になるのはSKILL.mdというMarkdownファイルで、frontmatterに名前と説明を持ち、本文に手順を書きます。Anthropicが2025年10月に[エージェントへ専門作業を教える仕組みとして発表](https://www.anthropic.com/news/skills)し、Claude Codeでは`.claude/skills/`配下に置くと、作業内容に応じてエージェントが自分で読み込みます。

このスキルという単位が、2026年11月にエージェント横断の話になりました。GitHubが公開した実務ガイド「Build once, run on any agent」（2026-11-12公開・2026-11-15確認）は、スキルを「繰り返すエンジニアリング作業を、チームがレビューして再利用できるファイルへまとめるもの」と定義し、一度作ればどのエージェントでも動かせる書き方を正面から扱っています。

<LinkCard url="https://github.blog/ai-and-ml/github-copilot/build-once-run-on-any-agent-a-practical-guide-to-agent-skills/" title="GitHub公式: Build once, run on any agent — a practical guide to agent skills" />

ここで押さえたいのは、スキルの実体がただのテキストだということです。コードでもAPIでもないので、gitで差分が見え、プルリクエストでレビューでき、コピーすれば配れます。「エージェントの挙動をファイルとして管理する」という点で、スキルはプロンプトの進化形というより、運用手順書の置き場所がエージェントの読める位置へ移ったものに近い。

Claude Code固有の作成手順——ディレクトリ構成、frontmatterの書き方、最初の1本の作り方——は以前の記事に書きました。今回はその次の段階、**エージェントやプロジェクトをまたいでも壊れない書き方**の話です。

## 「どのエージェントでも動く」の仕組み——能力はホストが供給する

同じMarkdownファイルが、なぜClaude CodeでもCopilotでも動くのか。答えは単純で、**スキル自身は何も実行しないから**です。

スキルが書いているのは「何を、どの順で、どう判断しながらやるか」だけ。それを実際に実行する能力——ファイルを読む、コマンドを走らせる、MCPサーバーのツールを呼ぶ——は、スキルを読み込んだホスト（Claude Code、Copilot、Agent SDKで組んだ自作エージェント）が供給します。GitHubのガイドはこの分担を明確に書いていて、**ツール、プロジェクトの文脈、権限の3つは、スキルではなく実行するホスト側に固有のまま残る**としています。

この分担は、MCPとの役割の違いとして見ると掴みやすいです。MCPはエージェントに能力（ツール）を足す規格で、スキルは使い方（手順と判断）を足す仕組み。どちらで実装するか迷う場面の判断軸は[MCPサーバーとスキルの使い分けの記事](/blog/mcp-vs-skills)に書きましたが、移植性の観点では「能力はホストとMCPが持ち、スキルはそれを前提の道具として使う」という層の分けがそのまま効いてきます。

裏を返すと、スキルは**ホストの供給物を書き込んだ瞬間に移植性を失います**。特定のツール接続設定、特定のリポジトリのパス、特定の権限前提。どれもスキルに書けてしまうし、書けば当面は動きます。ただそれは「どのエージェントでも動くファイル」ではなく、「この環境でしか動かない設定ファイル」をMarkdownで書いただけです。

## スキルに書くもの——手順・判断基準・完了条件

では何を書くか。運用して残ったのは3種類だけでした。

**手順**。作業の順番と分岐です。「AをしてからB」「Xの場合はC、それ以外はD」。エージェントは手順の行間を埋めるのは得意ですが、順序の意図までは推測できないので、順番に意味がある箇所ほど明示します。

**判断基準**。どちらに倒すかの基準です。私が運用しているSNS自動化のスキル群では、たとえば「公開前審査にPASSした原稿だけを次工程へ渡す」「2回修正してもFAILなら隔離して報告する」という基準をスキル本文に置いています。基準は「よい記事を書く」のような形容詞ではなく、**確認可能な条件**で書きます。PASSかFAILか、2回か3回か。エージェントが自分で判定できる形になっているかが線です。

**完了条件**。何が揃えば終わりかです。無人運用では人が途中で補正しないので、完了条件が曖昧なスキルは「終わったつもり」で止まります。「公開後にmanifestへslugが反映されたことを確認してから告知を起票する」のように、完了を観測する手順までを完了条件に含めます。

本文の3種類に加えて、frontmatterの**description**も「書くもの」側の重要な1行です。スキルは全文が常にエージェントへ読み込まれるのではなく、まず名前と説明だけが候補として見え、作業内容と合致したときに本文が読まれます。つまりdescriptionは紹介文ではなく**発動条件**です。「ブログ記事に関する作業では必ずこのスキルを使う」のように、どんな依頼のときに読まれるべきかが判定できる書き方にします。ここが曖昧だと、スキルは存在するのに使われない、という一番もったいない壊れ方をします。

この節に共通するのは、どれも**ホストが変わっても意味が変わらない**ことです。手順と判断と完了は作業そのものの性質であって、実行環境の性質ではありません。1つのスキルに複数の作業を詰めると、この性質が崩れて発動条件も書けなくなるので、分量が膨らんできたら「1スキル1責務」で分割します。

## スキルに書かないもの——ツールの実体・固有の文脈・権限・秘密

書かない側は4種類です。GitHubガイドの「ホスト固有のまま残る」3つに、運用上もう1つ足しています。

**1. ツールの実体と接続設定**。どのMCPサーバーへどう接続するか、認証情報をどう渡すかは、ホストの設定ファイルの仕事です。スキルには「画像を生成してアップロードする」という手順のレベルで書き、ツールの接続詳細を書き込みません。接続設定をスキルに書くと、ホストの設定と二重管理になり、どちらかが必ず古くなります。

**2. プロジェクト固有の文脈**。固定ID、ファイルパス、スキーマ、記法ルールの類です。これはスキルへ書き写さず、**参照先ファイルに逃がして「実行時に読む」とだけ書きます**。私の運用では、ブログ執筆スキルは公開先リポジトリの記法ガイド（docs/writing-guide.md）を書き写さず、実行時に読む指示だけを持ちます。データベースの固定IDも同様に、スキーマ文書側に置いてスキルからは参照します。こうしておくと、記法やIDが変わってもスキルの版は上がらず、ガイド1枚の更新で全スキルが追従します。

**3. 権限**。「このコマンドは実行してよい」「この操作は禁止」の類をスキルの文章で守らせないことです。スキルは指示であって強制ではありません。守らせたいルールはホストの権限設定とフックでコードとして強制し、スキルには書かないか、書くとしても二段目の注意書きとして扱います。禁止事項をプロンプトに書くだけでは守られない、という話は[ガードレール設計の記事](/blog/ai-agent-guardrails)に整理した通りで、スキルも同じです。むしろスキルはプロンプトより再利用されるぶん、「文章で禁止したから大丈夫」の影響範囲が広がります。

**4. 秘密情報**。トークンや資格情報の実値です。スキルはレビューして配る前提のファイルなので、秘密が1行入った瞬間に配れないファイルになります。これは移植性以前の話ですが、「動いたから」とスキルへ実値を貼る事故は起きやすいので、点検項目として明示しておく価値があります。

## スキルは厚くするほど賢くなる、と思っていた

運用を始めた頃の私は、逆の方向に進んでいました。スキルに書き足すほど挙動が安定するはずだ、と考えて、手順も文脈も注意書きも1つのSKILL.mdへ積んでいく。短期的にはそれで動きます。

効いたのは逆でした。いま13個のスキルで毎日の執筆・審査・計測を無人で回していますが、安定に寄与したのは書き足した量ではなく、**スキルから追い出した量**です。記法ガイドは公開先リポジトリへ、固定IDはスキーマ文書へ、禁止事項の強制は設定とフックへ、ブランドの定義はブランド文書へ。スキル本体には手順と判断基準だけが残り、結果としてどのスキルも「参照先を読んで、手順どおりに進め、基準で判定する」という同じ形になりました。

理由は2つあります。1つは変更の局所化です。厚いスキルは、記法変更でもID変更でも毎回スキル自体の改訂になり、13個へ同じ修正を撒くことになります。薄いスキルなら参照先の1枚を直すだけです。

もう1つは監査可能性です。指示追従が強いモデルほど、ファイルに書いてあることをそのまま実行します。古い注意書きや一時しのぎの一文が残っていれば、それも実行されます。OpenAIが[GPT-6 Astra移行時の指示ファイル監査](/blog/gpt-6-astra-agents-md-audit)を公式に推奨したのはまさにこの構図で、スキルが薄ければ監査は手順と判断基準の確認で済みますが、厚いスキルは「どの行が生きているのか」から調べることになります。

この「書かない」規律を支えるために、スキルとそれ以外の層を分けています。権限設計・フック・審査基準のような**守らせる層は、スキルから変更できない場所**に置き、スキル側は実行手順の層として版数を持たせ、変更のたびにCHANGELOGへ適用日・変更・根拠を1件記録する。指示ファイルをどの層に置くかという設計は、CLAUDE.mdとAGENTS.mdの整理として別記事に書きました。

## 移植性の点検リスト——配る前に見る6項目

手元のスキルを配る前、またはエージェントをまたいで使う前に、次の6項目を確認しています。

1. **ツール名の直書きに依存していないか**。「◯◯ツールを呼ぶ」ではなく「何をするか」のレベルで書けていれば、ホスト側のツール構成が変わっても手順は生きます
2. **固定ID・パス・スキーマを参照先へ逃がしたか**。スキル本文を検索して、環境が変わると無効になる値が残っていないかを見ます
3. **権限をスキルの文章だけで守らせていないか**。「禁止」と書いた行があるなら、同じ内容がホスト側の設定やフックで強制されているかを突き合わせます
4. **秘密情報の実値が入っていないか**。トークン、資格情報、内部URLの類です
5. **完了条件と失敗時の挙動が書いてあるか**。別のホストで動かしたとき、途中で止まったのか完了したのかを判別できる書き方になっているか
6. **版数と変更記録があるか**。配ったスキルは配った先で古くなるので、どの版かを特定できる印がないと、挙動の差を調べる手段がなくなります

6項目のうち1〜4が「書かない」側、5〜6が「書く」側の点検です。比率として、消す点検のほうが多い。それがこの記事で一番伝えたかったことでもあります。

## まとめ——線引きは、どこから見ても同じ場所に落ちる

Agent Skillsの書き方を整理しました。

- スキルに書くのは**手順・判断基準・完了条件**。いずれも確認可能な条件で書く
- 書かないのは**ツールの実体・プロジェクト固有の文脈・権限・秘密情報**。ツールと文脈と権限はホスト側に残るというGitHubガイドの線引きは、運用の実感とも一致する
- 固有の文脈は参照先ファイルへ逃がし、スキルは「実行時に読む」とだけ書く。守らせたいルールはスキルではなく設定とフックで強制する
- スキルには版数と変更記録を持たせ、配った後に挙動を追える形にする

この線引きの面白いところは、動機が違っても同じ場所に落ちることです。チームで配りたい人は秘密と固有値を消すことになり、エージェントをまたぎたい人はツールと権限の前提を消すことになり、長く保守したい人は変更が局所化するよう文脈を追い出すことになる。どの入口から入っても、スキルは「手順と判断だけの薄いファイル」へ向かいます。最初から薄く書くのが、結局いちばん早道です。
