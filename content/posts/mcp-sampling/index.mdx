結論から言うと、MCPのsamplingは「ツールを実行しているサーバーが、クライアント側のLLMに生成を依頼する」仕組みです。サーバーは自分でAPIキーを持たず、モデルも選ばず、生成だけを頼める。MCPサーバーを書く側から見ると「鍵なしでLLMが使える」おいしい機能に見えます。

ただ、先に言い切っておきます。**「鍵が要らない」の正体は「決定権がない」です。** どのモデルで動くか、そもそも応答が返るか、いつ返るか。その全部がクライアントとユーザーの側にあります。生成が機能の本体になるツールをsampling頼みで設計すると、動かすクライアントが変わった瞬間に壊れます。

この記事では、samplingの仕組みを仕様の一次情報から整理し、「借りてよい場面」と「依存してはいけない場面」の線引きをまとめます。想定読者は、MCPサーバーを自作している方と、エージェントの機能をどのプリミティブで組むか設計している方です。

## samplingとは。サーバーからモデルへの「逆向き」の依頼

MCPのやり取りの基本方向は、クライアントからサーバーです。エージェントが`tools/call`でツールを呼び、サーバーが結果を返す。samplingはこの向きが逆転する機能の一つで、処理中のサーバーが`sampling/createMessage`リクエストをクライアントへ送り、クライアント側のLLMに生成させた結果を受け取ります。

<LinkCard url="https://modelcontextprotocol.io/specification/2025-06-18/client/sampling" title="MCP仕様 2025-06-18: Sampling" />

仕様の要点は4つです。

1. **使えるのは、クライアントが対応を宣言した場合だけ。** samplingはクライアント側のオプションcapabilityで、初期化時に宣言していないクライアントへサーバーが依頼を送ることはできません
2. **依頼の中身は、ほぼ普通のチャット呼び出し。** メッセージ列と`maxTokens`を必須に、システムプロンプト、temperature、停止シーケンスなどを添えられます
3. **モデルは「希望」までしか言えない。** `modelPreferences`でモデル名のヒントと、コスト・速度・知能の3つの優先度（0〜1）を渡せますが、仕様はこれを助言と位置づけ、最終決定はクライアントに残します
4. **応答には、実際に使われたモデル名が入る。** サーバーは「何かのモデルが生成した結果」と「それがどのモデルだったか」を受け取ります

用途としてイメージしやすいのは、ツール実行の途中で要約・分類・言い換えのような「知的な下請け」が欲しくなる場面です。ページを取得して要約まで返すツール、大量のログから異常らしい行を選ばせるツール。従来この部分は、サーバー側に自前のLLM呼び出しを実装するしかありませんでした。つまり、鍵と課金ごと抱えるしかなかった。

## なぜ「サーバーに鍵を持たせない」が要るのか

samplingがない世界を考えると、この設計の動機が見えます。

要約機能つきのMCPサーバーを配布するとします。生成をサーバー内で完結させるなら、サーバーはどこかのLLM APIを直接呼ぶことになる。するとサーバーを動かす人全員に、APIキーの用意と課金の管理が発生します。モデルの引退や値下げのたびに追従するのもサーバー作者の仕事です。ツール1本のために、モデル運用を丸ごと背負う構図になります。

samplingはこれをクライアントへ委任します。ユーザーは自分がすでに契約しているモデルをそのまま使い、サーバーはどのベンダーのモデルかを知らなくていい。`modelPreferences`で言えるのは「速さ重視で」「知能重視で」「この名前に近いモデルがあれば」という希望までで、クライアントは同等の別モデルへ読み替えてかまわない、と仕様自身が書いています。

ここまでが、samplingの表の顔です。鍵も、課金も、モデル更新への追従も手放せる。配布するサーバーほど効く、きれいな委任の設計だと思います。

## 依頼の形は、ほぼチャットAPI。固有なのはmodelPreferences

実装イメージを持つために、依頼の形も見ておきます。サーバーがクライアントへ送る`sampling/createMessage`は、おおよそこういうリクエストです（仕様のサンプルを要約の例に置き換えたものです）。

```json
{
  "method": "sampling/createMessage",
  "params": {
    "messages": [
      {
        "role": "user",
        "content": {
          "type": "text",
          "text": "次のリリースノートを3行で要約してください。（本文略）"
        }
      }
    ],
    "modelPreferences": {
      "hints": [{ "name": "claude" }],
      "costPriority": 0.3,
      "speedPriority": 0.8,
      "intelligencePriority": 0.5
    },
    "systemPrompt": "あなたは簡潔な技術文書の編集者です。",
    "maxTokens": 300
  }
}
```

メッセージ列、システムプロンプト、`maxTokens`。LLMのチャットAPIを一度でも触っていれば、ほぼ既視感のある形です。コンテンツはテキストのほか、画像や音声も仕様上は送れます。

MCP固有の部分は`modelPreferences`に集まっています。`hints`のモデル名は部分一致で評価され、複数並べれば優先順になります。しかもクライアントは、ヒントに挙がった名前のモデルを持っていなければ、**同等と判断した別モデルへ読み替えてよい**。3つのpriorityも「コストをどれくらい重視するか」を0〜1で伝えるだけの相対値です。応答側はこうなります。

```json
{
  "role": "assistant",
  "content": {
    "type": "text",
    "text": "（生成された要約）"
  },
  "model": "（クライアントが実際に選んだモデル名）",
  "stopReason": "endTurn"
}
```

`model`フィールドに入るのは、サーバーが指定したものではなく「クライアントが選んだ結果」です。リクエストとレスポンスのどちらを見ても、モデルの決定権がクライアント側に置かれていることが形に出ています。

## 「鍵が不要」の裏返しは「何も保証されない」

ところが仕様を読み進めると、この機能の建て付けが「サーバーが自由に使えるLLM」ではないことが分かります。

仕様はsamplingに人間の関与を強く組み込んでいます。ユーザーが依頼を拒否できるhuman in the loopを常に置くべきだとし、クライアントはサーバーへ送るプロンプトも、サーバーへ返す生成結果も、ユーザーがレビューして握れる形にすべきだとしています。つまりsamplingの実体は、**ユーザーの監督付きで又借りするLLM**です。

サーバー側から見ると、保証されないものが4つあります。

- **対応**: オプションcapabilityなので、宣言しないクライアントには依頼を送ることすらできない
- **承認**: human in the loopが入る以上、ユーザーが断れば応答は返らない
- **モデル**: ヒントは助言で、何で生成されるかは最後までクライアント次第
- **内容**: 返す前にユーザー側でレビュー・修正される余地が、仕様上の推奨として存在する

[elicitationの記事](/blog/mcp-elicitation)で、「どのプリミティブも『誰がそこにいる前提の機能か』を持っている」という整理をしました。elicitationの宛先は人そのもの。samplingの宛先は一見モデルですが、承認の建て付けを挟む以上、実質の宛先は「モデルと、それを監督する人」のペアです。鍵が要らないのは、鍵を持っている人の監督下に入るから。そう読むと、この機能に何を預けてよいかが決めやすくなります。

## 無人実行では、承認ステップを誰が押すのか

この建て付けが一番きしむのが、定時実行やヘッドレス実行です。

人の承認を前提にしたステップは、無人の経路では「全部自動で許可する」か「全部断る」かのどちらかに倒すしかありません。全部許可に倒すなら、仕様が置いた安全装置（送るプロンプトと返る結果を人が見る）を自分の手で外すことになります。全部断るなら、sampling依存のツールは無人経路で必ず空振りします。対話では動いたのに無人では動かない、あるいは動くけれど誰も中身を見ていない。elicitationと同じ型の罠が、宛先を変えてもう一度現れます。

なお、承認UIをどう作るか、無人セッションで自動承認の設定を持つかどうかは、仕様ではなく各クライアントの持ち物です。無人運用でsampling依存のサーバーを使うなら、使うクライアントがこの場面をどう扱うかをドキュメントと実際の挙動で確かめてから、依存を決めるのが安全です。

## 線引き。「本体」なら持つ、「添え物」なら借りる

ここまでを、設計の判断に畳みます。samplingを使うか迷ったら、この3つを自分に聞くのがおすすめです。

1. **その生成が返らなくても、ツールの主目的は果たせるか。** 果たせないなら、samplingは土台にできません。生成はサーバー側で自前の鍵を持つか、後述のとおり呼び出し元へ寄せます
2. **結果の品質は、モデル選択に敏感か。** 敏感な処理をヒント止まりの指定に乗せると、クライアントが変わるたびに品質が揺れます
3. **動かすクライアントを、自分で決められるか。** 社内の固定構成なら対応状況を前提にできますが、不特定のクライアントへ配布するサーバーほど、オプションcapability前提は持ち込みにくくなります

借りると決めた場合も、実装には逃げ道を用意します。クライアントのcapabilityは初期化時に分かるので、samplingが宣言されていなければ、生成を添える機能を落として素材だけを返す。そして「要約は省略しました。このクライアントはsamplingに対応していません」のように、**何が欠けたかを結果に明示する**。黙って劣化すると、呼び出し側のエージェントは欠けた部分を創作で埋めかねません。欠けたことを言葉にして返すのは、生成を借りる設計の最低限の作法だと思います。

そしてもう一つ、samplingを検討する前に思い出したい選択肢があります。**そもそも生成をサーバーでやらない**ことです。MCPツールの呼び出し元には、たいていエージェント、つまりモデルがいます。ツールは取得や変換といった決定的な仕事だけを返し、要約や判断は呼び出し元のモデルに任せる。素材を返すのがツール、料理するのがエージェント、という分担にすると、samplingなしで同じ結果になる場面はかなり多いはずです。この分担の考え方は[tools・resources・promptsの使い分けの記事](/blog/mcp-tools-resources-prompts)で整理しています。

逆にsamplingが活きるのは、クライアント環境が固定されていて対応を前提にでき、かつ「返らなくても本体は壊れない」添え物の生成を、サーバー作者が課金を抱えずに足したい場面です。候補名の提案、エラーメッセージの平易化、分類ラベルの仮付け。この距離感なら、借り物のLLMで十分です。

## 「借り物」と呼ぶと、設計が決まる

samplingは、サーバーがクライアントのLLMをユーザーの監督付きで借りる仕組みです。鍵・課金・モデル追従を手放せる代わりに、対応・承認・モデル・タイミングの決定権も一緒に手放します。

だから判断はシンプルです。生成が機能の本体なら、自前で持つ。添え物なら、借りる。迷ったら、呼び出し元のエージェントへ寄せて、ツールは決定的な仕事に絞る。「鍵が要らない」という入口の魅力ではなく、「何が保証されないか」から決めると、samplingは置き場所のはっきりした道具になります。

仕様の他のプリミティブとの全体像は、[tools・resources・promptsの使い分け](/blog/mcp-tools-resources-prompts)と[elicitationの整理](/blog/mcp-elicitation)もあわせてどうぞ。
