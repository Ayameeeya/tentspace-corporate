結論から言うと、Claude Codeの`deniedMcpServers`でMCPサーバーを名前（`serverName`）で拒否するのは「一覧から見えなくする」操作であって、実行を止めるセキュリティ制御ではありません。止めたいなら、URL（`serverUrl`）かコマンド（`serverCommand`）で指定する。この区別が、2026年11月20日のv2.1.330で実際の挙動差として表に出ました。

想定読者は、Claude CodeにMCPサーバーを足してきて、そろそろ「使わせないサーバー」を設定で管理したい実装者。そして、エージェントに渡す接続先を統制したい側の方です。追加の設定（`claude mcp add`やスコープ）は別の記事で扱っているので、この記事は「止める側」だけに絞ります。

## deniedMcpServersとは何か

Claude Codeの設定には、MCPサーバーを拒否するリスト`deniedMcpServers`があります。ここに載せたサーバーは、セッションからは使えないものとして扱われます。エントリの指定方法は大きく3通りです。

- `serverName`: サーバーの名前で指定する
- `serverUrl`: 接続先のURLで指定する
- `serverCommand`: ローカルで起動するコマンドで指定する

一見するとどれも「そのサーバーを拒否する」同じ操作に見えます。実際には、この3つは効く範囲が違いました。それがはっきりしたのが、v2.1.330の変更です。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code公式変更履歴（v2.1.330）" />

前提をひとつ補足します。Claude Codeが繋ぐMCPサーバーには、ローカルでコマンドとして起動するものと、リモートの接続先へHTTPで繋ぐものがあります。さらにclaude.ai側で管理されるコネクタは、同じ接続先URLを複数のコネクタが共有する形があり得ます。今回の変更は、この「同じURLを共有するコネクタ群」をどう数えるかの話です。1つの接続先に入口が複数ある構成では、「どの単位で拒否が効くのか」が設定の意味そのものを左右します。

## 2.1.330で名前指定の効く範囲が縮んだ

公式変更履歴のv2.1.330（2026年11月20日付）と、その検証記事（DevelopersIO、2026年11月21日公開）によると、変更の内容はこうです。

v2.1.329までは、claude.aiコネクタを`serverName`（名前）で拒否すると、**同じURLを共有する他のコネクタも一緒に隠れていました**。v2.1.330からは、名前指定は指定したそのコネクタだけを隠します。同じURLの配下にあるコネクタをすべて塞ぎたい場合は、`serverUrl`で当該URLを拒否する必要があります。

<LinkCard url="https://dev.classmethod.jp/articles/20261121-cc-updates-v2-1-330/" title="DevelopersIO: Claude Code v2.1.330アップデートの検証" />

つまり「名前で1行書いておけば、裏で同じ接続先を向いている別の入口も止まっていた」状態が終わり、名前は名前の分しか効かなくなりました。破壊的変更と呼ばれているのはこの部分です。設定ファイルを1文字も変えていなくても、版を上げた瞬間に拒否の実効範囲が狭くなります。

症状として現れるとしたら、版を上げた後に、今まで見えていなかったコネクタが一覧へ現れる形です。ここで反射的に名前でもう1行足して消すと、また同じ構造に戻ります。現れたものを前に、消したいのか止めたいのかを決める。対処の分かれ目はそこです。

## 「セキュリティ制御ではない」という一文

この変更で私が重要だと思ったのは、挙動の差分そのものより、検証記事が引いているドキュメント側の整理です。`serverName`のエントリは**セキュリティ上の統制ではない**。どのサーバーが実際に動くかを決めたいなら、`serverCommand`か`serverUrl`を使うべきだと明記されています。

言い換えると、こうなります。

- 名前指定は、一覧の**表示を整理する**操作
- URL・コマンド指定は、**実行を決める**操作

名前は人間が後から付けたラベルで、同じ接続先に別の名前を付け直すことができます。ラベルを拒否リストに書いても、接続先そのものは塞がっていない。一方でURLとコマンドは「実際にどこへ繋ぐか」「実際に何を起動するか」という実体の側なので、ここで拒否すれば名前を何と付けようが届きません。

拒否したつもりの行が、実は表示を消していただけだった。v2.1.329まではたまたま名前指定でも広く隠れていたので、この取り違えが事故になりにくかったのだと読んでいます。挙動が正確になったことで、書いた設定の意図と実効範囲のずれが、今回初めて目に見える形になりました。

## 版を上げる前の棚卸し手順

この変更を踏まえると、`deniedMcpServers`を使っている環境で先にやることは設定の書き換えではなく、分類です。手順はこうなります。

1. **拒否エントリを3つに分類する。** 自分の設定にある`deniedMcpServers`の行を、`serverName`指定・`serverUrl`指定・`serverCommand`指定に分けて数えます。
2. **名前指定の行の意図を確認する。** その行は「一覧から消したい」のか「実行を止めたい」のか。止めたい意図の行が名前指定で書かれていたら、それが今回の影響範囲です。
3. **止めたい行をURLかコマンド指定へ置き換える。** リモートのサーバーやコネクタなら`serverUrl`、ローカル起動のサーバーなら`serverCommand`へ寄せます。
4. **置き換えてから版を上げ、前後で`/mcp`の一覧を比べる。** 拒否が意図どおり効いているかは、設定ファイルではなくセッション側の一覧で確認します。

私の判断としては、名前指定は「使わないサーバーを一覧から片付ける」整理用と割り切り、止める用途には最初からURL・コマンド指定だけを使う。この分担にしておけば、今回のような表示側の挙動変更があっても、統制の実効範囲は動きません。

なお、置き換え後にどの行がどう効くかを私はまだ自分の全環境で検証しきれていません。名前・URL・コマンドが混在した複雑な設定では、必ず自分の`/mcp`一覧での前後比較を正としてください。

棚卸しのとき、各エントリに対して立てる質問は3つに絞れます。

1. **この行は何を識別子にしているか。** 名前か、URLか、コマンドか。まずここを機械的に仕分けます。
2. **この行が消えたら何が困るか。** 「一覧がうるさくなるだけ」なら整理用の行です。「エージェントがそのサーバーを呼べてしまう」なら統制用の行で、名前指定のままでは用を成しません。
3. **この行の効きを、どこで確認しているか。** 設定ファイルのdiffしか見ていないなら、確認していないのと同じです。実効値はセッション側の`/mcp`一覧にしか現れません。

2番目の質問が特に効きます。書いた本人は「止めるため」のつもりでも、数カ月前の自分が整理のために足した行と区別が付かなくなっていることはよくあります。行ごとに目的を言えない拒否リストは、挙動変更のたびに意味が揺れます。

## 拒否や承認の境界は、版ごとに動く

もうひとつ、この件を単発のニュースとして流さないほうがいい理由があります。同じv2.1.330には、`deniedMcpServers`以外にも境界が動く変更が同居していました。公式変更履歴によると、ルートディレクトリやホーム、作業フォルダを対象にする`rm`コマンドのうち、より多くが承認を求めるようになり、承認に答える人がいない環境では拒否されます。また、スケジュール実行と`/loop`の継続上限は7日から30日へ延長されました。

つまり「止まるもの」「通るもの」「続くもの」の境界が、1つの版の中で同時に複数動いています。設定ファイルを変えていなくても、版を上げれば実効値が変わる。これはv2.1.330に限った話ではなく、変更履歴のChangedの欄には毎週のようにこの種の行が並びます。

無人で回している環境なら、なおさらです。人が画面を見ていれば「あれ、一覧から消えていない」とすぐ気づけますが、無人の経路では、拒否したつもりのサーバーが呼べてしまう状態も、逆に通るはずの操作が止まる状態も、静かに進行します。版を上げる前に変更履歴のChangedを読み、承認・拒否に触れる行があれば先に自分の設定を棚卸しする。この順番を習慣にする価値が、今回の変更で1つ増えたと思っています。

## 拒否リストの強度は「何を識別子にするか」で決まる

ここまでの話は`deniedMcpServers`固有の仕様ですが、構図はもっと一般的です。許可・拒否リストの強度は、ルールの数ではなく、**何を識別子にして書くか**で決まります。

同じClaude Codeの変更履歴には、v2.1.325（2026年11月13日付）の修正としてこういう一文もあります。Bashの許可ルール（allowルール）が、**そこに書かれた名前と違うプログラムを実行してしまう場合があった**。許可リストに書いた「名前」と、実際に動く「実体」は一致しないことがある。拒否側で起きたことと同じずれが、許可側でも起きていたわけです。

だから、リストを書くときの判断はこう整理できます。

- 表示・整理が目的なら、人間に読みやすい識別子（名前）でよい
- 実行の可否を決めるなら、実体に近い識別子（URL・コマンド・パス）で書く
- そのルールが「消す」のか「止める」のかを、エントリごとに言えるようにしておく

この整理は、権限設定を「渡さない・許す・止める・外側で強制」の4層で考える話の、「止める」層の中の解像度の話でもあります。層の全体像は以前に書いたので、設定全体を見直すときはそちらと合わせて読んでください。

逆方向の失敗も補足しておきます。この記事で扱ったのは「止めたつもりが止まっていない」側ですが、MCPサーバーには「使うつもりだったのに黙って外れている」側の失敗もあります。読み込まれない、セッションの途中で構成が変わる、通知なく外れる。そちらの切り分けは別の記事で整理しているので、拒否リストの棚卸しとセットでどうぞ。

## まとめ

- `deniedMcpServers`の`serverName`指定は、v2.1.330から指定したコネクタだけを隠すようになった。同じURLの他コネクタまでは隠れない
- ドキュメント上も、名前指定はセキュリティ制御ではないと整理された。実行を止めるなら`serverUrl`か`serverCommand`
- 版を上げる前に、拒否エントリを名前・URL・コマンドで分類し、「止めたい」行だけ実体側の指定へ置き換える
- 効き方の確認は設定ファイルではなく、前後の`/mcp`一覧で行う
- 同じ版には`rm`の承認拡大やスケジュール上限の延長も同居しており、承認・拒否の境界は版ごとに動く。無人運用では変更履歴のChangedを読んでから版を上げる

設定は書いた瞬間ではなく、挙動が変わった瞬間に読み直すものだと、また思わされた変更でした。拒否リストに限らず、「このルールは消すのか、止めるのか」を言えるかどうか。そこが無人で動かすエージェント設定の分かれ目だと思います。
