MCP（Model Context Protocol）とは、AIアプリケーションに外部のツールやデータをつなぐためのオープンな共通規格です。2024年11月にAnthropicが公開し、いまはClaudeに限らず、主要なAI開発エコシステムの多くが対応しています。

一言でいえば「AIアプリのUSB-Cポート」。接続の口を規格化しておけば、ツール側は接続コードを1回書くだけで、対応するどのAIアプリからも使えるようになります。公式ドキュメントもこの比喩で説明しています。

この記事では、MCPが解決する問題、プロトコルの中身、2つの接続方式、使い始める3つの入口を[公式ドキュメント](https://modelcontextprotocol.io)ベースで整理します。このブログでは自作MCPサーバーの実装記録も公開しているので、仕様の説明だけでなく「実際に運用するとどこが本題になるか」も最後に触れます。

## MCPが解決するのは「N×M問題」

MCP以前の世界では、AIアプリとツールの接続は個別実装でした。

たとえばチャットアプリにGitHub連携を足すなら、そのアプリ専用のGitHubプラグインを書きます。別のエディタでも同じGitHub連携が欲しければ、またそのエディタ専用に書き直し。AIアプリがN個、つなぎたいツールがM個あると、最悪N×M本の接続コードが要る計算になります。

MCPはこの間に共通のプロトコルを1枚挟みます。

- ツール側は「MCPサーバー」を1回だけ実装する
- AIアプリ側は「MCPクライアント」を1回だけ実装する
- 以後、両者は組み合わせ自由。N×MがN+Mになる

発表時のAnthropicの説明でも、断片化した個別実装を単一のプロトコルで置き換えることが目的として示されています。

<LinkCard url="https://www.anthropic.com/news/model-context-protocol" title="Anthropic: Introducing the Model Context Protocol" />

実際、この狙いはAnthropicの外にも広がりました。OpenAIの[Agents SDK](https://openai.github.io/openai-agents-python/mcp/)やGoogleの[Agent Development Kit](https://google.github.io/adk-docs/tools/mcp-tools/)もMCPサーバーへの接続をサポートしています。「Claude用の仕組み」ではなく、ベンダーをまたぐ共通規格として扱えるのが現在地です。

具体例を1つ。このブログのSNS運用自動化では、SNSへの投稿やSlackへの通知といった操作を、MCPのツールとしてエージェントから呼ぶ構成を[実装記録](/blog/mcp-server-cloudflare-workers)として公開しています。個別サービスのAPI仕様を知っているのはサーバー側だけで、エージェント側が知っているのはMCPの話し方だけ。この分業がMCPの価値です。

## function callingとは何が違うのか

「それ、function callingと何が違うの？」はMCPの定番の疑問なので、先に片付けておきます。

function calling（tool use）は、モデルが「このツールをこの引数で呼びたい」と構造化して返すための、**モデルAPIの機能**です。各社のモデルAPIに組み込まれていて、呼ばれたツールを実際に実行するのはアプリ側の仕事でした。つまり、ツールの定義を集めてくる・実行する・結果を返すという周辺の配線は、これまでアプリごとの個別実装だったわけです。

MCPはこの配線部分の規格です。ツールをどう公開するか、どう見つけるか、どう実行を依頼するかをプロトコルとして決めます。モデルがツールを選ぶ頭脳はfunction callingのまま、ツールの調達口をMCPが標準化する。対立する技術ではなく、層が違う補完関係です。

RAGとの関係も同じ整理ができます。RAGは「検索した文脈をモデルに注入する」設計パターンで、MCPはその検索先（社内文書、DB、ナレッジベース）への接続口を規格化できます。「RAG vs MCP」という比較を見かけたら、層の違う話が混ざっているサインです。

## 仕組み：ホスト・クライアント・サーバーの3役

MCPの登場人物は3つです。

- **ホスト**: ユーザーが触るAIアプリ本体。Claude CodeやClaudeのデスクトップアプリなど
- **クライアント**: ホストの中に居て、サーバーと1対1の接続を張る部品
- **サーバー**: ツールやデータを提供する側。GitHub用、Notion用、自社システム用など

ホストは複数のクライアントを持てるので、「Claude CodeにGitHubサーバーとNotionサーバーを同時につなぐ」構成が普通に組めます。通信はJSON-RPC 2.0ベースで、接続時にお互いの対応機能をネゴシエーションします。

サーバーがホストへ提供できるものは、大きく3種類に分かれています。

- **tools**: モデルが呼び出す操作。「Issueを作る」「クエリを実行する」など、実行の主導権はモデル側
- **resources**: アプリが文脈として読み込むデータ。ファイルやDBのレコードなど
- **prompts**: ユーザーが選んで使う定型テンプレート

日常の体感では、ほとんどの連携は tools が主役です。「MCP対応」と聞いたら、まず「どんなtoolsが生えるのか」を見るのが手っ取り早い理解の近道です。ちなみにサーバーからクライアント側へ依頼する機能（samplingやelicitation）も仕様にはありますが、最初は「そういう拡張もある」程度の認識で困りません。

つないだ後の流れも単純です。

1. 接続時にクライアントとサーバーが初期化のやり取りをして、対応機能を確認する
2. クライアントがツール一覧を取得し、各ツールの名前・説明・入力スキーマをモデルに見せる
3. モデルが「このツールをこの引数で呼びたい」と言ったら、クライアントがサーバーへ実行を依頼し、結果を会話に戻す

ポイントは2です。モデルがツールを選ぶ材料は、サーバーが自己申告した名前と説明文。つまりMCPサーバー作りの品質は、コードと同じくらい「ツールの説明文の書き方」で決まります。自作するなら、ここが一番の推敲ポイントです。

## 接続方式は2つ：stdioとStreamable HTTP

MCPサーバーの動かし方は、仕様上2つの標準トランスポートに整理されています。

- **stdio**: サーバーを手元のマシンでプロセスとして起動し、標準入出力でつなぐ方式。ローカルのファイルやCLIを触るサーバーに向きます
- **Streamable HTTP**: サーバーをWeb上に置き、HTTPでつなぐ方式。チームでの共有や、常時稼働させたいサーバーに向きます

初期の仕様にあったHTTP+SSE方式は、[2025年3月26日改訂の仕様](https://modelcontextprotocol.io/specification/2025-03-26/changelog)でStreamable HTTPに置き換えられました。少し古い記事を読むときは、この改訂の前後どちらの話かに注意してください。

選び方の目安は単純で、「自分のPCの中のものを触らせたいならstdio、どこからでも使いたいならStreamable HTTP」です。SNS投稿やSlack通知のようにWeb側の仕事だけをするサーバーなら、Cloudflare Workersのような実行環境にStreamable HTTPで置く構成が素直です。

## MCPが決めるのは「つなぎ方」だけ

ここが入門時にいちばん誤解しやすいポイントです。MCPは接続の規格であって、それ以上のことは何も保証しません。

- つないだツールを**いつ・どう使うか**を決めるのはモデルとホスト側の実装
- ツールの**出来の良し悪し**はサーバー実装者の責任
- **安全かどうか**も規格の外側。サーバーは自己申告で「私はこういうツールです」と名乗るだけ

とくに3つ目は運用で効いてきます。外部のMCPサーバーをつなぐことは、その作者のコードに自分の環境への入口を渡すことと同義です。つなぐ前の最低ラインとして、次の3つは確認する価値があります。

- 誰が公開しているサーバーか（公式か、個人か、フォークか）
- 渡すトークンの権限は最小か（読み取りで足りる用途にフル権限を渡さない）
- 書き込み系のツールが何本生えるか（読むだけのつもりが、消せる・送れるツール込みだった、はよくあります）

それでも規格側が守ってくれるわけではないので、何を許し、何を断るかの設計は別途必要です。ここは1本の記事になる分量なので、別記事に切り出しています。

## 使い始める3つの入口

立場によって、MCPとの最初の接点は3パターンに分かれます。

### 1. 既製のサーバーをつないで使う

いちばん多い入口です。Claude Codeなら `claude mcp add` コマンドで接続できます。公式・サードパーティのサーバーは[コミュニティのレジストリ](https://github.com/modelcontextprotocol/registry)やベンダー各社の公式ドキュメントから探せます。設定の置き場所やスコープの考え方は、次の記事で手順にしています。

<LinkCard slug="claude-code-mcp-setup" />

### 2. 自分のツールをサーバーとして自作する

社内システムや自作サービスをAIから触らせたい場合はこちら。[公式SDK](https://github.com/modelcontextprotocol)がTypeScript・Pythonを含む複数言語で提供されていて、最小のサーバーなら数十行で立ちます。Cloudflare Workersで本番運用するまでの構成と判断は、自作入門の記事に実装記録としてまとめています。

### 3. 既存のAPIをMCP化して公開する

すでにREST APIを持っているサービスなら、それをMCPツールとして見せ直す選択肢もあります。OpenAPI定義からの自動生成と手書き実装の分かれ目は、[別の記事](/blog/rest-api-mcp-tools)で比較しました。

## つなぐほど賢くなる、は逆だった

最後に、仕様書には載っていない運用の話を1つ。

直感的には、サーバーを足すほどエージェントは賢くなりそうに見えます。実際は逆方向の力が働きます。接続したサーバーのツール定義は、毎回モデルのコンテキストに載ります。つまりツールを足すほど、モデルが常に抱える荷物が増え、関係ないツールまで選択肢に入って判断がぶれやすくなる。コストも静かに増えます。

だから運用の本題は「何をつなぐか」ではなく「何をつながないか」になります。この作業にGitHubは要るのか。この定時処理にブラウザ操作は要るのか。接続を絞る判断軸は、[設定ガイド](/blog/claude-code-mcp-setup)とツールの使い分けの記事でそれぞれ扱っています。

## まとめ：規格の理解は30分、設計はそこから

整理します。

- MCPはAIアプリと外部ツールをつなぐオープンな共通規格。接続コードのN×M問題をN+Mにする
- 登場人物はホスト・クライアント・サーバー。提供物の主役はtools
- 接続方式はローカルのstdioと、リモートのStreamable HTTPの2つ
- 規格が決めるのは「つなぎ方」だけ。使い方・品質・安全は設計の仕事

プロトコル自体の理解は、正直30分で足ります。そのあとに待っているのが、どのサーバーを許すか、ツールを何本に絞るか、断る仕組みをどこに置くかという設計の仕事。次の一歩には、接続してみる人は設定ガイドを、作ってみる人は自作入門をどうぞ。
