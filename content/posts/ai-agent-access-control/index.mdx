結論から言うと、サイトに来るAIエージェントは「人間」とも「bot」とも別の、第3のトラフィックとして数えられる段階に入りました。2026年11月4日、Cloudflareがエージェント経由のアクセスを「Personal Assistants」というカテゴリで可視化し、エージェント単位で許可・制限・ブロックを選べる仕組みを発表しています。ただ、先に判断を言っておくと、この発表を読んで今やるべきことはブロックではなく計測です。対応エージェントの一覧も、識別の外部標準も、まだ公開されていないからです。

想定読者は、自社サイトやメディアを運営していて「AIエージェントにどう対応するか」を決めかねている方。それから、エージェント時代のbot対策を設計し直したい実務者の方です。前半で発表の中身を一次情報から整理し、後半で「どのサイトは何から始めるべきか」の判断を書きます。

## 「人かbotか」の二分法から、エージェントがはみ出し始めた

personal agentは、人の指示を受けて、調べ物や予約や購入をブラウザやAPI越しに代行するタイプのAIエージェントです。サイト側から見ると、これが扱いに困る存在でした。

従来のbot対策は、おおざっぱに言えば「人間は通す、botは種類に応じて制御する」という設計です。Cloudflareのbot分析にも、Verified Bot・Likely Human・Likely Automated・Automatedという区分が並んでいました。検索エンジンのクローラーのように身元を名乗る行儀のよいbotは通し、スクレイパーのような自動アクセスは絞る。この枠組みで長く回ってきました。

ところがpersonal agentは、どちらの箱にも収まりません。網羅的にページを集めるクローラーと違って、エージェントは「特定の1ユーザーの、その場の用事」で来ます。リクエストの規模は人間の閲覧に近いはずです。でも操作しているのは人間ではない。bot扱いで一律に止めれば、その向こうにいる実在ユーザーの用事を止めることになります。逆に人間扱いで素通しすれば、誰の代理が何件来ているのか、観測する手段がありません。

「robots.txtで指定すればいいのでは」と思うかもしれません。これも効きにくい。robots.txtは、網羅的に収集するクローラーが自主的に従う慣習です。宣言であって強制ではないうえ、想定しているのは「サイト全体を巡回する収集者」の行儀です。人の代理でピンポイントに1ページへ来るエージェントは、そもそもクローラーとして振る舞っていないので、クローラー向けの行儀作法だけでは制御の枠に入りません。配信の手前に立つインフラ側で、識別して、数えて、通すか決める。そういう層が必要になります。

この「どちらでもない訪問者」に専用の箱を用意したのが、今回の発表です。

## Cloudflareが追加した4つの機能を一次情報から読む

発表の内容は大きく4つです（2026年11月4日公開、確認日2026年11月5日）。

### Bot分析に「Personal Assistants」カテゴリが加わった

Security AnalyticsのBot Analysisに、前述のVerified Bot / Likely Human / Likely Automated / Automatedと並ぶ形で「Personal Assistants」カテゴリが追加されました。エージェント経由のトラフィックが、人間ともbotとも混ざらずに1つの箱として見える。可視化の土台はここです。

### エージェント別のリクエスト数ウィジェット

Top statisticsに、エージェント別のリクエスト数を示すウィジェットが加わりました。1つのエージェントで絞り込むと、そのエージェントが踏んでいるパス、返しているステータスコード、ネットワークへ、他のウィジェットも追従します。「エージェントが来ているか」の次の、「どのエージェントが、どこで、何をしているか」まで降りられる作りです。

### Account Abuse Protection——止める単位が「bot」から「利用者」へ

early accessとして公開されたAccount Abuse Protectionは、各エージェントがどの利用者を代理しているか、各エージェントを使っているアカウント数、ログインやサインアップがpersonal agent由来かを表示します。そしてHashed User IDという仕組みで、特定のアカウントにだけWAFルールを適用できます。他の利用者にはブロックをかけずに、です。

### ポリシーは「AI Crawler and Agent access policies」へ

既存のAgentsポリシーは「AI Crawler and Agent access policies」へ改称され、対応するpersonal agentごとに、Allow（ブロックしない）／広告のあるページではBlock／Blockの3択を、サイト全体のポリシーとは別に選べるようになりました。検索向け・学習向けのポリシーは変更なし。また、新しくゾーンを登録するときのオンボーディングでは「広告で収益を得ているか」を尋ね、答えに合わせて推奨ポリシーを変えるようになっています。

## 「ブロックできる」は主役ではない——一覧も識別標準も、まだ無い

機能一覧だけ読むと「エージェントをブロックできるようになった」が主役に見えます。私の読みは逆で、この発表で実務に使えるのは可視化の側だけです。発表のページを読み込むと、制御の足元に3つの空白があります。

1つめ。**対応するpersonal agentの一覧が公開されていません**。エージェント単位でAllow/Blockを選べると言っても、その「単位」に何が並ぶのかがページには書かれていない。

2つめ。**識別が外部標準ではなく、Cloudflare自身のbot intelligenceに依存します**。ページが挙げているのは自社のverified botディレクトリとHashed User IDで、業界で合意された識別の仕組みがあるわけではありません。エージェント側が名乗りを上げる標準がない以上、識別には誤りも取りこぼしもあり得ます。

3つめ。**Account Abuse Protectionはearly access**です。今後の予定として、エージェント経由で利用者の文脈をプライバシーに配慮して運ぶ方法、エージェントの評判評価、責任の所在の確立が挙げられていますが、時期の明示はありません。

この3つを踏まえると、今Blockを入れるのは割に合いません。誤識別すれば実在ユーザーの用事を巻き添えにし、未対応のエージェントは素通りする。止めた効果も止めた損害も、どちらも測れない状態でスイッチだけ先に押すことになります。一方で計測には空白の影響がない。来ているなら件数が見え、来ていないならゼロが見える。どちらでも判断材料になります。

もう1つ、この発表で面白いのはAccount Abuse Protectionの設計思想です。「怪しいエージェントを止める」のではなく、「エージェントの向こうにいる悪い利用者だけを止める」。bot対策の単位が、bot種別からエージェント越しの個別アカウントへ動いています。これはエージェントのアクセスを前提として受け入れたうえで、濫用だけを削る発想です。ブロック機能の追加と同じリリースに、ブロックしない前提の機能が入っている。提供側自身が、一律遮断を本命と見ていないように読めます。

## 計測で何を答えられるようにするか——3つの問い

「まず数える」と言っても、眺めるだけでは判断につながりません。計測の目的は、次の3つの問いに自分のサイトの数字で答えられるようにすることです。

**問い1: エージェント経由のアクセスは、全体の中で無視できる量か。** Personal Assistantsカテゴリの件数を期間で見ます。ゼロに近いなら、ブロックの検討自体がまだ不要です。逆に目に見える割合があるなら、次の問いへ進む価値があります。

**問い2: エージェントはどのページに来ているか。** エージェント別ウィジェットで絞り込むと、踏んでいるパスまで追えます。来ているのが商品ページなのか、ドキュメントなのか、問い合わせフォームなのかで、その流入が収益の敵なのか味方なのかは変わります。広告で成り立つページに集中しているなら「広告ページのみBlock」の検討材料になり、ドキュメントに来ているなら迎える整備の優先度が上がります。

**問い3: ログインやサインアップにエージェントが混ざっているか。** 会員機能のあるサイトなら、認証の経路にエージェント由来が混ざり始めているかは、不正対策の設計を変える分岐点です。Account Abuse Protectionが見せようとしているのは、まさにここです。

この3つに数字で答えられる状態を作ってから、初めてポリシーのスイッチに手をかける。順序を逆にしないことが、この段階では一番大事だと考えています。

## サイト種別ごとの現実的な初手

問いへの答えはサイトごとに違うので、何から始めるかもタイプごとに分けて考えます。

**広告収益のサイト**。「広告のあるページではBlock」という選択肢が別枠で用意され、新規ゾーンのオンボーディングでも広告収益の有無を尋ねて推奨ポリシーを合わせる設計です。エージェント経由の閲覧は広告収益につながりにくい、という整理がこの設計の背景にあると読めます。それでも初手はBlockではなく、Personal Assistantsカテゴリの件数確認です。全トラフィックの何割がエージェント経由なのかが分からないうちは、ブロックの益も損も見積もれません。

**ECや会員制サイト**。本命はAccount Abuse Protectionの方向だと考えています。エージェント経由のログインやサインアップが見えること、濫用アカウントだけを狙い撃ちできることは、不正対策の粒度をちょうど必要なところへ合わせられる可能性があります。ただしearly accessなので、今は仕様の変化を追いながら様子を見る段階です。

**技術ブログやドキュメントサイト**。エージェントに読まれること自体が、人へ届く導線の一部になりつつあるタイプのサイトでは、ブロックは逆効果になり得ます。むしろ「迎える側の整備」とセットで考える領域です。エージェント向けにサイト構造を案内するllms.txtのような仕組みについては、以前に実験した記事があります。

最後に自分の採否を明示しておきます。計測は使います。Personal Assistantsカテゴリを見るだけならリスクがなく、エージェント流入の実態という、これまで観測手段がなかった数字が手に入るからです。Blockは当面使いません。理由は前述の3つの空白です。なお、私自身のサイトでこのカテゴリの実トラフィックをまだ確認できていないため、「実際にどのくらい来ているか」の数字はここには書きません。未検証のことは未検証のままにしておきます。

## 止める前に、数える

今回の発表で確認できたことを整理します。

- サイトに来るAIエージェントは「Personal Assistants」カテゴリとして、人間ともbotとも別枠で可視化できるようになった
- エージェント別のリクエスト数・パス・ステータスコードまで追える
- エージェント単位のAllow／広告ページのみBlock／Blockを、全体ポリシーと別に選べる
- Account Abuse Protection（early access）は、エージェントではなく「エージェント越しの悪い利用者」だけを止める方向を示した
- 一方で、対応エージェントの一覧と識別の外部標準は未公開のまま

判断としては、可視化は今すぐ価値があり、ブロックはまだ材料不足。エージェントのアクセスは今後も増える前提で、まず自分のサイトにどれだけ来ているのかを数えるところから始めるのが、現時点の現実的な一手だと考えています。
