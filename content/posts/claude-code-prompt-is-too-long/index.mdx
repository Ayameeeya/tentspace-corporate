結論から言うと、Claude Codeの「Prompt is too long」エラーへの対処は2段あります。まず本体を2.1.310以降へ更新すること。このエラー後の圧縮（コンパクション）が効き切らず、同じエラーが繰り返される不具合が直っています。そしてもう1段が本題で、**巨大なツール結果を会話に入れない上流の設計**です。圧縮はあくまで最後の安全網で、網にかかりにくい「密なテキスト」がある以上、エラーが出てから削るのではなく、入り口で絞る方に重心を置くべきだと考えています。

この記事では、エラーの正体、圧縮という安全網の仕組み、2.1.310の修正が示した「圧縮で直らないケース」、そして会話を太らせないための設計を順に整理します。想定読者は、Claude Codeで長めのセッションを回していてこのエラーに当たった方と、`claude -p`やAgent SDKの無人実行を運用している方です。

## 「Prompt is too long」は何が起きているか

このエラーは、Claude Codeがモデルへ送ろうとしたリクエストが、コンテキストウィンドウ（モデルが一度に受け取れる入力の上限）に収まらなかったことを示します。Claude Codeは毎ターン、システムプロンプト、ツール定義、そしてそれまでの会話履歴——あなたの指示、モデルの応答、各ツールの実行結果——をまとめて送ります。つまり膨らむ本体は、たいてい会話履歴です。

膨らみ方には偏りがあります。手で打つ指示文が上限を圧迫することはまずありません。効いてくるのは**ツール結果**です。ログファイルの全文読み、巨大なJSONを返すAPI呼び出し、数千行のdiff、ビルド出力。1回の結果が数万字という塊は普通に発生し、それが会話に残り続けます。

ここで押さえておきたいのは、このエラーが「会話が長い」ではなく「**今回のリクエストが大きい**」という指摘だという点です。ターン数が少なくても、直前のツール結果が巨大なら出ます。逆に長い会話でも、後述する圧縮が効いていれば出ません。切り分けの起点はターン数ではなく、会話の中に居座っている塊の方です。

## 圧縮という安全網と、その置き場所

Claude Codeには、コンテキストが上限へ近づいたときに会話履歴を要約して詰め直す圧縮（コンパクション）の仕組みがあります。自動で走るほか、`/compact`で手動でも実行できます。要約である以上、細部は落ちます。どこまで何を残すかの使い分けと、「圧縮より先に`/clear`で区切る」という基本方針は、以前コンテキスト管理の入門記事にまとめました。

今回の話で大事なのは、圧縮の位置づけです。圧縮は「超えそうになってから削る」装置であって、会話に入ってくるものを選別はしません。そして要約で詰め直すという性質上、**何でも同じ比率で小さくできるわけではない**。ここに今回の不具合の種がありました。

## 圧縮しても直らないケースがあった——2.1.310の修正

2026年10月23日リリースのClaude Code 2.1.310に、こういう修正が入りました。「Prompt is too long」エラーの後に走る圧縮が、base64やSVGのような**密度の高いテキスト**を含む会話を削り切れず、圧縮したはずの次のリクエストも同じエラーで失敗することがあった、というものです。あわせて、トランスクリプト（会話記録）が非常に大きい場合の、非対話セッション（`claude -p`、Agent SDK）での圧縮時のメモリ使用量も改善されています。

<LinkCard url="https://code.claude.com/docs/en/changelog" title="Claude Code Changelog（公式）" />

私がこの修正を重要だと思うのは、不具合の直接の内容より、そこから読める構造の方です。エラーが出る、圧縮が走る、それでも同じエラーが出る——つまり**圧縮という安全網は、素材によっては網にならない**ことが、公式の修正という形で裏づけられました。2.1.310でこの症状自体は手当てされましたが、「圧縮で削りにくいものがある」という性質は、要約という方式に由来するものです。更新で症状が消えても、設計側の教訓は残ります。

なお、圧縮にはもうひとつ副作用があります。会話履歴を詰め直すということは、プロンプトの先頭側から内容が変わるということで、プレフィックス一致で効いているプロンプトキャッシュはそこで作り直しになります。圧縮が頻発するセッションは、上限との戦いと同時にコストの面でも損をしている。この構造は別記事で扱いました。

## 「密なテキスト」の正体

changelogが例に挙げたのはbase64とSVGでした。共通点を考えると、どちらも**冗長性が低く、要約で意味を保ったまま縮める余地がほとんどない**テキストです。自然文やコードなら「この関数は〜をする」と1行に畳めますが、base64の1万字を要約しても、その画像は復元できません。残すか捨てるかの二択になりやすい塊です。

実務で同じ性質を持ちやすいものを挙げておきます。

- 画像やバイナリを文字列化した**base64**（スクリーンショットの貼り付け、データURI）
- 図版として生成・取得した**SVGの生テキスト**
- ミニファイ済みのJS/CSS、ソースマップ
- 1行が極端に長い**巨大なJSON**（APIの生レスポンス、lockfileのdiff）
- エンコード済みデータの混ざったログ

こうした塊がツール結果として会話に入ると、以後のターンずっと上限を圧迫し続けます。圧縮が改善された2.1.310以降でも、塊が大きいこと自体のコストは消えません。

## まず止める: いま出ているエラーへの対処

エラーに当たっている最中なら、手順はシンプルです。前提として、いまコンテキストをどれだけ使っているかは`/context`で見られます。感覚ではなく数字で確認してから手を打つ方が、どの対処が効いたかも分かります。

1. **バージョンを確認して更新する。** 2.1.310より前で「圧縮後も同じエラーが続く」症状なら、まず更新です。上記の不具合そのものを踏んでいる可能性があります。
2. **`/compact`を手動で試す。** 更新後の圧縮は密なテキストの扱いが改善されています。指示付きで「◯◯の調査結果だけ残して」と要約の焦点を渡すと、落としたくない文脈を守れます。
3. **区切れるなら`/clear`で区切る。** いまのタスクに過去の経緯が要らないなら、要約より白紙の方が確実で、コストも安い。残したい結論だけ手でメモに書き出してから切る運用が堅いです。
4. **直前に貼った・読ませた巨大な塊を疑う。** エラーの直前に全文読みした大きなファイル、貼り付けた長大な出力があれば、それが本体です。次の節の入り口対策に進みます。

## 上流の設計: 会話に入れない

ここからが本題の2段目、エラーを出さないための設計です。方針は1つで、**会話履歴をストレージとして使わない**。大きなデータは会話の外（ファイル）に置き、会話には参照と抜粋だけを通します。

具体的には、こういう形に寄せます。

- **全文読みを既定にしない。** ログやデータファイルは、まずgrepで該当箇所を絞る、行数を指定して部分読みする。「とりあえず全部読んで」は、数万字の塊を会話へ招き入れる指示になります。
- **大きな出力はファイルへ逃がす。** 長いビルドログやAPIレスポンスは、リダイレクトでファイルに落としてから必要な範囲だけ読む。CLAUDE.mdに手順として書いておけば、エージェント側の既定の動きにできます。
- **base64やSVGを会話に貼らない。** 画像はパスで渡す、生成物はファイルに書かせてパスだけ受け取る。文字列化したバイナリを会話へ通すのは、圧縮で削れない重りを積む行為です。
- **MCPツールの返す量に上限を付ける。** 自作ツールなら、ページネーションや文字数上限を付けて「一度に全部返さない」設計にします。返しすぎるツールは、呼ぶたびに会話を太らせます。

どれも地味ですが、効き方は確実です。圧縮が「超えてから削る」のに対して、こちらは「そもそも積まない」。安全網の世話になる回数そのものが減ります。

## 非対話運用での注意

`claude -p`やAgent SDKの無人実行では、この問題の性質が少し変わります。対話なら、エラーを見た人間が`/clear`なり部分読みへの切り替えなりで介入できますが、無人セッションでは誰も止めてくれません。巨大なツール結果を抱えたまま圧縮とエラーを往復すれば、そのRoutineは黙って失敗します。

2.1.310で非対話セッションの巨大トランスクリプト圧縮のメモリ使用量が改善されたのは、裏を返せば、無人実行はトランスクリプトが巨大化しやすい使われ方だということでもあります。無人運用側でできることは対話以上に上流へ寄ります。

- **1セッションに詰め込まない。** 長い仕事はタスクを分割し、セッションを短く保つ。セッションをまたぐ文脈は、会話履歴ではなくファイルや外部の台帳に持たせます。
- **ツール結果の上限を設計時に決める。** 無人で呼ばれるツールこそ、返す量の上限が要ります。人がいないので「今回は多いな」という調整が効きません。
- **ヘッドレスの基本設計とセットで考える。** 出力形式、権限、ターン上限といった無人実行の枠組みは入門記事にまとめています。コンテキストの太り方も、この枠組みの一部として最初に決めておくのが結局安上がりです。

## 症状別の切り分け早見

最後に、症状から対処へ直行するための早見を置いておきます。

- **セッション開始直後に出た** → 会話が長いせいではありません。最初に読ませたファイルや貼り付けた内容に巨大な塊がないかを見ます。読ませ方を部分読みへ変えるのが先です。
- **長く使っていて出た。圧縮したら収まった** → 正常な上限到達です。ただし圧縮が頻発するなら、毎回のキャッシュ作り直し分のコストを払い続けています。タスクの区切りで`/clear`を挟む運用に変えます。
- **圧縮が走ったのに、また同じエラーが出る** → 2.1.310より前なら、まず更新。更新済みなら、会話の中に要約で削れない塊（base64、SVG、巨大JSON）が残っていないかを疑い、`/clear`で区切るか、塊の発生源だったツールの返し方を直します。
- **無人実行（`claude -p`、Agent SDK）のRoutineが途中で失敗していた** → ログでこのエラーを確認したら、そのRoutineのタスク分割とツール結果の上限設計を見直します。無人側は「エラーが出てから削る」が成立しないので、対処はすべて上流に置きます。

どのケースでも、「どの塊が会話を太らせたか」を特定せずに圧縮だけで逃げると、同じ場所でまた詰まります。犯人の特定が先、圧縮は後。この順番だけ覚えておけば、切り分けはだいたい迷いません。

## まとめ

「Prompt is too long」は、今回のリクエストがコンテキスト上限を超えたという信号で、犯人はたいてい会話に居座る巨大なツール結果です。2.1.310より前には、エラー後の圧縮がbase64やSVGのような密なテキストを削り切れず、同じエラーを繰り返す不具合がありました。まず更新、それから`/compact`と`/clear`の使い分け。ここまでが応急処置です。

そのうえで、恒久対策は上流にあります。全文読みを既定にしない、大きな出力はファイルへ逃がす、バイナリの文字列を会話へ通さない、ツールの返す量に上限を付ける。圧縮は要約である以上、削れない素材が必ずある——この前提に立つと、対処の重心は「超えたら削る」から「最初から積まない」へ自然に移ります。エラーの文言は上限の話をしていますが、直すべき場所は入り口です。
