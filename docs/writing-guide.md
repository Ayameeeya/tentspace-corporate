# 記事執筆ガイド

> 憲法層。本ガイドは、人間・AI を問わずすべての書き手が参照する記事記法の正本です。

## タイトルと description

- タイトルは32字前後を目安に、検索者が実際に打つ語を前半へ置きます。「実装記録」「設計メモ」などの内部の呼び名をタイトルの主語にしません。記録型であることは副題や本文で示します。
- 例: `〜の排他claim設計｜実装記録`ではなく、`AIエージェントの二重投稿を防ぐ方法｜Notionキューでの排他制御`のように、検索課題と解決内容を先に示します。
- descriptionは120〜140字を目安にします。冒頭の1文は読者が何を得るかから始め、何を作ったかの説明は2文目以降に置きます。
- 誇張せず、記事に無い約束を加えません。本文で説明していない成果、網羅性、再現性をdescriptionだけで約束しないでください。

## 利用可能な MDX コンポーネント

記事側で import は不要です。以下のコンポーネントは、すべての記事へグローバルに提供されます。

### LinkCard

一次情報や関連する記事を、タイトル・説明・画像・リンク先ドメイン付きの横長カードで示します。

内部記事は `slug` で指定します。タイトル、説明、カバー画像はコンテンツコレクションからビルド時に解決されます。存在しない slug や下書き記事を指定すると検証に失敗します。

```mdx
<LinkCard slug="claude-code-custom-skills-guide" />
```

外部ページは完全な `https://` URL を指定します。OGP と favicon はビルド時に取得され、キャッシュされます。記事に合わせて表示名を固定したい場合は `title` も指定できます。OGP を取得できなくても `title` があればカード外観を維持し、記事のビルドは継続します。

```mdx
<LinkCard url="https://blog.cloudflare.com/example/" title="Cloudflare公式：参考資料" />
```

`slug` と `url` はどちらか一方だけを、文字列として指定してください。`title` は外部ページの `url` と組み合わせる場合だけ使用できます。

## LinkCard の使い所

- 一次情報の主要リンクと、読者の次の理解につながる内部記事は、本文中のベタ貼りより LinkCard を推奨します。
- 目安は 1 記事につき 1〜4 枚です。
- 本文中の軽い言及や、文章の流れの中で読む短い参照はテキストリンクのままで構いません。
- カードだけを連続して羅列せず、それぞれのリンクを置く理由が分かる本文を添えます。

### Dialogue

記事が生まれた実際の会話を、話者ごとの吹き出しで再構成する導入コンポーネントです。記事側の import は不要です。

```mdx
<Dialogue>
  <Say by="hiro">別スレッドで話した内容を記事化したいときは、どうするのが楽ですかね</Say>
  <Say by="ai">一番楽な形は「話したスレッドの最後で一言」です。仕組みを作りましょう</Say>
</Dialogue>
```

利用できる話者は次の2名です。未定義の `by` はビルド時に検出されます。

- `hiro`: Hiro。右側・オレンジ系
- `ai`: AI。左側・グレー系

通常と異なる感情を伝える必要がある発言だけ、`mood` を指定できます。省略時は通常顔です。

```mdx
<Say by="hiro" mood="troubled">ちょっと困りましたね</Say>
<Say by="ai" mood="angry">それは見過ごせません</Say>
<Say by="hiro" mood="crying">これは悲しいです</Say>
```

利用できる表情は `normal` / `troubled` / `angry` / `crying` です。表情を装飾として多用せず、実在した会話の感情を補う場合だけ使います。

## Dialogue の使い所

- **記事冒頭の導入フック専用**です。本文の途中や結論には置かず、全編を対話形式にしません。導入で臨場感を作り、本文は地の文で書きます。
- 分量は **4〜8 往復**を目安にし、1発言は60字程度までの短い文にします。冒頭フックの範囲を超えて会話を引き延ばさないでください。
- **実在した会話の再構成のみ**に使います。読みやすい言い回しへの整形はできますが、存在しなかった発言を創作してはいけません。
- 対話の素材は、仮説ページの発注書にある「冒頭対話案」を正とします。

## 記事構成

- **結論先出しを鉄則**とします。導入の最初の地の文で、記事の結論を1〜2文で言い切ってください。Dialogue がある記事では、その直後を最初の地の文とします。読者が最初の10秒で「読む価値」を判定できる状態を作ります。
- その後の本文は、**起承転結のストーリーライン**で展開します。起（課題・背景）→承（試行）→転（設計が覆った瞬間・意外な発見）→結（結論の回収と運用）の流れを作り、**「転」を必ず1つ**置きます。
- 平坦な機能説明の羅列は避けます。「転」が見当たらない題材では、素材の中から予想と違った点を探して「転」にします。

> **構成の名前を見出しに書かない**。「起 / 承 / 転 / 結」「導入」「まとめ」などの構成ラベルは執筆時の設計語であり、記事の見出しには使いません。見出しは**その節の内容を表す具体的な文**にします。
>
> - ×「転: 比較していたはずが、エディタの役割のほうが縮んだ」
> - ○「比較していたはずが、エディタの役割のほうが縮んだ」
>
> 発注書（仮説ページ）のストーリーライン節に起承転結の表記がある場合も、それは**構成の指示**であって見出し文ではありません。

## 記事の分量

- ブログ記事の分量は、**5,000〜8,000字**を目安とします。
- 字数に届かせるための水増しは禁止します。足りない場合は、実装の具体、失敗記録、数値などの素材を足すか、題材を分割してください。

## 運用ルール

本ガイドは、人間・AI を問わず全書き手の正本です。**MDX コンポーネントを追加したら、必ず本ガイドに記法と使い所を追記します。** このリポジトリを読むエージェントは、個別のプロンプトへ記法を書き写さず、本ガイドを参照してください。

既存記事への遡及適用は不要です。リライトや情報更新の機会に、自然な範囲で LinkCard や Dialogue を適用します。
